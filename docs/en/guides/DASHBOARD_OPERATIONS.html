Dashboard Operations Runbook

Operational guide for Dashboard V2, persistent notifications, comparable snapshots, and machine-driven automation.

Deployment¶

API Process¶

uvicorn src.api.main:app --host 0.0.0.0 --port 8000

Dashboard routes are served from:

  • /dashboard for the frontend
  • /api/v2/dashboard/* for REST
  • /api/v2/dashboard/ws for realtime updates

Minimum Dashboard Config¶

dashboard:
  snapshot_enabled: true
  snapshot_interval_minutes: 60
  snapshot_retention_days: 365
  snapshot_db_path: data/dashboard_snapshots.sqlite
  notification_cooldown_seconds: 3600
  notification_delivery_audit_db_path: data/dashboard_subscriptions.sqlite
  notification_pending_db_path: data/dashboard_subscriptions.sqlite

Channel Secrets¶

Typical notification settings:

dashboard:
  notification_telegram_token: ${DASHBOARD_TELEGRAM_TOKEN:-}
  notification_telegram_chat_id: ${DASHBOARD_TELEGRAM_CHAT_ID:-}
  notification_slack_webhook_url: ${DASHBOARD_SLACK_WEBHOOK_URL:-}
  notification_webhook_url: ${DASHBOARD_WEBHOOK_URL:-}
  notification_webhook_auth_header: ${DASHBOARD_WEBHOOK_AUTH_HEADER:-}
  notification_smtp_host: ${DASHBOARD_SMTP_HOST:-}
  notification_smtp_port: ${DASHBOARD_SMTP_PORT:-587}
  notification_smtp_user: ${DASHBOARD_SMTP_USER:-}
  notification_smtp_password: ${DASHBOARD_SMTP_PASSWORD:-}
  notification_email_from: ${DASHBOARD_EMAIL_FROM:-}

Data Stores¶

Dashboard V2 now uses multiple persistent SQLite stores:

Store Default Path Purpose
Snapshot store data/dashboard_snapshots.sqlite Snapshot history, compare/export source data
Subscription store data/dashboard_subscriptions.sqlite Persistent notification subscriptions
Delivery audit store data/dashboard_subscriptions.sqlite by default Delivery attempts and statuses
Pending delivery store data/dashboard_subscriptions.sqlite by default Digest and quiet-hours queue

If needed, split delivery and pending paths from the subscription store by overriding:

  • dashboard.notification_delivery_audit_db_path
  • dashboard.notification_pending_db_path

Health Monitoring¶

API Health¶

curl http://localhost:8000/health

Prometheus Metrics¶

Dashboard health metrics are exported through the standard metrics endpoint.

Key gauges:

Metric Labels Meaning
codegraph_project_health_score project, group, language Composite project health
codegraph_project_audit_score project Audit score
codegraph_project_compliance_score project Compliance score
codegraph_project_release_status project Release status mapped to numeric gauge
codegraph_project_sca_health project SCA health
codegraph_project_sca_vulnerabilities project, severity Vulnerability counts
codegraph_portfolio_avg_health group Portfolio average
codegraph_red_zone_items_count project, category Red-zone item counts

Related assets:

  • grafana/dashboard_ciso.json
  • monitoring/rules/dashboard_alerts.yml

Expected Scheduler Logs¶

Typical messages:

INFO Snapshot scheduler started (interval=60 min)
INFO Snapshot collection complete: 15/15 projects
WARN Snapshot collection failed for broken-proj: ConnectionError
WARN Pending notification delivery flush failed: ...
INFO Snapshot scheduler stopped

Snapshot Operations¶

Manual Baselines¶

API:

  • POST /api/v2/dashboard/snapshots
  • GET /api/v2/dashboard/snapshots
  • POST /api/v2/dashboard/snapshots/compare
  • POST /api/v2/dashboard/snapshots/{snapshot_id}/export
  • GET /api/v2/dashboard/portfolio/compare-periods

CLI:

codegraph dashboard snapshot create --scope project --project my-service --reason "before patch"
codegraph dashboard snapshot list --scope project --project my-service
codegraph dashboard snapshot compare --from-snapshot <older> --to-snapshot <newer> --include-drilldown
codegraph dashboard snapshot export <snapshot_id> --baseline-snapshot <older> --format markdown

Release-Gate Snapshots¶

Release checks can automatically create pre/post snapshots.

Relevant config:

  • snapshot_release_pre_enabled
  • snapshot_release_post_enabled
  • snapshot_release_immutable
  • snapshot_release_retention_class

Release response fields:

  • pre_snapshot_id
  • post_snapshot_id
  • snapshot_diff

Portfolio Runtime Operations¶

Portfolio runtime reuses the same filtered scope across overview, history, saved views, alerts, and export.

Primary portfolio endpoints:

  • GET /api/v2/dashboard/portfolio
  • GET /api/v2/dashboard/projects
  • GET /api/v2/dashboard/red-zone
  • GET /api/v2/dashboard/compliance/heatmap
  • GET /api/v2/dashboard/sca/overview
  • GET /api/v2/dashboard/metrics/mapping
  • GET /api/v2/dashboard/portfolio/compare-periods
  • POST /api/v2/dashboard/export

Saved views and portfolio alerts:

  • GET /api/v2/dashboard/saved-views
  • POST /api/v2/dashboard/saved-views
  • GET /api/v2/dashboard/saved-views/{view_id}
  • DELETE /api/v2/dashboard/saved-views/{view_id}
  • POST /api/v2/dashboard/subscriptions

Operator expectation:

  • saved views must preserve the same filters and compare set used by the portfolio screen
  • portfolio alerts may target either scope=portfolio or scope=saved_view
  • export payloads should include the same filters, compare set, and saved-view identity shown in Web

Notification Operations¶

User-Facing Endpoints¶

  • GET /api/v2/dashboard/subscriptions
  • POST /api/v2/dashboard/subscriptions
  • PATCH /api/v2/dashboard/subscriptions/{id}
  • DELETE /api/v2/dashboard/subscriptions/{id}
  • POST /api/v2/dashboard/subscriptions/test
  • POST /api/v2/dashboard/subscriptions/bootstrap
  • GET /api/v2/dashboard/event-catalog

Operator Endpoints¶

  • GET /api/v2/dashboard/deliveries
  • GET /api/v2/dashboard/deliveries/summary
  • GET /api/v2/dashboard/deliveries/pending
  • POST /api/v2/dashboard/deliveries/process-pending

Bootstrap and First Live Data¶

/dashboard/notifications may legitimately start empty for a new user. The productized path for first live data is:

  1. configure at least one delivery channel or accept failed/pending local audit records
  2. create a project-scoped subscription or call bootstrap directly
  3. run POST /api/v2/dashboard/subscriptions/bootstrap
  4. confirm GET /api/v2/dashboard/deliveries/summary reports non-zero live_total or pending

CLI equivalents:

codegraph dashboard notifications summary --user-id acceptance-r4 --format json
codegraph dashboard notifications bootstrap --user-id acceptance-r4 --project codegraph --format json

Delivery Policies¶

Implemented behavior:

  • cooldown-based deduplication
  • quiet-hours defer
  • daily digest queueing
  • critical bypass for deferred policies
  • bounded retry/backoff for critical delivery paths
  • channel-aware redaction for sensitive details

Routine Checks¶

Use the summary and pending APIs to monitor:

  • failed delivery count
  • pending queue depth
  • channel-specific error concentration
  • test vs real delivery ratios

Truthful runtime rule:

  • test deliveries are not equivalent to live pipeline evidence
  • sales-deck screenshots captured by frontend/scripts/capture_sales_deck_ui.mjs use demo fixtures only

Machine Access for Automation¶

Dashboard automation should use service accounts, not personal tokens.

Admin API:

  • GET /api/v1/auth/service-accounts/action-catalog
  • POST /api/v1/auth/service-accounts
  • GET /api/v1/auth/service-accounts
  • GET /api/v1/auth/service-accounts/{id}
  • POST /api/v1/auth/service-accounts/{id}/rotate
  • POST /api/v1/auth/service-accounts/{id}/credentials/{credential_id}/revoke
  • POST /api/v1/auth/service-accounts/{id}/deactivate

CLI:

codegraph auth service-account create --owner admin --name ci-bot --template ci --interface api
codegraph auth service-account list --format json
codegraph auth service-account inspect --id <service-account-id>
codegraph auth service-account rotate --id <service-account-id>
codegraph auth service-account revoke --id <credential-id>
codegraph auth service-account deactivate --id <service-account-id>

Machine clients should send:

  • X-API-Key: <service-account-credential>
  • X-CodeGraph-Machine-Contract: <supported-version> when using machine-only flows

Operational notes:

  • quotas are enforced per service account
  • revoked credentials should fail immediately
  • API and MCP use the same scope/interface enforcement model

Backup and Recovery¶

Backup¶

Stop the API process or use SQLite backup semantics:

sqlite3 data/dashboard_snapshots.sqlite ".backup data/dashboard_snapshots.bak"
sqlite3 data/dashboard_subscriptions.sqlite ".backup data/dashboard_subscriptions.bak"

Restore¶

  1. Stop the API process.
  2. Restore the required .sqlite files.
  3. Start the API process.
  4. Verify: - /health - dashboard routes - GET /api/v2/dashboard/snapshots - GET /api/v2/dashboard/deliveries/summary

Reset Guidance¶

Do not reset stores casually in production.

  • resetting the snapshot store removes historical compare evidence
  • resetting the subscription store removes user subscriptions
  • resetting the shared notification DB may also remove delivery audit and pending queue state

Scaling Notes¶

  • Prefer one active snapshot scheduler instance for steady-state writes.
  • Multiple API instances are acceptable for read traffic and delivery APIs.
  • If multiple instances are deployed, ensure only one instance owns scheduled snapshot collection and pending-delivery flush.

Common Incidents¶

Pending Queue Keeps Growing¶

Symptoms:

  • GET /deliveries/pending returns many overdue items
  • GET /deliveries/summary shows rising pending

Checks:

  1. Verify the scheduler is running.
  2. Call POST /api/v2/dashboard/deliveries/process-pending.
  3. Inspect failing channels in GET /deliveries?status=failed.

Webhook Delivery Fails¶

Symptoms:

  • repeated failed deliveries on channel=webhook
  • last_error indicates HTTP auth or network failure

Checks:

  1. Validate notification_webhook_url.
  2. Verify notification_webhook_auth_header.
  3. Test the endpoint with POST /subscriptions/test.

Release Gate Returns No Snapshot Evidence¶

Checks:

  1. Confirm snapshot_release_pre_enabled / snapshot_release_post_enabled.
  2. Check API logs around release_gate.
  3. Verify snapshot DB write permissions.

Machine Client Starts Failing After Rotation¶

Checks:

  1. Confirm the new credential was distributed to the caller.
  2. Verify the old credential was not revoked before rollout.
  3. Check contract header compatibility with X-CodeGraph-Machine-Contract.

Verification Checklist¶

  • Dashboard pages load under /dashboard
  • /api/v2/dashboard/portfolio returns data
  • snapshots can be created, listed, compared, and exported
  • subscriptions/test succeeds for at least one configured channel
  • subscriptions/bootstrap creates or reuses a real project-scoped subscription
  • deliveries/summary and deliveries/pending return sane values
  • release-gate responses include snapshot evidence when enabled
  • service-account create/rotate/revoke path works for automation users
