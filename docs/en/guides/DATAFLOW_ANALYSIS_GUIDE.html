Analyze security data flows

Trace input data to sensitive operations. Audit a project or analyze a method through MCP, then inspect calls and sanitization.

User GuidesUpdated: 2026-10-03

Dataflow analysis helps answer a practical question: how does input data reach an operation that executes SQL, starts a command, or writes a file? CodeGraph searches the CPG for paths from a source to a sink and shows calls, code locations, and detected sanitization functions.

Use the result to review input handling, audit security, or check a fix. Follow the reported path, inspect data transformations, and compare them with the application’s execution conditions.

Task Analysis route What to inspect

Broad project audit

Install the CLI using the CLI guide. Run this PowerShell example from the CodeGraph repository root. You need an accessible GoCPG service and a current CPG for a registered project. CodeGraph uses the project, database, and source association to check freshness. Choose that project’s database and a new report file:

$env:CODEGRAPH_ALLOW_LOCAL_PYTHON_CLI = '1'
python -m src.cli audit --db 'C:/analysis/project.duckdb' `
  --profile deep_security --skip-persistence --skip-llm-conclusion --language en `
  --format json --output 'dataflow-audit.json'
if ($LASTEXITCODE -ne 0) { throw 'Audit failed' }
$report = Get-Content -Raw 'dataflow-audit.json' | ConvertFrom-Json

The report is written to the current directory and overwrites a file with the same name. Inspect freshness and analysis-completeness diagnostics. --skip-persistence skips audit projections, dashboard snapshots, and command history; it does not reduce scope. The output file is still written. --skip-llm-conclusion produces the report without an LLM conclusion. To include an LLM summary, configure a provider and remove this option. Inspect each check’s results and execution details in the report.

For Could not resolve a configured project/source context, choose a registered project’s database using the import guide. For a stale graph, refresh the CPG through the project workflow and repeat the audit.

Targeted taint path

Verify availability and invocation policy for codegraph_security_taint_analysis_run in the active profile. It requires method_name; defaults are source_category="user_input" and sink_category="sql". The supported source categories are user_input, file_read, network, and env. Supported sink categories are sql, command, file_write, xss, and buffer.

The current handler chooses the analysis category from nonempty sink_category, otherwise from source_category. Sources come from the domain plugin catalog; source_category is echoed as a supplied argument. The handler then filters returned paths by exact method name among crossed functions or the source/sink function. Configured path-count and time limits apply before this method filter. To continue the search, check the exact method name, limit diagnostics, and selected sink category.

Agent-facing calls use the current project context. Do not pass a raw storage path. If the tool is not available in the active profile, request the correct role/profile instead of substituting a retired name.

The tool uses GoCPG gRPC. See the MCP operator guide for setup. After selecting the correct project, call codegraph_security_taint_analysis_run with these arguments:

{
  "method_name": "<exact-method-name-from-your-CPG>",
  "source_category": "user_input",
  "sink_category": "sql"
}

Replace method_name with the exact name recorded in the current graph. This JSON is the argument object for an MCP call, not a REST request or a shell command. Inspect each returned path and its source/sink functions; use count as the number of returned paths, and record a verdict for each path after checking execution conditions.

The response contains method, the supplied categories, taint_paths, and count. The response echoes the supplied categories; analysis selection is described above. For an Error: ... response, restore access to the selected CPG using the error message and repeat the call.

Read a path

Read a path
Path field Reviewer action
source, sink Open the functions, files, and lines; check the input and sensitive operation.
path, functions_crossed Inspect the function sequence between source and sink.
sanitizers Check detected sanitization functions against the sink’s input requirements.
risk_score, risk_level, confidence Use analyzer estimates to prioritize review.
inter_procedural, tainted_fields Inspect function boundaries and tracked data fields.

Validate a finding

  1. Confirm the source is actually attacker-controlled in this execution context.
  2. Follow each call and assignment in the reported path.
  3. Check sanitization, validation, encoding, authorization, and trust-boundary transitions.
  4. Verify whether the sink is reachable with the reported data shape.
  5. Record the code revision, source/sink categories, evidence refs, and reviewer verdict.

After reviewing the reported paths, continue with the application’s remaining sources, sinks, and runtime boundaries.
