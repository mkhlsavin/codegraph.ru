Dashboard score methodology

Use this guide when a dashboard number affects prioritization, risk review, or a release decision. It explains what the project health score contains.

User GuidesUpdated: 2026-08-24

Use this guide when a dashboard number affects prioritization, risk review, or a release decision. It explains what the project health score contains, when the score is unavailable, and why freshness must be checked separately.

The current score_formula_version is v1. The response exposes both the version and score_breakdown, so a consumer does not have to reverse-engineer a single number.

Composite score

The score is clamped to 0–100 and combines five normalized components:

  • audit — 30%;
  • compliance — 25%;
  • release — 20%;
  • SCA — 15%;
  • quality — 10%.

The source defaults live in src/config/runtime_sections/unified_config_dashboard.py. A deployment may override them, so the response’s component weights are authoritative for a particular result.

Component normalization

  • Audit uses the 0–10 audit score divided by 10.
  • Compliance uses the 0–100 GOST 56939 score divided by 100.
  • Release maps pass to 1, warn to 0.5, and fail or an unknown value to 0.
  • SCA starts at 1 and subtracts 0.15 per critical, 0.08 per high, and 0.02 per medium vulnerability, then clamps the result to 0–1.
  • Quality has its own inner weights: runtime coverage — 40%; documentation coverage — 20%; dead-code ratio — 20%; complexity — 20%. Complexity reaches its maximum penalty at an average complexity of 20.

If runtime line coverage is unavailable, its quality input is zero and the breakdown retains the unavailability reason. Runtime coverage and successful test counts remain separate inputs.

Availability and score

Read health_score_available before reading the numeric value. CodeGraph marks the grade as N/A and the risk as unknown when the required evidence is not available. The response explains the cause with one or more stable reason codes:

  • audit_snapshot_missing;
  • compliance_report_missing;
  • release_gate_missing;
  • sca_summary_missing.

A missing input is therefore not equivalent to a bad but complete result. Fix or regenerate the missing evidence, then request the health response again.

Grades and risk levels

Default grade boundaries are:

Grades and risk levels
Grade Health score
A 85 or higher
B 70–84.99
C 55–69.99
D 40–54.99
F below 40

Risk adds operational signals to the numeric score:

  • critical: score < 40, a critical finding exists, or compliance is < 40;
  • high: score < 55 or the release gate is fail;
  • medium: score < 70 or the release gate is warn;
  • low: none of those conditions applies.

This means two projects with the same score can have different risk levels.

Freshness is a separate decision

A valid formula becomes actionable when its evidence is current. Inspect the analysis basis and surface freshness. The UI and API distinguish current, stale, missing, updating, failed, and unknown. Do not approve a release from a stale or unknown basis merely because the grade is high.

Reproducible check

Run:

python -m src.cli dashboard health <project> --format json

Verify health_score_available, score_formula_version, score_breakdown, risk_level, and the analysis basis together. Repeating the check against the same evidence revision should produce the same score.

Sources of truth

  • src/api/services/dashboard/aggregation_core/aggregation_scoring_mixin.py — normalization, contributions, grades, and risk.
  • src/api/services/dashboard/aggregation_core/aggregation.py — availability rules, output fields, and formula version.
  • src/config/runtime_sections/unified_config_dashboard.py — default weights and thresholds.
  • src/api/services/dashboard/surface_state/surface_freshness.py — freshness states and recovery metadata.

For navigation and actions, use the Dashboard user guide. For telemetry and alerts, use Monitoring.
