Dashboard score methodology

The dashboard has two distinct scoring layers: 1. a twelve-question project audit, Q1–Q12, on a 0–10 scale; 2. a 0–100 Health Score that combines Audit.

User GuidesUpdated: 2026-09-09

The dashboard has two distinct scoring layers:

  1. a twelve-question project audit, Q1–Q12, on a 0–10 scale;
  2. a 0–100 Health Score that combines Audit, Compliance, Release, SCA, and Quality.

Neither number replaces its underlying evidence. Before using it for a release decision, inspect the breakdown, provenance, and freshness. The audit’s technical foundation is a Code Property Graph. See How GoCPG builds a CPG and how the approach differs from Joern for the graph construction and enrichment pipeline. The component model, architecture DSL, presets, baseline/waiver, and release profiles are covered in Architecture control in CodeGraph.

How the Q1–Q12 audit is scored

Each section combines findings from its source scenarios with quantitative CPG metrics where a reliable mapping exists. The following table matches the Dashboard’s Help → Score source panel.

How the Q1–Q12 audit is scored
Section Question Primary scenarios and metrics
Q1 Readability and coding standards Refactoring; methods with many parameters.
Q2 Module structure and reuse Architecture; dependency cycles and Martin instability.
Q3 Redundant or hard-to-maintain code Refactoring and technical debt; long methods, dead code, and unreachable code.
Q4 Scalability Performance and architecture; structural bottlenecks.
Q5 Performance at volume Performance; average and maximum cyclomatic complexity.
Q6 Architecture for growth Architecture audit. There is no reliable universal metric substitute.
Q7 Vulnerabilities Security and compliance; high-risk hotspots, eval/exec, weak cryptography, and hard-coded secrets.
Q8 Injection and data exposure Security and entry points; SQL- and shell-injection paths.
Q9 Maintainability Technical debt and refactoring; TODO/FIXME markers, maintainability index, and configuration errors.
Q10 Testability and coverage Runtime line/method coverage and uncovered higher-risk methods.
Q11 Coupling complexity and extensibility Architecture and technical debt; complex-method ratio and inheritance depth.
Q12 Documentation Documentation and comment coverage for public entities.

Finding contribution

Synthetic findings already derived from metrics are not counted again in the severity weight. Other findings use these weights:

Finding contribution
Severity Weight
critical 1.00
high 0.70
medium 0.40
low 0.15
info 0.05

Repeated findings of the same severity have diminishing impact. If n is the zero-based occurrence number within a severity:

weight(n) = severity_weight / (1 + 0.3 × n)
W = sum of weight(n) for real findings in the section
base_section_score = 10 × exp(-0.3 × W)

A critical finding therefore matters more than an informational one, while a large set of identical messages does not increase the penalty linearly.

Metric contribution and insufficient data

After the severity calculation, the scorer applies the section metric penalty Pq:

section_score = round(clamp(base_section_score - Pq, 0, 10), 1)

The metric penalty is capped at 3 points for Q1–Q9, Q11, and Q12. Q10 has a separate calculation and may subtract up to 9 points. Q6 has no metric penalty: an architecture scenario must provide its evidence.

Missing data is not treated as a perfect result:

  • if no source scenario succeeded and there is no permitted metric basis, the section receives a neutral 5.0;
  • if there are no findings but usable metrics exist, scoring starts at 10.0 and applies the metric penalty;
  • a thin set of primary findings may cap the section at 8.0 or 8.8;
  • for metric-dependent Q1, Q3, Q5, Q9, Q10, Q11, and Q12, a missing total_methods basis produces a neutral 1.5 penalty instead of a false 10.0.

Q10 coverage rule

Method coverage has an 82% share and line coverage an 18% share:

coverage_score = clamp(
  10 × (0.82 × method_coverage + 0.18 × line_coverage)
  - risk_uncovered_penalty,
  0, 10
)
P10 = 10 - coverage_score

risk_uncovered_penalty includes uncovered critical/high methods, taint sources, API entry points, and graph-critical methods, capped at 2.5 points. Fail-safe caps also apply:

  • unavailable runtime coverage caps Q10 at 5.0;
  • line coverage < 5% and method coverage < 30% caps Q10 at 3.9;
  • line coverage < 20% and method coverage < 60% caps Q10 at 5.9.

A successful test count is not a substitute for runtime coverage.

Overall Audit score

overall_score_raw is first calculated as the mean of all twelve sections. CodeGraph then reduces the sensitivity of the headline number to the same risk being repeated in several sections. The defaults are:

blended = 0.30 × overall_score_raw + 0.70 × module_health
audit_score = round(clamp(min(overall_score_raw + 3.5, blended), 0, 10), 1)

module_health is a method-count-weighted mean across modules. Each module starts at 10 and receives bounded penalties for dead-code ratio (up to 3), maintainability index below 80 (up to 3), Martin instability (up to 2), and TODO density (up to 2). For a clean module with a maintainability index of at least 90, the instability penalty is multiplied by 0.35. These coefficients are configurable; the configuration version and persisted audit snapshot are authoritative for a particular result.

How the other components are scored

Compliance

The GOST R 56939 report assigns each process one status:

  • full = 1;
  • partial = 0.5;
  • gap = 0;
  • n_a is excluded from the denominator.
compliance_score = 100 × sum(process_value) / applicable_process_count

If no processes apply, the result is 0 rather than 100. Critical gaps remain separate evidence: equal percentages do not imply identical gap profiles.

Release

Release Gate runs the checks in the selected profile. Every check is either a blocker or a warning:

  • any failed blocker → fail;
  • no failed blocker, but at least one failed warning → warn;
  • all checks pass → pass.

An unknown profile, a check error, or an authorization failure is fail-closed. In the default standard profile, critical findings are prohibited, high findings are limited to five, average cyclomatic complexity is limited to 15, and coverage must be at least 55%. The last two checks are warnings. The gost-56939, standard, and minimal profiles have different check sets, so always read the profile ID and individual check results with the status.

SCA

The SCA component uses dependency vulnerability counts by severity:

sca = clamp(1 - 0.15 × critical - 0.08 × high - 0.02 × medium, 0, 1)

Low and informational vulnerabilities do not enter this formula, but remain in the SCA report. This formula scores the persisted severity summary; it does not replace reachability analysis.

Quality

complexity_norm = min(avg_complexity / 20, 1)
quality = 0.40 × runtime_line_coverage
        + 0.20 × documentation_coverage
        + 0.20 × (1 - dead_code_ratio)
        + 0.20 × (1 - complexity_norm)

All ratios are in the 0–1 range. If runtime line coverage is unavailable, its contribution is zero and the unavailability reason remains in score_breakdown.

Composite Health Score

The current score_formula_version is v1. The default formula is:

health_score = 100 × clamp(
  0.30 × audit/10
  + 0.25 × compliance/100
  + 0.20 × release
  + 0.15 × sca
  + 0.10 × quality,
  0, 1
)

Release maps pass to 1, warn to 0.5, and fail to 0. A deployment may override component weights, so the response’s score_breakdown is authoritative for a particular result.

What “Score source” means

The panel shows section provenance, not another score:

  • current — the section was recalculated from metrics for the current revision;
  • snapshot — current metrics were insufficient, so a fresh audit snapshot was used;
  • stale_snapshot — only an expired snapshot is available;
  • n_a — the section does not apply to this project;
  • needs_audit — no reliable current or snapshot basis exists.

The Dashboard overlay recalculates only sections with a dependable metric mapping. Q6, for example, remains needs_audit without a full architecture audit. By default a snapshot remains fresh for at most 168 hours, though a deployment may change that limit. Inspect source refs, revision IDs, and evidence timestamps.

The project surface separately reports current, stale, missing, updating, failed, or unknown. A high score on a stale or unknown basis does not authorize a release.

When the composite is unavailable

Read health_score_available before the number. If required evidence is missing, CodeGraph returns grade N/A and risk unknown. Stable reasons include:

  • audit_snapshot_missing;
  • compliance_report_missing;
  • release_gate_missing;
  • sca_summary_missing.

An unavailable input is not a zero score. Restore or regenerate the evidence before interpreting the result.

Grades and risk levels

Grades and risk levels
Grade Health score
A 85 or higher
B 70–84.99
C 55–69.99
D 40–54.99
F below 40

Risk also uses operational signals: critical for score < 40, a critical finding, or compliance < 40; high for score < 55 or Release fail; medium for score < 70 or Release warn; otherwise low.

Reproducible check

python -m src.cli dashboard health <project> --format json

Inspect health_score_available, score_formula_version, score_breakdown, risk_level, the audit snapshot, and analysis basis together. Repeating the check against the same evidence revision should produce the same result.
