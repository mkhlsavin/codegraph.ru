Getting Started¶

Accessing the Dashboard¶

The dashboard is a web application served from the CodeGraph API server. Once the server is running, open your browser and navigate to:

http://<host>:<port>/dashboard

For example, with default settings:

http://localhost:8000/dashboard

The dashboard loads the Portfolio Overview page by default. No additional setup is required — it reads data from the same CodeGraph API that powers the CLI and MCP tools.

URL Structure¶

All dashboard pages live under the /dashboard base path:

Page URL Description
Portfolio Overview /dashboard Home page, all projects at a glance
Project Detail /dashboard/projects/:name Single project deep-dive
Notifications /dashboard/notifications Subscription management, event catalog, delivery audit
Compliance Center /dashboard/compliance Cross-project compliance heatmap
Cross-Repo Analysis /dashboard/cross-repo Dependencies and duplication
SCA / SBOM Center /dashboard/sca Vulnerability and dependency overview

The :name parameter in the Project Detail URL is the project name (URL-encoded if it contains special characters).

Authentication¶

The dashboard uses the same authentication as the CodeGraph API. If JWT or OAuth2 is configured, you will be prompted to log in. API key authentication can also be used by including the X-API-Key header when accessing the API directly.

For automation, CI, and MCP/API consumers, prefer service-account credentials instead of personal API keys. Service-account access is documented in the enterprise RBAC guide and uses the same machine scope enforcement across API and MCP.

Portfolio Overview¶

The Portfolio Overview is the landing page. It presents a high-level summary of all registered projects and highlights areas requiring immediate attention.

KPI Cards¶

Six KPI cards appear at the top of the page:

Card Description Scale
Avg Health Average health score across all projects 0–100
Avg Audit Average audit quality score 0–10
Compliance Average GOST R 56939 compliance percentage 0–100%
Total Findings Sum of all audit findings across projects Count (red if critical > 0)
Vulnerabilities Total SCA vulnerabilities across projects Count (red if > 5)
Duplications Number of cross-repository code duplications Count

When a KPI value crosses its alert threshold, the number turns red to draw attention.

Project Cards¶

Below the KPI strip, each project is shown as a clickable card. A project card displays:

  • Project name — click to navigate to the Project Detail page
  • Language — programming language (uppercase label)
  • Risk level — colored dot: green (low), yellow (medium), orange (high), red (critical)
  • Grade badge — letter grade (A through F) in the top-right corner
  • Health score bar — horizontal progress bar, color-coded:
  • Green (85+), blue (70–84), yellow (55–69), orange (40–54), red (below 40)
  • Audit score and Compliance percentage — compact numbers at the bottom
  • Trend arrow — improving, stable, or degrading
  • Critical findings badge — appears only if the project has critical findings

Filters¶

Two filter dropdowns sit between the KPI cards and the project grid:

  1. Language filter — select a programming language to show only projects in that language. The dropdown is populated dynamically from the projects currently loaded.
  2. Risk filter — select a minimum risk level (critical, high, medium, low) to narrow results.

Filters are applied immediately. Clearing a filter (selecting “All languages” or “All risks”) shows all projects again.

Risk Distribution Donut¶

The right sidebar contains a donut chart that visualizes how projects are distributed across risk levels:

  • Green — low risk
  • Yellow — medium risk
  • Orange — high risk
  • Red — critical risk

The chart updates when filters change.

Release Readiness¶

Below the donut chart, the Release Readiness panel shows how many projects have each release gate status:

Status Color Meaning
pass Green All release gate checks passed; safe to release
warn Orange Some checks issued warnings; review before release
fail Red One or more blocking checks failed; do not release

Red Zone Alerts¶

The Red Zone panel at the bottom of the sidebar lists the most critical issues across all projects. Each alert shows:

  • Severity pill — critical or high
  • Project name — which project is affected
  • Message — brief description of the issue

Click any red zone item to navigate to the corresponding project’s detail page. A counter in the panel header shows the total number of red zone items.

Project Detail¶

Click any project card in the Portfolio Overview to open the Project Detail page. The URL format is:

/dashboard/projects/<project-name>

Health Summary Strip¶

The page header displays the project name, grade badge, risk dot, language, domain, and the latest audit commit hash. A trend arrow in the top-right indicates whether the project is improving, stable, or degrading.

Below the header, six mini-stat cards show key metrics at a glance:

Metric Description
Health Score Composite score out of 100
Audit Score Audit quality out of 10
Compliance GOST R 56939 compliance percentage
Release Gate Status indicator (PASS / WARN / FAIL)
Findings Total audit findings (red if critical > 0)
Test Coverage Unit test line coverage percentage

Audit Tab¶

The default tab. It contains four panels:

  1. 12-Dimension Audit Radar Chart — a radar (spider) chart plotting the project’s score across all 12 quality dimensions. See The 12-Dimension Radar Chart.

  2. Section Scores — a vertical list of all 12 dimensions with horizontal score bars (0–10 scale). Each row shows the dimension number (Q1–Q12), name, and filled bar.

  3. Findings by Severity — a 2x2 grid showing the count of findings at each severity level (critical, high, medium, low), each with a colored pill.

  4. Quality Metrics — a table of structural metrics: - Total Methods - Dead Methods (count and percentage) - Average Complexity - Maximum Complexity - Documentation Coverage - Dependency Cycles (SCC count)

Compliance Tab¶

Two panels side by side:

  1. GOST R 56939 — score bar, plus a 2x2 summary of process statuses: - Full (green) — fully met - Partial (yellow) — partially met - Gap (red) — not met - N/A (gray) — not applicable

If critical gaps exist, they are listed below as red badges showing the process IDs (e.g., 5.7, 5.11).

  1. GOST R 57580.3 — a table showing: - Maturity Level (out of 4) - Capabilities (out of 25) - Risk Score

Release Gate Tab¶

A single panel showing the release gate status with a colored indicator (PASS/WARN/FAIL) and a metrics table:

Field Description
Profile Active release gate profile (gost-56939, standard, or minimal)
Blockers Number of blocking issues (red if > 0)
Warnings Number of non-blocking warnings
Last Check Timestamp of the most recent release gate evaluation

SCA / SBOM Tab¶

Two panels:

  1. Dependencies — a table listing: - Total dependencies - Direct dependencies - Outdated packages - License risks (red if > 0) - SCA health score

  2. Vulnerabilities — a 2x2 grid showing vulnerability counts by severity (critical, high, medium, low).

Trends Tab¶

The Trends tab shows how the project’s metrics have changed over time.

Period selector — five buttons to choose the time window: 7d, 30d, 90d, 180d, 1y.

Delta badges — four compact indicators showing the change in health, audit, compliance, and findings over the selected period. Positive changes are green; negative changes are red. For the “Findings” delta, the logic is inverted — a decrease in findings is shown as positive (green).

Trend chart — a line chart plotting health score, audit score, compliance, and findings over time within the selected period.

The 12-Dimension Radar Chart¶

The radar chart is a spider diagram with 12 axes, one for each quality dimension. Each axis ranges from 0 to 10. The project’s score on each dimension is plotted as a point, and the points are connected to form a polygon. A larger polygon indicates a healthier project.

To read the chart:

  1. Look at the overall shape — a balanced polygon (roughly circular) indicates uniform quality across all dimensions.
  2. Identify concavities — any axis where the polygon dips inward represents a weak dimension.
  3. Compare against the maximum boundary — the outer edge represents a score of 10 on every dimension.

Quality Dimensions Reference¶

# Dimension What It Measures
Q1 Architecture Module structure, layering, separation of concerns
Q2 Complexity Cyclomatic complexity, nesting depth, function length
Q3 Dependencies External dependency count, coupling, import depth
Q4 Dead Code Unreachable functions, unused methods, dead code ratio
Q5 Duplication Clone detection, copy-paste code, structural similarity
Q6 Documentation Doc coverage, comment quality, public API documentation
Q7 Security Vulnerability count, taint analysis findings, CWE coverage
Q8 Error Handling Exception handling patterns, error propagation, null checks
Q9 Performance Algorithmic complexity, resource usage patterns
Q10 Testing Test coverage, test-to-code ratio, assertion density
Q11 Maintainability Readability, naming conventions, technical debt indicators
Q12 Code Style Formatting consistency, linting violations, style adherence

Compliance Center¶

Access via /dashboard/compliance. This page provides a cross-project view of GOST R 56939 compliance.

The header shows the standard name, the number of projects analyzed, and the number of processes evaluated. An Export GOST button downloads the compliance data in GOST format.

Three KPI cards appear at the top:

Card Description
Total Gaps Number of gaps across all projects and processes (red if > 0)
Processes with Gaps How many processes have at least one project with a gap (orange if > 0, shown as X / total)
Projects Analyzed Number of projects included in the analysis

Reading the Heatmap¶

The Compliance Matrix is a heatmap grid where:

  • Rows represent projects
  • Columns represent GOST R 56939 processes (e.g., 5.1, 5.2, …, 5.14)
  • Cells are color-coded by compliance status:
Color Status Meaning
Green FULL Process requirements are fully met
Yellow PARTIAL Process requirements are partially met; action needed
Red GAP Process requirements are not met; critical gap
Gray N/A Process is not applicable to this project

How to interpret the heatmap:

  1. Scan columns — a column that is mostly red or yellow indicates a process that is problematic across multiple projects. This is an organizational issue, not a project-specific one.
  2. Scan rows — a row with many red/yellow cells indicates a project that needs significant compliance work.
  3. Look for patterns — if the same processes are gaps across different projects, consider creating shared compliance tooling or templates.

Gap Analysis Table¶

Below the heatmap, the Gap Analysis table lists every process that has at least one project with a GAP status. The table is sorted by the number of affected projects (most gaps first).

Column Description
Process Process ID (e.g., 5.11)
Name Human-readable process name
Projects with Gap Number of projects that have a GAP for this process (shown as X / total)

The count turns red when more than 2 projects have a gap for the same process, and orange when more than 1.

GOST Export¶

Click the Export GOST button to download a JSON file containing compliance data formatted according to GOST R 56939 requirements. This file can be used for regulatory submissions and audit documentation.

Cross-Repository Analysis¶

Access via /dashboard/cross-repo. This page analyzes relationships and duplications across all repositories.

Four KPI cards at the top:

Card Description
Code Duplications Total number of detected cross-repository code duplications
Dependencies Total number of inter-repository dependency edges
Circular Deps Number of circular dependency chains (red if > 0)
Consolidation Candidates Number of functions recommended for consolidation into shared libraries

Dependency Graph¶

An interactive force-directed graph showing how repositories depend on each other:

  • Nodes represent repositories, labeled with the repository name and grouped by domain.
  • Edges represent dependency relationships between repositories.
  • Circular dependencies are highlighted in red to indicate problematic cycles that should be resolved.

Interaction: - Zoom — use the mouse scroll wheel to zoom in and out. - Pan — click and drag on the background to pan the view. - Drag nodes — click and drag any node to reposition it; the graph will re-settle around the new position.

Duplication Table¶

The Top Duplications table shows the most significant code duplications found across repositories:

Column Description
Code Code snippet or function name (truncated to 40 characters)
Repos Number of repositories containing this duplication
Lines Number of duplicated lines of code

Below the table, a severity breakdown shows how many duplications fall into each severity level.

Consolidation Recommendations¶

When the system identifies functions that are duplicated across multiple repositories, it suggests consolidating them into a shared library. The table shows:

Column Description
Function Name of the duplicated function
Repositories Comma-separated list of repositories containing the function
Est. Savings (LOC) Estimated lines of code saved by consolidating (shown in green)

Access via /dashboard/sca. This page provides a portfolio-wide view of software composition analysis.

Four KPI cards at the top:

Card Description

Vulnerabilities Total CVE count (red if > 0)
Critical CVEs Number of critical-severity CVEs (red if > 0)
Outdated Number of outdated packages across all projects

Vulnerability Overview¶

A bar chart breaks down vulnerabilities by severity:

  • Red — Critical
  • Orange — High
  • Yellow — Medium
  • Green — Low

If no vulnerabilities are detected, the chart area displays a “No vulnerabilities detected” message.

Most Vulnerable Packages¶

A table listing the packages with the highest number of associated CVEs:

Column Description
Package Package name
Version Currently installed version

License Risks¶

If license compatibility issues are detected, a table appears listing:

Column Description

Drill-Down Navigation¶

The dashboard supports a hierarchical drill-down flow:

Portfolio Overview → Project Detail → Section Tab → Individual Finding
  1. Portfolio → Project — click any project card on the Portfolio Overview to open its detail page.
  2. Project → Section — use the tab bar (Audit, Compliance, Release Gate, SCA/SBOM, Trends) to explore different aspects of the project.
  3. Red Zone → Project — click any red zone alert to jump directly to the affected project.

The browser’s back button works as expected. You can also use the sidebar navigation to jump directly to the Compliance Center, Cross-Repo Analysis, or SCA Center at any time.

Export¶

The dashboard supports exporting data in multiple formats for reporting, auditing, and integration with external systems.

Supported Formats¶

Format Content Type Description
JSON application/json Machine-readable structured data; suitable for CI/CD integration
Markdown text/markdown Human-readable report; suitable for review and documentation
GOST application/json JSON structured according to GOST R 56939 requirements; suitable for regulatory submissions
PDF application/pdf Formatted document; suitable for management reporting and audit evidence

API Examples¶

Export portfolio data via the REST API:

# Export portfolio as JSON
curl -X POST http://localhost:8000/api/v2/dashboard/export \
  -H "Content-Type: application/json" \
  -d '{"scope": "portfolio", "format": "json"}' \
  -o portfolio-export.json

# Export a single project as Markdown
curl -X POST http://localhost:8000/api/v2/dashboard/export \
  -H "Content-Type: application/json" \
  -d '{"scope": "project", "project_name": "my-project", "format": "markdown", "language": "en"}' \
  -o project-report.md

# Export compliance section in GOST format
curl -X POST http://localhost:8000/api/v2/dashboard/export \
  -H "Content-Type: application/json" \
  -d '{"scope": "portfolio", "format": "gost", "sections": ["compliance"]}' \
  -o compliance-gost.json

# Export as PDF
curl -X POST http://localhost:8000/api/v2/dashboard/export \
  -H "Content-Type: application/json" \
  -d '{"scope": "project", "project_name": "my-project", "format": "pdf", "language": "en"}' \
  -o project-report.pdf

The POST /api/v2/dashboard/export endpoint accepts:

Field Type Required Description
scope string Yes "portfolio" or "project"
project_name string If scope = project Name of the project to export
format string Yes "json", "markdown", "gost", or "pdf"
language string No "en" or "ru" (default: "ru")
sections string[] No Filter to specific sections (e.g., ["compliance"])

CLI Examples¶

# Portfolio overview as JSON
python -m src.cli dashboard export --scope portfolio --format json --output portfolio.json

# Single project as JSON
python -m src.cli dashboard export --scope project --project my-project --format json --output report.json

# Portfolio overview in table format
python -m src.cli dashboard overview --format table --language en

# Project health score
python -m src.cli dashboard health my-project --include-sections --format markdown

# View trends for the last 90 days
python -m src.cli dashboard trends my-project --period 90d --format table

# Red zone items (critical and high severity)
python -m src.cli dashboard red-zone --severity critical,high --format table

# Compare two projects
python -m src.cli dashboard compare project-a project-b --format table

Limitations¶

  • PDF export requires the optional weasyprint dependency. If not installed, the export endpoint returns an error for the pdf format.
  • Export file size is limited by the dashboard.export_max_pages configuration parameter.
  • Real-time data — export snapshots reflect the data at the time of export. If an audit is in progress, partial results may be included.
  • Large portfolios — exporting a portfolio with more than 50 projects may take several seconds. Use the sections filter to export only the data you need.

Notifications¶

The dashboard notification layer is a persistent service, not an in-memory prototype. Subscriptions, delivery audit, and deferred deliveries survive process restarts.

The main user-facing surface is the /dashboard/notifications page, which combines:

  • subscription CRUD
  • event catalog browsing
  • test-send
  • delivery audit
  • pending queue inspection
  • manual processing of due pending deliveries

Event Types¶

The event catalog is versioned and available through GET /api/v2/dashboard/event-catalog.

Current catalog examples include:

Event Trigger
risk_change Health or risk posture meaningfully regressed between snapshots
release_gate_fail Release gate ended in fail
report_completed Audit report job finished successfully
compliance_threshold Compliance score crossed the configured threshold
sca_critical Critical SCA exposure increased
suppression_expiring Release suppression is approaching expiry

Each delivery carries a correlation ID and, when available, a deep link back to the dashboard object.

Channels¶

Four delivery channels are supported:

  • telegram
  • slack
  • email
  • webhook

Channel adapters use typed dashboard config with environment fallback.

Config Key Purpose
notification_telegram_token / DASHBOARD_TELEGRAM_TOKEN Telegram bot token
notification_telegram_chat_id / DASHBOARD_TELEGRAM_CHAT_ID Telegram target chat
notification_slack_webhook_url / DASHBOARD_SLACK_WEBHOOK_URL Slack incoming webhook
notification_webhook_url / DASHBOARD_WEBHOOK_URL Generic HTTP webhook endpoint
notification_webhook_auth_header / DASHBOARD_WEBHOOK_AUTH_HEADER Optional webhook auth header
notification_smtp_* / DASHBOARD_SMTP_* SMTP settings for email delivery

Sensitive details can be redacted automatically for restricted channels. By default, only explicitly allowed channels receive full sensitive context.

Subscriptions API¶

Users manage subscriptions through /api/v2/dashboard/subscriptions.

Supported fields:

  • channel
  • events
  • scope
  • project_filter
  • saved_view_id
  • delivery_mode
  • schedule
  • quiet_hours
  • enabled
  • minimum_severity
  • include_sensitive_details

Examples:

# List subscriptions
curl http://localhost:8000/api/v2/dashboard/subscriptions \
  -H "Authorization: Bearer $TOKEN"

# Create a daily digest for one project
curl -X POST http://localhost:8000/api/v2/dashboard/subscriptions \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "channel": "email",
    "events": ["risk_change", "release_gate_fail", "report_completed"],
    "scope": "project",
    "project_filter": "my-project",
    "delivery_mode": "daily_digest",
    "enabled": true
  }'

# Update an existing subscription
curl -X PATCH http://localhost:8000/api/v2/dashboard/subscriptions/{id} \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"channel": "webhook", "events": ["release_gate_fail"], "scope": "portfolio"}'

# Send a test notification without saving
curl -X POST http://localhost:8000/api/v2/dashboard/subscriptions/test \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"channel": "slack", "events": ["release_gate_fail"], "sample_event_type": "release_gate_fail"}'

Operator APIs:

  • GET /api/v2/dashboard/deliveries
  • GET /api/v2/dashboard/deliveries/summary
  • GET /api/v2/dashboard/deliveries/pending
  • POST /api/v2/dashboard/deliveries/process-pending

Notification Configuration¶

Relevant dashboard config keys:

Parameter Description
notification_cooldown_seconds Deduplication window
notification_compliance_threshold Threshold for compliance-triggered events
notification_health_drop_threshold Threshold for health-regression events
notification_retry_attempts Retry count for critical delivery paths
notification_retry_backoff_seconds Retry backoff between attempts
notification_restrict_sensitive_details Global redaction switch

Policy behavior:

  • normal events can be deferred by quiet hours or digest mode
  • critical events bypass quiet hours and digest
  • due pending deliveries can be flushed by scheduler or manually

Snapshot Store & Trends¶

The snapshot layer now supports manual baselines, compare/export workflows, and release-gate evidence in addition to time-series trends.

How It Works¶

Each snapshot stores both metrics and provenance metadata:

  • scope and scope_ref
  • reason
  • initiator
  • trigger_source
  • analyzer_version
  • rule_version
  • source_ref
  • immutable
  • retention_class

Supported scopes:

  • project
  • group

Snapshots are created from:

  • background scheduler
  • manual API and CLI requests
  • release-gate pre/post automation

Scheduled Collection¶

When snapshot_enabled is set, the scheduler periodically collects project health and stores snapshots. The same scheduler also gives the notification service a chance to detect events and flush due pending deliveries.

Key config:

Parameter Default Description
snapshot_enabled false Enable the background scheduler
snapshot_interval_minutes 60 Collection interval
snapshot_retention_days 365 Cleanup threshold for non-protected snapshots
snapshot_db_path data/dashboard_snapshots.sqlite SQLite path
snapshot_list_limit 100 Maximum list API/CLI payload size
snapshot_release_pre_enabled true Create pre-release snapshot
snapshot_release_post_enabled true Create post-release snapshot
snapshot_release_immutable false Mark release snapshots immutable
snapshot_release_retention_class release Retention class for release snapshots

Trends API¶

Trend and snapshot APIs now serve different use cases:

  • GET /api/v2/dashboard/projects/{name}/trends for live trend views
  • GET /api/v2/dashboard/snapshots/{project}/trends for persisted trend history
  • POST /api/v2/dashboard/snapshots to create manual baselines
  • GET /api/v2/dashboard/snapshots to list stored baselines
  • POST /api/v2/dashboard/snapshots/compare to compare two baselines
  • POST /api/v2/dashboard/snapshots/{snapshot_id}/export to export one baseline or a compare report

CLI equivalents:

codegraph dashboard snapshot create --scope project --project my-project --reason "before upgrade"
codegraph dashboard snapshot list --scope project --project my-project
codegraph dashboard snapshot compare --from-snapshot <older> --to-snapshot <newer> --include-drilldown
codegraph dashboard snapshot export <snapshot_id> --baseline-snapshot <older> --format markdown

Retention & Granularity¶

The trend store still applies downsampling for long windows, but stored baselines are preserved as standalone evidence objects.

Period Granularity
≤ 30 days Daily
31–180 days Weekly
> 180 days Monthly

Notes:

  • immutable snapshots are excluded from ordinary cleanup
  • compare output can label dimensions as improved, regressed, or unchanged
  • optional drilldown previews expose source-level artifacts behind aggregate shifts

Operations¶

Release gate is snapshot-aware. POST /api/v1/release/check may create both pre_snapshot_id and post_snapshot_id, and the response can include snapshot_diff.

This makes it possible to:

  • capture the exact state before a release decision
  • export the before/after delta later
  • include snapshot evidence in release-driven notifications

FAQ¶

1. Why did my project’s health score drop?¶

The health score is a weighted composite of five components: audit (30%), compliance (25%), release gate (20%), SCA (15%), and quality (10%). A drop can be caused by any of these components decreasing. To investigate:

  1. Open the project detail page and check each tab for changes.
  2. Use the Trends tab to identify when the drop occurred and which metric changed.
  3. Common causes: new critical CVEs discovered in dependencies, compliance processes reverting to GAP status, a failed release gate check, or a decrease in test coverage.

See Dashboard Methodology for the exact formula.

2. What does GAP in process 5.11 mean?¶

A GAP for any GOST R 56939 process means the project does not meet the requirements for that process. Process 5.11 specifically covers testing and verification. A GAP in 5.11 typically indicates insufficient test coverage, missing test documentation, or incomplete verification procedures. Check the Compliance tab of the affected project and the Compliance Center heatmap for cross-project patterns.

3. How do I compare teams or projects?¶

Use the CLI compare command:

python -m src.cli dashboard compare team-a-project team-b-project --format table

Or use the Portfolio Overview page — filter by language or risk level to narrow down to the projects you want to compare. The KPI cards will update to reflect the filtered set.

For a detailed dimension-by-dimension comparison, the CLI --format radar option generates data suitable for radar chart visualization.

4. What does grade A/B/C/D/F mean?¶

Grades are derived from the composite health score:

Grade Score Range Meaning
A 85–100 Excellent — production-ready security posture
B 70–84 Good — minor issues, no blockers
C 55–69 Fair — several issues requiring attention
D 40–54 Poor — significant issues present
F 0–39 Critical — project must not be released

Grade thresholds are configurable in config.yaml under dashboard:.

5. What do risk levels mean?¶

Risk levels are an operational classification that combines the health score with specific condition overrides:

Risk Level Condition
Critical Health score < 40, OR any critical SCA vulnerabilities, OR compliance < 40%
High Health score < 55, OR release gate status = FAIL
Medium Health score < 70, OR release gate status = WARN
Low Health score >= 70 AND release gate = PASS

The highest matching condition determines the risk level. A project with a health score of 72 but a failed release gate is still classified as high risk.

6. How do I interpret the compliance heatmap?¶

The heatmap is a matrix of projects (rows) vs. GOST R 56939 processes (columns). Each cell is color-coded:

  • Green (FULL) — the project fully meets this process requirement
  • Yellow (PARTIAL) — partially met, improvements needed
  • Red (GAP) — not met, this is a compliance gap
  • Gray (N/A) — process does not apply to this project

Focus on red columns (widespread gaps) and red rows (projects needing the most compliance work).

7. How do I read the radar chart?¶

The radar chart has 12 axes (Q1 through Q12), each representing a quality dimension scored 0–10. The project’s scores form a polygon:

  • A large, round polygon = high, balanced quality
  • A small polygon = low quality overall
  • A polygon with sharp dips = specific weak dimensions

Compare the polygon shape against the outer boundary (score 10 on every axis) to see where improvement is needed most.

8. What does a release gate FAIL mean?¶

A FAIL status means one or more blocking checks in the release gate did not pass. The project should not be released until all blockers are resolved. Open the Release Gate tab to see the number of blockers and warnings, and the active profile. Common blockers include critical security findings, compliance gaps in mandatory processes, and failed SCA checks.

9. How often is dashboard data updated?¶

Dashboard data is refreshed each time an audit, compliance check, or SCA scan completes for a project. The timestamp shown in the Portfolio Overview header indicates when the data was last aggregated. For real-time updates, the dashboard uses a WebSocket connection at /api/v2/dashboard/ws that pushes incremental updates as they become available.

To trigger a manual refresh, re-run the relevant analysis:

python -m src.cli audit --db /path/to/project.duckdb
python -m src.cli compliance gost-56939
python -m src.cli release check --db /path/to/project.duckdb

10. How do I export data for auditors?¶

For regulatory auditors who need GOST-formatted reports:

  1. Navigate to the Compliance Center and click Export GOST, or
  2. Use the API:
curl -X POST http://localhost:8000/api/v2/dashboard/export \
  -H "Content-Type: application/json" \
  -d '{"scope": "portfolio", "format": "gost", "sections": ["compliance"], "language": "ru"}' \
  -o audit-report.json
  1. Or use the CLI:
python -m src.cli dashboard export --scope portfolio --format gost --language ru --output audit-report.json

For a comprehensive PDF report suitable for management review:

python -m src.cli dashboard export --scope project --project my-project --format pdf --language ru --output report.pdf

11. What is the difference between audit findings and SCA vulnerabilities?¶

  • Audit findings are issues found by static analysis of your source code (dead code, complexity, security patterns, etc.). They are detected by CodeGraph’s audit engine and organized by 12 quality dimensions.
  • SCA vulnerabilities are known CVEs in third-party dependencies (libraries, packages). They are detected by Software Composition Analysis and tracked by CVE identifiers.

Both contribute to the health score but through different components (audit at 30% weight, SCA at 15%).

12. Can I suppress a finding so it does not affect the score?¶

Yes. Use the release gate suppression mechanism:

python -m src.cli release suppress --finding-id FINDING-123 --reason "Accepted risk per JIRA-456" --ticket JIRA-456

Suppressed findings are excluded from the release gate evaluation but remain visible in the audit results for traceability.

13. How do I set up Telegram notifications?¶

  1. Create a Telegram bot via @BotFather and get the token.
  2. Add the bot to your target chat/group.
  3. Set environment variables: DASHBOARD_TELEGRAM_TOKEN and DASHBOARD_TELEGRAM_CHAT_ID.
  4. Enable the scheduler in config.yaml: yaml dashboard: snapshot_enabled: true
  5. Create a subscription via the API: bash curl -X POST http://localhost:8000/api/v2/dashboard/subscriptions \ -H "Authorization: Bearer $TOKEN" \ -H "Content-Type: application/json" \ -d '{"channel": "telegram", "events": ["risk_change", "release_gate_fail", "sca_critical"]}'

14. How do I view historical trends?¶

Use the snapshot trends endpoint:

curl http://localhost:8000/api/v2/dashboard/snapshots/my-project/trends?period=90d

This requires the snapshot scheduler to be enabled (snapshot_enabled: true). Without it, the endpoint falls back to live data from the regular trends service, which only has data from audit history.
