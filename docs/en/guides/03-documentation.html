How It Works¶

Intent Classification¶

The DocumentationIntentDetector classifies queries into one of 10 intents (+ fallback), sorted by priority. Each intent has EN and RU keywords with morphological matching.

Intent Priority Description
mvd_doc 3 Minimum Viable Documentation for project
module_overview 5 Module/subsystem overview
coverage_doc 7 Documentation coverage analysis
diagram_doc 8 Diagrams (call graph, component, dependency)
pipeline_doc 10 Processing pipeline documentation
business_logic_doc 12 Business logic extraction
type_doc 14 Type documentation and conversions
function_doc 20 Single function documentation
usage_example 30 Usage examples
api_reference 40 API reference

If no intent matches, the fallback general_documentation is used (confidence=0.5).

The detector also extracts: - target — function or module name from the query (via regex patterns and semantic mappings) - format — output format: markdown (default), html, rst, latex - diagram_type — for diagram_doc: callgraph, component, dependency, system_architecture, tech_stack, or deployment_view

Two-Phase Architecture¶

S03 uses a two-phase approach:

Phase 1: Handler-based (no LLM). The integrate_handlers() function tries 8 registered template-based handlers. For documentation diagrams, Phase 1 now starts by building a deterministic semantic graph from repository evidence. Handlers then produce structured reports and Mermaid views directly from CPG data plus repo artifacts through DocumentationReportFormatter. If a handler matches and finds enough evidence, the response is returned without calling the LLM.

Phase 2: LLM fallback. If no handler matched, the full pipeline runs: 4-phase CPG retrieval collects methods, CallGraphAnalyzer enriches with usage patterns, then LLM generates documentation with graph context.

Query -> DocumentationIntentDetector -> integrate_handlers()
  |                                          |
  |  Phase 1: Deterministic graph + handlers? Yes -> Structured report (no LLM)
  |                                 No  -> Phase 2: Full pipeline
  |
  Phase 2: CPG Retrieval (4 phases) -> CallGraphAnalyzer
           -> LLM with graph context -> Documentation

Deterministic Semantic Graph¶

For system-level documentation requests, S03 builds a typed documentation graph before rendering the output. This graph is deterministic and does not depend on LLM prompting.

The graph stores:

  • Entities such as project, subsystem, language, framework, database, platform, and deployment_target
  • Relations such as part_of, uses, and runs_on
  • Source attribution for every fact: source_kind, source_path, confidence, and extraction_method=deterministic

This gives S03 a stable intermediate model that can be reused by diagrams and future documentation outputs instead of generating each artifact from unrelated one-off queries.

Freshness Preflight¶

Before S03 enters either the deterministic handler path or the LLM fallback path, it now runs a mandatory CPG freshness preflight.

The preflight does three things:

  1. resolves the active db_path and repository source_path;
  2. checks whether the current CPG is fresh relative to repository HEAD;
  3. if the CPG is stale, runs gocpg update first and only then continues with documentation generation.

If refresh fails, S03 does not proceed with documentation handlers or LLM fallback. This is the same operational rule already used by the freshness-orchestrated audit flow: documentation should not be generated from a stale graph.

The freshness outcome is also stored in metadata.cpg_freshness, including whether refresh was required, whether it succeeded, and why the workflow was blocked when it could not continue.

Input Sources¶

Phase 1 documentation graph extraction combines three deterministic evidence sources:

  1. CPG facts: subsystems and project structure from the active CPG
  2. Repo manifests and config: pyproject.toml, requirements*.txt, package.json, go.mod, Dockerfile*, docker-compose*.yml, Kubernetes YAML, Helm, Terraform
  3. Repository docs: README.md and docs/**/*.md

Graph Coverage And Gaps¶

Phase 3 adds graph-based documentation coverage summaries on top of the same semantic graph. Coverage is evaluated as deterministic documentation evidence for three buckets:

  1. Subsystems/components: whether a discovered subsystem has any documentation facts beyond its bare CPG boundary
  2. APIs/interfaces: whether subsystems expose endpoints or communicate via explicit interface/protocol facts in docs
  3. Deployment/integration facts: whether subsystems have documented deployment, datastore, dependency, or integration relations

The gap flow is now remediation-aware:

  1. detect candidate gaps from deterministic graph evidence;
  2. classify which expectations are actually applicable;
  3. run deterministic remediation passes before final reporting;
  4. show only residual gaps as the final unresolved set.

Applicability gates are explicit:

  • api_interface_gap is only applicable when the subsystem has endpoint/router/boundary evidence;
  • deployment_integration_gap is only applicable when the subsystem has deployment target, runtime, datastore, or integration evidence;
  • otherwise the expectation is reported as Not Applicable, not as a residual defect.

Deterministic remediation passes currently cover:

  • subsystem evidence synthesis from CPG metadata and graph neighbors;
  • interface recovery from endpoints, protocols, and boundary evidence;
  • deployment recovery from manifests and runtime relations;
  • runtime backfill from manifests/config into generated documentation output.

This produces explicit residual-only gap lists such as:

  • subsystems with no deterministic documentation facts;
  • subsystems with no API/interface facts;
  • subsystems with no deployment/integration facts;
  • runtime technologies or deployment surfaces present in manifests but absent from docs.

Coverage output also separates:

  • Automatically Closed Gaps
  • Not Applicable Expectations
  • Residual Documentation Gaps
  • Warnings Requiring Manual Review
  • Automatic Recovery Summary

Consistency Checks¶

Phase 3 also runs deterministic consistency checks between docs claims and non-doc evidence. The checks are intentionally narrow and auditable:

  • docs technologies/deployment targets that are not corroborated by manifests/config;
  • docs dependency claims between subsystems that are not corroborated by CPG or manifest-derived relations;
  • docs datastore claims that are not corroborated by repo runtime/config evidence.

These checks do not replace S11. They only flag documentation mismatches between repository docs and deterministic repo evidence.

If a warning cannot be strictly confirmed or disproved from deterministic evidence, it stays in Warnings Requiring Manual Review. It must not be promoted to Automatically Closed Gaps.

Domain Extension Points¶

Domain plugins can extend S03 semantic extraction without changing core S03 code:

  • Additional entity patterns: get_documentation_entity_patterns() adds domain-specific deterministic entities such as buses, external systems, or protocols
  • Aliases: get_subsystem_aliases() and get_documentation_aliases() let docs terms map to canonical subsystem/component names
  • Relation inference hook: infer_documentation_relations(graph) can add deterministic domain-specific relations after the generic passes

This keeps domain-specific extraction logic inside src/domains/, while S03 stays generic.

Eight Documentation Handlers¶

The 8 handlers are registered in HandlerRegistry("documentation"):

Handler Priority Intent
MVDDocHandler 3 mvd_doc
CoverageDocHandler 7 coverage_doc
DiagramDocHandler 8 diagram_doc
FunctionDocHandler 10 function_doc
BusinessLogicDocHandler 12 business_logic_doc
TypeDocHandler 14 type_doc
PipelineDocHandler 15 pipeline_doc
ModuleOverviewHandler 20 module_overview

All handlers inherit from DocumentationHandler (extends BaseHandler), which provides incremental documentation session tracking — _get_doc_session(), _update_doc_session(), and _get_session_delta() allow tracking which functions/modules have been documented across multiple queries.

When S03 Stays Deterministic¶

S03 can answer several project-level documentation requests entirely in Phase 1 without LLM fallback when enough evidence is present:

  • system architecture reconstruction
  • tech stack layer overview
  • data flow reconstruction
  • dependency tree generation
  • deployment view generation
  • call graph, component, and dependency diagrams
  • function docs, module overviews, coverage reports, and MVD when the relevant handlers have enough CPG evidence

CPG Retrieval Pipeline¶

The LLM fallback phase uses a 4-phase CPG retrieval pipeline to find relevant methods:

Phase 1: Direct Function Lookup¶

extract_function_names_from_query() extracts function names using 8 regex patterns:

  1. Backtick quoted: `funcName`
  2. Function call syntax: funcName(
  3. “function X” / “method X” phrases
  4. “X function” reversed order
  5. “for X” / “of X” patterns
  6. CamelCase identifiers (e.g., ExecInitNode)
  7. snake_case identifiers (e.g., heap_insert)
  8. Domain-specific naming conventions from plugin

Found names are queried directly in nodes_method for exact matches.

Phase 2: Pattern-Based Search¶

If no direct results, _get_documentation_keywords() loads keyword-to-pattern mappings from the domain plugin and searches by matched patterns using search_methods_by_name_pattern().

Phase 3: Subsystem-Based Search¶

If still no results, subsystem keywords and aliases are loaded from the domain plugin. The query is matched against subsystem names using keyword_match_morphological(), then get_methods_by_subsystem() retrieves methods.

Phase 4: Keyword Fallback¶

As a last resort, _extract_significant_words() extracts meaningful words from the query (filtering stop words) and searches by each word individually.

CallGraphAnalyzer Integration¶

After methods are retrieved, CallGraphAnalyzer(cpg) from src/analysis/ enriches each method with usage pattern analysis:

  • find_all_callers(method_name, max_depth) — who uses this method
  • find_all_callees(method_name, max_depth) — what this method calls
  • analyze_impact(method_name) — importance score for documentation priority

The analyzer identifies: - Key methods — methods with high impact_score are prioritized for thorough documentation - Entry points — methods with no callers or matching entry point patterns from the domain plugin - Public API — methods with many callers are flagged as public API - Call examples — direct callers provide usage context for documentation

Documentation Types¶

Function Documentation¶

Generates API documentation for individual functions with signature, parameters, description, usage examples, and related functions (callers/callees from call graph).

Module Overview¶

Generates architecture documentation for modules/subsystems including component structure, key functions, data flow, and inter-module dependencies.

MVD (Minimum Viable Documentation)¶

Generates project-level Minimum Viable Documentation — a structured overview covering architecture, key modules, entry points, and API surface.

Coverage Report¶

Analyzes documentation coverage at two levels:

  • classic comment/function coverage from CPG statistics;
  • graph-based documentation coverage for subsystems, APIs/interfaces, and deployment/integration facts.

Phase 3 coverage output now includes explicit documentation gaps and deterministic consistency warnings when docs claims disagree with manifest/config/CPG evidence.

Diagrams¶

Generates Mermaid diagrams from CPG data: - Call graph — function call relationships - Component diagram — subsystem/module architecture - Dependency diagram — file/module dependency graph

The diagram_type is auto-detected from the query and now supports both the legacy CPG-only views and new semantic-graph views.

Architecture Views¶

The deterministic semantic graph powers three system-level architecture views in Phase 1:

  • System Architecture — high-level project + subsystems + external technologies/deployment targets
  • Tech Stack Layers — grouped technologies across frontend, backend, data, infrastructure, and tooling
  • Deployment View — deployment targets reconstructed from Docker, Compose, and Kubernetes artifacts

Phase 2 extends this with two more graph-powered views:

  • Data Flow — subsystem to endpoint/protocol/datastore communication edges
  • Dependency Tree — project-level dependency structure across subsystems, technologies, and deployment surfaces

These views are documentation artifacts. They describe structure and runtime shape, but they do not perform the architectural quality analysis that belongs to S11.

Pipeline Documentation¶

Documents data processing pipelines and execution flows — traces query processing from input to output through the call graph.

Business Logic Extraction¶

Extracts business rules, invariants, and validation logic from code — identifies conditional logic, assertions, and constraint checks.

Type Documentation¶

Documents type systems, type conversions, and cast operations — analyzes type flow through function signatures and return types.

Export Formats¶

Documentation can be exported to external platforms:

  • GitBook — GitBookExporter(output_dir) generates SUMMARY.md with chapter structure and individual markdown files
  • Docusaurus — DocusaurusExporter(output_dir) generates MDX files with frontmatter and sidebar configuration

The DocumentationReportFormatter provides 8 format methods matching each documentation type: format_function_documentation, format_module_overview, format_pipeline_documentation, format_coverage_report, format_diagram_documentation, format_type_documentation, format_mvd_document, format_business_logic_report.

Generated Package Structure¶

When S03 runs full package generation, the output directory is not just a dump of section files anymore. It is intended to be a navigable package with explicit entrypoints:

  • documentation_<lang>_<timestamp>.md — combined all-in-one document
  • INDEX.md — package entrypoint with section roles and suggested reading paths
  • package_manifest.json — machine-readable package metadata
  • section_manifests/*.json — machine-readable per-section manifests with selected items and next-step links
  • cpg_freshness.json — freshness evidence for the graph used during generation
  • sections/*.md — individual section documents

Recommended reading order depends on the use case:

  • repo orientation: mvd_doc -> diagram_doc -> module_overview
  • subsystem change planning: mvd_doc -> module_overview -> function_doc
  • documentation quality review: coverage_doc -> mvd_doc -> module_overview

Section files are intentionally role-specific:

  • mvd_doc is the landing page for repository understanding
  • diagram_doc is the visual architecture entrypoint
  • module_overview is the subsystem inventory
  • function_doc is a curated entrypoint set: a representative function sample, not a complete API reference
  • coverage_doc is a quality appendix, not a primary onboarding document

The machine-readable section_manifests/*.json files are intended for downstream tooling and indexing. They record:

  • section purpose and category;
  • suggested next documents;
  • selection criteria for representative outputs;
  • selected modules/functions/diagram metadata for the generated section.

When coverage_doc is included, the package now also contains package-level quality artifacts:

  • remediation_summary.json — machine-readable summary of deterministic remediation passes and counts before/after recovery
  • residual_gaps.json — machine-readable residual gap set for downstream tooling

When full generation is run with opt-in patch preparation, the package additionally includes:

  • doc_patch_plan.json
  • doc_patch_plan.md

These files are deterministic draft suggestions only. They do not modify repository docs automatically.

Project Detail Documentation Tab¶

The dashboard Project Detail page can expose the latest generated S03 package through a dedicated Documentation tab. The tab is intentionally read-only:

  • it reads the latest generated package from the configured documentation output directory;
  • it does not trigger package generation automatically when the page is opened;
  • it treats markdown as the canonical storage format and renders HTML only as a derived UI representation.

The tab entrypoint is INDEX.md when it exists. The same package manifest and section manifests are used to populate navigation, section roles, and suggested reading paths.

The tab is freshness-aware and distinguishes these package states: current, stale_cpg, missing, generation_failed, and unknown.

  • current — the package freshness metadata is present and the current project CPG is still coherent with that package;
  • stale_cpg — the package exists, but the project CPG has moved ahead and the package must be regenerated on the fresh graph;
  • missing — no complete generated package is available for the project;
  • generation_failed — a partial package exists, but required entry artifacts are missing;
  • unknown — package freshness could not be proven from the available metadata.

When the tab is not current, the UI should show a regeneration recommendation and the deterministic command that can be used to rebuild the package. Reader-facing documents remain separate from appendix-level quality artifacts:

  • INDEX.md, mvd_doc, diagram_doc, and other section markdown files are shown as reader docs;
  • coverage_doc, remediation_summary.json, and residual_gaps.json are exposed as quality appendix evidence.

Markdown is rendered deterministically to HTML in the UI. Mermaid fenced blocks may be rendered as diagrams, but the stored source of truth remains the original markdown file in the generated package.

CLI Usage¶

# Generate function documentation
python -m src.cli query "Generate documentation for heap_insert"

# Module overview
python -m src.cli query "Document the executor module architecture"

# Documentation coverage
python -m src.cli query "Show documentation coverage for the storage subsystem"

# Generate diagrams
python -m src.cli query "Generate call graph diagram for the parser module"

# Full documentation generation
python -m src.cli.generate_docs full --output ./docs/generated --language en
python -m src.cli.generate_docs full --output ./docs/generated --language en --prepare-doc-patches

# Generate specific section
python -m src.cli.generate_docs section mvd_doc --language en

# Export to GitBook/Docusaurus
python -m src.cli.export_docs --format gitbook --output ./gitbook-docs
python -m src.cli.export_docs --format docusaurus --output ./docusaurus-docs

Related Scenarios¶

  • Onboarding - Codebase exploration and understanding
  • Architecture - Deeper structural and dependency analysis
  • Feature Development - Finding integration points

S03 vs S01 vs S11: S03 generates documentation artifacts (API docs, module overviews, diagrams, coverage reports) from code and repo evidence. S01 (onboarding) helps developers explore and understand unfamiliar codebases interactively. S11 (architecture) focuses on structural analysis — dependency cycles, layer violations, coupling metrics, and architecture smells. All three use CPG data, but S03 uses it to reconstruct documentation, while S11 uses it to diagnose architecture quality problems.
