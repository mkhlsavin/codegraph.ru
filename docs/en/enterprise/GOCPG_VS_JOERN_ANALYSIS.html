Evaluate GoCPG and Joern for a customer workload

GoCPG and Joern both use Code Property Graphs, but they are different products with different data, query, integration, and operating boundaries.

EnterpriseUpdated: 2026-08-24

GoCPG and Joern both use Code Property Graphs, but they are different products with different data, query, integration, and operating boundaries. This guide helps a customer design a fair evaluation. It intentionally publishes no speed, accuracy, memory, node-count, or language-coverage winner without a separate immutable benchmark manifest and raw evidence.

Snapshot and authority

Source review date: 24 August 2026.

GoCPG claims in this article come from the current CodeGraph checkout, especially gocpg/pkg/cpg/schema, gocpg/pkg/storage/duckdb, gocpg/api/proto/gocpg/v1, and gocpg/docs/api/schema.md.

Joern claims are limited to its official documentation and official repository. Joern releases frequently; pin the exact release and artifact digest instead of relying on the date of this article.

Decision map

Decision map
Decision question GoCPG / CodeGraph evaluation Joern evaluation
Primary user workflow CodeGraph project import, services, CLI, MCP, REST, and governed evidence. Joern CLI, interactive shell, scripts, server, and query database.
Storage ownership GoCPG is the writer for project CPG DuckDB files; CodeGraph consumes gRPC and service contracts. Joern documents its own graph storage and project model.
Query model GoCPG protobuf/gRPC operations and CodeGraph service abstractions. Scala-based CPG query language and extensible passes/plugins.
Security-analysis fit Evaluate CodeGraph task workflows, evidence, provider boundaries, and deployment controls. Evaluate Joern queries, taint/dataflow behavior, overlays, and research workflow.
Integration fit Measure the complete customer path, not GoCPG parsing alone. Measure the complete Joern import, query, export, or server path selected for the pilot.

Neither column is a universal winner. Select by the customer’s languages, queries, automation, deployment, authorization, evidence, and operator skills.

Architecture boundaries

In CodeGraph, GoCPG builds and owns the CPG storage boundary. Application components should use the GoCPG gRPC services or CodeGraph project-scoped interfaces; direct database writes are not a supported user integration.

Joern’s official material describes a platform for source, bytecode, and binary analysis that creates CPGs and exposes a Scala-based domain-specific query language. Its extension model includes query packages, CPG passes, and plugins. Validate only the frontends and overlays present in the pinned release.

These architectures affect operator tooling, failure isolation, upgrade strategy, schema access, and the skills needed to create custom analysis.

Language and semantic coverage

Do not compare language counts alone. For every language in the customer corpus, define:

  • exact file types, framework and generated-code policy;
  • parser success and failure criteria;
  • symbols, calls, control flow, data flow, types, and source locations required by the use case;
  • cross-file and interprocedural behavior expected by the query;
  • unsupported or partially supported constructs;
  • how incomplete parsing and unresolved calls are reported.

A parser accepting a file records syntax coverage. Inspect the semantic facts required by the pilot through the generated graph and the pilot queries.

Query and evidence comparison

Define equivalent questions before writing tool-specific queries. Examples include entry-point inventory, call reachability, source-to-sink paths, dependency impact, or structural pattern matches. For each result, retain source locations and enough graph or query evidence for an independent reviewer.

Do not compare raw node counts as a quality score: schemas, normalization, implicit nodes, overlays, and deduplication can differ. Compare whether the required facts are correct and usable.

Reproducible benchmark protocol

Every quantitative result needs an immutable benchmark manifest containing:

  • GoCPG/CodeGraph commit, Joern release, artifact digests, and configuration;
  • corpus repository commit, language subset, include/exclude rules, and expected facts;
  • hardware, operating system, runtime limits, cache state, and concurrent load;
  • exact import, query, export, and cleanup commands;
  • cold and warm run policy, repetitions, timeout, failures, and outlier treatment;
  • wall time, CPU, peak memory, storage size, and result completeness where relevant;
  • raw logs and machine-readable results with digests;
  • normalization rules, reviewer, deviations, and known limitations.

Run each tool in a clean, tool-appropriate workspace. Do not reuse one tool’s cache or generated graph as input evidence for the other.

Interpret results

Report failed imports, partial graphs, timed-out queries, unsupported constructs, and manual setup as results rather than excluding them silently. Separate:

  • parser or import throughput;
  • query latency after import;
  • end-to-end time to a usable answer;
  • correctness and completeness against labeled facts;
  • operator effort and customization cost;
  • deployment, security, support, and lifecycle fit.

A result from one repository and machine is evidence for that measured scenario only.

Selection checklist

Choose only after both candidates have been assessed against the same customer acceptance set:

  • required languages and semantic facts;
  • representative security and architecture questions;
  • automation and integration interfaces;
  • identity, secrets, network, storage, and audit requirements;
  • incremental update and repository-change behavior;
  • failure recovery, observability, upgrade, and rollback;
  • licensing, support, staffing, and operational ownership;
  • reproducible evidence and disclosed gaps.

If the benchmark manifest is missing, treat quantitative comparison as unverified and base the decision only on demonstrated architecture and workflow fit.
