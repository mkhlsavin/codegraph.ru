RBAC и авторизация

Роли, разрешения, политики доступа и интеграция с корпоративной идентификацией для рабочих пространств CodeGraph.

Корпоративная эксплуатацияОбновлено: 2026-06-14

Этот справочник помогает администраторам и разработчикам проверить роли пользователей, разрешения API и доступ машинных учётных записей. Роль пользователя, область проекта и разрешения машинной учётной записи проверяются отдельно: одна таблица ролей не описывает все условия допуска запроса. Здесь scope — строка разрешения, которую проверяет контракт доступа; её машинное значение сохраняется без перевода.

Область действия и источник истины

Документ описывает реализацию, которая сейчас находится в src/.

Модель авторизации

CodeGraph использует три связанных слоя авторизации:

Модель авторизации
Слой Что контролирует Основная реализация
Роли пользователей Разрешения пользователей для зависимостей маршрутов и логики приложения Permission, Role, ROLE_PERMISSIONS, has_permission()
Разрешения машинных учётных записей Доступ API-ключей и сервисных учётных записей к маршрутам API/MCP MachinePrincipal, API_ROUTE_SCOPE_MAP, MCP_ROUTE_SCOPE_MAP, authorize_machine_request()
Область группы и проекта Членство в группах и доступ к выбранным проектам в установках с несколькими группами GroupRole, ProjectScopeMode, UserGroupAccess, UserProjectAccess, репозитории проектов

Аутентификация определяет пользователя или машинного субъекта доступа. Авторизация проверяет разрешения роли, строки scope, разрешённые интерфейсы, ограничения группы и проекта. Middleware выполняет дополнительные проверки безопасности.

Пользовательские роли и разрешения

Роли

Роли пользователя определены в двух enum для разных границ:

Роли
Enum Источник Назначение
Role src/api/auth/tokens/permissions.py Проверки разрешений в зависимостях аутентификации
UserRole src/api/database/models_base.py Роль пользователя, сохранённая в базе приложения

Оба enum сейчас используют одинаковые значения:

Роли, таблица 2
Роль Значение Смысл
VIEWER viewer Доступ к продукту для чтения
ANALYST analyst Права viewer, выполнение запросов и сценариев, запись сессий, создание API-ключей и базовая работа с задачами цифровых сотрудников
REVIEWER reviewer Права analyst, интеграции ревью и операции цифровых сотрудников с повышенным риском
ADMIN admin Администратор платформы

src/api/dependencies.py::require_role() трактует роли как иерархию: viewer < analyst < reviewer < admin.

Проверка разрешений

Permission сейчас содержит 31 значение, включая admin:all.

Особенности реализации:

  • ROLE_PERMISSIONS[Role.ADMIN] хранит только {Permission.ADMIN_ALL}.
  • get_role_permissions(Role.ADMIN) возвращает этот набор без разворачивания во все разрешения.
  • has_permission(Role.ADMIN, ...) возвращает True для любого запрошенного разрешения.
  • Явные scope также дают доступ, если строка совпадает с Permission.value.
  • Scope admin:all проходит все проверки разрешений в has_permission() и обходит проверку машинного scope.

Проверка ролевого разрешения

Из корня исходного репозитория CodeGraph с установленными Python-зависимостями сохраните пример в check_rbac.py и выполните python check_rbac.py:

from src.api.auth.permissions import Permission, Role, has_permission

assert has_permission(Role.VIEWER, Permission.SCENARIOS_READ)
assert not has_permission(Role.VIEWER, Permission.SCENARIOS_EXECUTE)
assert has_permission(Role.ANALYST, Permission.SCENARIOS_EXECUTE)
assert not has_permission(Role.ANALYST, Permission.REVIEW_EXECUTE)
assert has_permission(Role.REVIEWER, Permission.REVIEW_EXECUTE)
print("Role permission checks passed")

Ожидаемый результат — Role permission checks passed и код завершения 0. Ошибка AssertionError означает расхождение ожидаемого разрешения с реализацией. Пример проверяет только ролевую функцию, без токенов, HTTP и ограничений проекта.

Вспомогательные функции разрешений

Для проверки роли и scope используйте src.api.auth.permissions:

from src.api.auth.permissions import (
    Permission,
    Role,
    get_default_scopes_for_api_key,
    get_role_permissions,
    has_all_permissions,
    has_any_permission,
    has_permission,
    validate_scopes,
)

Ключевое поведение:

  • get_default_scopes_for_api_key() возвращает scenarios:read, scenarios:execute, query:execute, sessions:read, sessions:write, history:read.
  • validate_scopes() фильтрует неизвестные строки по перечислению Permission.
  • has_permission() сначала учитывает разрешения роли, затем явные строки scope.

Последовательность получения контекста:

  1. Повторно использовать request.state.machine_principal, если ScopeEnforcementMiddleware уже проверил API-ключ.
  2. Проверить X-YC-IAM-Token, если IAM включен.
  3. Проверить JWT Bearer-токен и отклонить отозванные идентификаторы JWT.
  4. Проверить X-API-Key как машинные учётные данные.
  5. Вернуть контекст без аутентификации, если действительных учётных данных нет.

В обработчиках маршрутов используйте эти зависимости:

from src.api.auth.middleware import (
    get_auth_context,
    get_current_user,
    get_optional_user,
    require_admin,
    require_analyst,
    require_any_permission,
    require_auth,
    require_auth_or_localhost,
    require_permission,
    require_reviewer,
    require_role,
)

require_auth_or_localhost() разрешает запросы локального плагина только при security.local_dev_unauthenticated_surfaces_enabled=true и обращении через loopback. Запросы, изменяющие состояние, должны содержать X-Actor-Agent-Id и X-Task-Id; общие идентификаторы агентов, например codex или codex-headless, отклоняются.

src/api/dependencies.py также содержит зависимости, которые читают базу данных и возвращают ORM-объекты User. Маршруты аутентификации используют их для управления учётными записями и API-ключами.

Методы аутентификации

Вход по имени пользователя и паролю

Маршруты доступны под /api/v1/auth:

Вход по имени пользователя и паролю
Маршрут Назначение
POST /register Создать локального пользователя и вернуть токены
POST /login Альтернативный маршрут входа для выдачи токенов
POST /token Основной маршрут выдачи токена по имени пользователя и паролю

Значения по умолчанию:

  • Срок действия access-токена: настройка access_token_expire_minutes в JWT-конфигурации, если expires_delta не передан. Резервное значение — 30 минут.
  • Срок действия refresh-токена: 7 дней.
  • Настройки подписи берутся из src/api/config.py (API_JWT_ALGORITHM, определение секрета JWT).

Отзыв:

  • blacklist_token() сохраняет отпечаток SHA-256 от JTI в памяти и в таблице token_blacklist.
  • is_token_blacklisted() сначала проверяет память, затем базу данных.
  • load_blacklist_cache() загружает неистёкшие записи об отзыве при запуске.
  • _blacklist_sync_task() периодически обновляет кеш в памяти.

API-ключи пользователей

API-ключи пользователей создаются через /api/v1/me/api-keys и передаются как X-API-Key.

Формат:

rag_<8 hex chars>_<48 hex chars>

Детали реализации:

  • generate_api_key() возвращает (full_key, prefix, key_hash).
  • Префикс начинается с rag_.
  • Секрет генерируется через secrets.token_hex(24).
  • Сохранённый хеш: SHA-256.
  • verify_api_key() использует secrets.compare_digest().
  • ApiKey.group_id может ограничить ключ одной группой.
  • API-ключи пользователей аутентифицируются как MachinePrincipal(subject_type="user", auth_method="api_key").
  • API-ключи пользователей по умолчанию разрешают интерфейсы api и mcp.
  • ApiKeyInfo — модель ответа без секрета.
  • ApiKeyWithSecret расширяет ApiKeyInfo и возвращается только при создании ключа.

Создание, чтение и отзыв API-ключей:

API-ключи пользователей
Маршрут Назначение
POST /api/v1/me/api-keys Создать ключ текущего пользователя
GET /api/v1/me/api-keys Список ключей текущего пользователя без секретов
DELETE /api/v1/me/api-keys/{key_id} Отозвать собственный ключ

Запрос создания по умолчанию использует ["scenarios:read", "query:execute"]; вспомогательная функция нижнего уровня get_default_scopes_for_api_key() возвращает более широкий исторический набор. Для запроса к API используйте значения по умолчанию обработчика маршрута.

Сервисные учётные записи

Сервисные учётные записи используют тот же заголовок X-API-Key, но другой префикс ключа:

svc_<8 hex chars>_<48 hex chars>

Сервисные учётные записи хранятся в service_accounts, их учётные данные — в service_account_credentials.

Средства контроля:

  • Управление сервисными учётными записями только для администратора.
  • Шаблоны политики: ci, portal, bot, agent.
  • Явные scopes и allowed_interfaces.
  • Необязательные ограничения group_id или project_id.
  • Сроки действия учётной записи и учётных данных.
  • Выпуск новых учётных данных без немедленного отзыва старых.
  • Ограничение количества активных ключей через security.service_account_max_active_credentials.
  • Отзыв ключей и отключение учётной записи.
  • Заголовок контракта машинного доступа: X-CodeGraph-Machine-Contract, сейчас 2026-03-v1.
  • Необязательная привязка mTLS с завершением TLS на прокси для настроенных интерфейсов.
  • Единые события аудита машинного доступа через AuditAction.MACHINE_ACCESS.

LDAP/Active Directory

Реализация LDAP находится в src/api/auth/providers/ldap_auth.py; подключение маршрутов находится в auth_external_routes.py.

Маршруты:

LDAP/Active Directory
Маршрут Назначение
POST /api/v1/auth/ldap Проверить пользователя в LDAP/AD и выдать JWT
GET /api/v1/auth/ldap/status Вернуть доступность LDAP и состояние соединения

LDAPAuthenticator.map_groups_to_role() читает LDAPConfig.role_mapping и нормализует DN/CN-алиасы групп. При нескольких совпадениях выбирается первая роль в порядке admin, reviewer, analyst, viewer. Если совпадений нет, возвращается analyst. Это значение по умолчанию имеет больше разрешений, чем viewer; проверьте сопоставление групп до подключения LDAP.

Yandex Cloud IAM

Проверка IAM находится в src/api/auth/providers/iam.py и инициализируется из настроек API, когда IAM включен.

Заголовок запроса:

X-YC-IAM-Token: <token>

Когда токен действителен, get_auth_context() возвращает:

  • role=Role.ANALYST
  • scopes=["scenarios:read", "query:execute", "review:execute"]
  • auth_method="iam"

Результаты проверки кешируются на настроенный срок действия кеша IAM-токенов.

Проверка разрешений машинных учётных записей

ScopeEnforcementMiddleware добавляется в src/api/main.py, когда security.api_key_scope_enforcement=true. Он проверяет запросы с X-API-Key до вызова обработчика маршрута.

Процесс:

  1. Проверить ключ пользователя или сервисной учётной записи.
  2. Сохранить MachinePrincipal в request.state.machine_principal.
  3. Определить запрошенную область проекта из X-Project-Id.
  4. Проверить необязательный заголовок контракта машинного доступа.
  5. Проверить необязательную привязку mTLS для сервисной учётной записи.
  6. Выполнить authorize_machine_request().
  7. Записать событие аудита машинного доступа.
  8. Вернуть 403 insufficient_scope при отказе в доступе.

Явная проверка scope в обработчике:

Ниже — фрагмент существующего приложения FastAPI, а не самостоятельный скрипт. Он предполагает импорт Depends из fastapi и созданный объект router типа APIRouter. Подключите обработчик к приложению и проверьте разрешённый и запрещённый запросы с настроенной аутентификацией; один импорт функции не проверяет доступ к маршруту.

from src.api.auth.tokens.scope_enforcement import require_scope

@router.get("/example")
async def example(auth=Depends(require_scope("query:execute"))):
    ...

require_scope() проверяет строки AuthContext.scopes; admin:all обходит эту проверку.

Маршруты администратора для управления доступом:

Маршрут Назначение

Ограничения:

  • Администратор платформы не может отключить собственную учётную запись.
  • Нельзя отключить последнего активного администратора платформы или понизить его роль.
  • Нельзя удалить последнего администратора группы или понизить его роль, если в группе нет другого администратора.
  • Область selected должна включать хотя бы один проект. Все выбранные проекты должны принадлежать назначенной группе.
  • Область all не может включать явные идентификаторы проектов.

Определение проекта и операции, зависящие от группы, должны использовать ProjectContext и разрешённую область проекта, а не путь базы данных от пользователя.

Middleware проверки путей

PathValidationMiddleware проверяет поля db_path и source_path в JSON-телах запросов POST, PUT и PATCH.

Правила:

  • Пустые строки и байты NUL отклоняются.
  • Относительные пути отклоняются, если path_validation_deny_relative=true.
  • Компоненты пути .. отклоняются.
  • Пути приводятся к фактическому расположению через os.path.realpath().
  • Полученный путь должен находиться внутри разрешённого базового каталога.

Разрешённые каталоги определяются по:

  • security.path_validation_allowed_base_dirs
  • родительским каталогам db_path зарегистрированных проектов
  • каталогам source_path зарегистрированных проектов

Поля конфигурации определены в SecurityConfig:

Middleware проверки путей
Поле По умолчанию
path_validation_enabled true
path_validation_deny_symlinks true
path_validation_deny_relative true
path_validation_allowed_base_dirs ["data/projects/"]

Аутентификация webhook

Проверка webhook находится в src/api/auth/machine/webhook_auth.py. Основная функция проверки — verify_webhook_signature().

Поддерживаемые платформы:

Аутентификация webhook
Платформа Заголовок подписи или токена Заголовок времени
sourcecraft X-SourceCraft-Signature X-SourceCraft-Timestamp
gitverse X-GitVerse-Signature; резервные варианты включают X-Gitea-Signature, X-Gogs-Signature, X-Hub-Signature-256, X-Hub-Signature X-GitVerse-Timestamp
github X-Hub-Signature-256 X-Hub-Timestamp
gitlab X-Gitlab-Token отсутствует

sourcecraft, gitverse и github проверяют подпись HMAC. gitlab сравнивает токен за постоянное время. Проверка возраста использует security.webhook_max_age_seconds, только если запрос содержит непустой заголовок времени поддерживаемой платформы. Отсутствующий заголовок не отклоняется этой проверкой. Она не ведёт список уже принятых событий и сама по себе не предотвращает повторную отправку в допустимом окне. GitLab не имеет такой проверки времени.

Операционные рекомендации

Для администраторов:

  1. Используйте admin только для администрирования платформы.
  2. Для повседневной сегрегации предпочитайте роли группы GroupRole и доступ к выбранным проектам.
  3. Используйте сервисные учётные записи для CI, ботов, порталов, MCP-клиентов и длительного машинного доступа.
  4. Берите шаблоны политики как основу и добавляйте только необходимые scope вызывающей стороны.
  5. Выпускайте новые ключи сервисной учётной записи до отзыва старых.
  6. Оставляйте загрузку кеша отозванных JWT включённой при запуске приложения.
  7. Держите проверку путей и scope API-ключей включёнными в общих средах.

Для разработчиков:

  1. Используйте require_permission() или require_role() для проверки доступа пользователей к маршрутам.
  2. Используйте require_scope() только когда контракт требует проверки строк scope.
  3. Добавляйте новые маршруты машинного доступа в API_ROUTE_SCOPE_MAP или MCP_ROUTE_SCOPE_MAP.
  4. Сохраняйте согласованность REST/MCP через общие сервисы, без дублирования логики авторизации.
  5. Никогда не авторизуйте операции, зависящие от группы, по переданному пользователем db_path.
  6. Для изменяющих состояние маршрутов локального плагина требуйте именованного исполнителя и подтверждение задачи.
  7. Не записывайте в журналы Bearer-токены, API-ключи, секреты сервисных учётных записей и webhook или исходные запросы к модели.
