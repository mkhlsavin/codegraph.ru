Оценка GoCPG и Joern для задач заказчика

GoCPG и Joern используют Code Property Graph, но являются разными продуктами с разными границами данных, запросов, интеграции и эксплуатации.

Корпоративная версияОбновлено: 2026-08-24

GoCPG и Joern используют Code Property Graph, но являются разными продуктами с разными границами данных, запросов, интеграции и эксплуатации. Руководство помогает спроектировать честную оценку. Сравнение скорости, точности, памяти, числа узлов и языков проводится по отдельному immutable benchmark manifest и raw evidence.

Срез и источники

Дата проверки источников: 24 августа 2026 года.

Сведения о GoCPG получены из текущего checkout CodeGraph, прежде всего из gocpg/pkg/cpg/schema, gocpg/pkg/storage/duckdb, gocpg/api/proto/gocpg/v1 и gocpg/docs/api/schema.md.

Сведения о Joern ограничены официальной документацией и официальным репозиторием. Joern выпускается часто, поэтому для проверки фиксируйте конкретный release и artifact digest, а не дату этой статьи.

Карта решения

Карта решения
Вопрос Оценка GoCPG / CodeGraph Оценка Joern
Основной пользовательский процесс CodeGraph project import, services, CLI, MCP, REST и governed evidence. Joern CLI, interactive shell, scripts, server и query database.
Владение хранилищем GoCPG записывает project CPG DuckDB; CodeGraph использует gRPC и service contracts. Joern документирует собственное graph storage и project model.
Модель запросов Protobuf/gRPC GoCPG и service abstractions CodeGraph. Scala-based CPG query language и расширяемые passes/plugins.
Security-analysis fit Проверяйте task workflows, evidence, provider boundaries и deployment controls CodeGraph. Проверяйте Joern queries, taint/dataflow, overlays и исследовательский процесс.
Integration fit Измеряйте полный customer path, включая parsing GoCPG. Измеряйте полный выбранный путь import, query, export или server Joern.

Универсального победителя нет. Выбор определяется языками, запросами, автоматизацией, развёртыванием, authorization, evidence и навыками операторов заказчика.

Архитектурные границы

В CodeGraph GoCPG строит CPG и владеет границей хранения. Компоненты приложения используют gRPC services GoCPG или project-scoped интерфейсы CodeGraph; прямые записи в БД относятся к внутренней диагностике.

Официальные материалы Joern описывают платформу анализа source, bytecode и binary, которая создаёт CPG и предоставляет Scala-based domain-specific query language. Расширение включает query packages, CPG passes и plugins. Проверяйте только frontends и overlays зафиксированного release.

Эти архитектуры влияют на operator tooling, failure isolation, upgrade strategy, schema access и навыки, нужные для custom analysis.

Языки и семантическое покрытие

Не сравнивайте только количество языков. Для каждого языка корпуса заказчика определите:

  • точные file types, framework и generated-code policy;
  • критерии успеха и отказа parser;
  • необходимые use case symbols, calls, control flow, data flow, types и source locations;
  • ожидаемое cross-file и interprocedural behavior;
  • unsupported или partially supported constructs;
  • представление incomplete parsing и unresolved calls.

Наличие семантических фактов, нужных пилоту, проверяется отдельными запросами и контрольными примерами после parser.

Сравнение запросов и evidence

До реализации tool-specific query задайте эквивалентные вопросы: inventory entry points, call reachability, source-to-sink paths, dependency impact или structural pattern matches. Для каждого результата сохраняйте source locations и graph/query evidence для независимого ревью.

Не используйте raw node count как оценку качества: schema, normalization, implicit nodes, overlays и deduplication различаются. Сравнивайте корректность и применимость требуемых фактов.

Воспроизводимый benchmark protocol

Для любого численного результата нужен immutable benchmark manifest:

  • commit GoCPG/CodeGraph, release Joern, artifact digests и конфигурация;
  • commit корпуса, языковой subset, include/exclude rules и expected facts;
  • hardware, ОС, runtime limits, cache state и concurrent load;
  • точные import, query, export и cleanup commands;
  • cold/warm policy, repetitions, timeout, failures и outlier treatment;
  • wall time, CPU, peak memory, storage size и result completeness по задаче;
  • raw logs и machine-readable results с digest;
  • normalization rules, reviewer, deviations и known limitations.

Запускайте каждый инструмент в чистом подходящем ему workspace. Не используйте cache или generated graph одного инструмента как входное доказательство другого.

Интерпретация результатов

Failed imports, partial graphs, timed-out queries, unsupported constructs и ручную настройку включайте в результаты, а не исключайте молча. Разделяйте:

  • parser или import throughput;
  • query latency после import;
  • end-to-end время до применимого ответа;
  • correctness и completeness по размеченным фактам;
  • operator effort и customization cost;
  • deployment, security, support и lifecycle fit.

Результат одного репозитория и компьютера относится только к измеренному сценарию.

Checklist выбора

Принимайте решение после оценки обоих кандидатов по одному acceptance set заказчика:

  • требуемые языки и семантические факты;
  • репрезентативные security и architecture questions;
  • automation и integration interfaces;
  • identity, secrets, network, storage и audit requirements;
  • incremental update и repository-change behavior;
  • failure recovery, observability, upgrade и rollback;
  • licensing, support, staffing и operational ownership;
  • reproducible evidence и disclosed gaps.

Если benchmark manifest отсутствует, считайте численное сравнение непроверенным и опирайтесь только на продемонстрированный architecture и workflow fit.
