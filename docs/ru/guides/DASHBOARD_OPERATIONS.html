Руководство по эксплуатации Dashboard

Эксплуатационное руководство для Dashboard V2, persistent notifications, comparable snapshots и machine-driven automation.

Развёртывание¶

API-процесс¶

uvicorn src.api.main:app --host 0.0.0.0 --port 8000

Dashboard surfaces:

  • /dashboard для frontend
  • /api/v2/dashboard/* для REST
  • /api/v2/dashboard/ws для realtime updates

Минимальная dashboard-конфигурация¶

dashboard:
  snapshot_enabled: true
  snapshot_interval_minutes: 60
  snapshot_retention_days: 365
  snapshot_db_path: data/dashboard_snapshots.sqlite
  notification_cooldown_seconds: 3600
  notification_delivery_audit_db_path: data/dashboard_subscriptions.sqlite
  notification_pending_db_path: data/dashboard_subscriptions.sqlite

Секреты каналов¶

Типовые notification settings:

dashboard:
  notification_telegram_token: ${DASHBOARD_TELEGRAM_TOKEN:-}
  notification_telegram_chat_id: ${DASHBOARD_TELEGRAM_CHAT_ID:-}
  notification_slack_webhook_url: ${DASHBOARD_SLACK_WEBHOOK_URL:-}
  notification_webhook_url: ${DASHBOARD_WEBHOOK_URL:-}
  notification_webhook_auth_header: ${DASHBOARD_WEBHOOK_AUTH_HEADER:-}
  notification_smtp_host: ${DASHBOARD_SMTP_HOST:-}
  notification_smtp_port: ${DASHBOARD_SMTP_PORT:-587}
  notification_smtp_user: ${DASHBOARD_SMTP_USER:-}
  notification_smtp_password: ${DASHBOARD_SMTP_PASSWORD:-}
  notification_email_from: ${DASHBOARD_EMAIL_FROM:-}

Хранилища данных¶

Dashboard V2 теперь использует несколько persistent SQLite stores:

Хранилище Путь по умолчанию Назначение
Snapshot store data/dashboard_snapshots.sqlite История snapshot’ов и источник compare/export
Subscription store data/dashboard_subscriptions.sqlite Persistent notification subscriptions
Delivery audit store по умолчанию data/dashboard_subscriptions.sqlite Журнал попыток доставки и итоговых статусов
Pending delivery store по умолчанию data/dashboard_subscriptions.sqlite Очередь digest и quiet-hours

При необходимости можно развести пути для delivery и pending store через:

  • dashboard.notification_delivery_audit_db_path
  • dashboard.notification_pending_db_path

Мониторинг здоровья¶

Проверка API¶

curl http://localhost:8000/health

Метрики Prometheus¶

Dashboard health metrics экспортируются через стандартный endpoint метрик.

Ключевые gauges:

Метрика Метки Смысл
codegraph_project_health_score project, group, language Композитная оценка здоровья проекта
codegraph_project_audit_score project Audit score
codegraph_project_compliance_score project Compliance score
codegraph_project_release_status project Статус release gate в виде numeric gauge
codegraph_project_sca_health project SCA health
codegraph_project_sca_vulnerabilities project, severity Количество уязвимостей
codegraph_portfolio_avg_health group Средняя оценка по портфелю
codegraph_red_zone_items_count project, category Число red-zone items

Связанные артефакты:

  • grafana/dashboard_ciso.json
  • monitoring/rules/dashboard_alerts.yml

Ожидаемые логи scheduler¶

Типовые сообщения:

INFO Snapshot scheduler started (interval=60 min)
INFO Snapshot collection complete: 15/15 projects
WARN Snapshot collection failed for broken-proj: ConnectionError
WARN Pending notification delivery flush failed: ...
INFO Snapshot scheduler stopped

Операции со snapshot’ами¶

Ручные baseline’ы¶

API:

  • POST /api/v2/dashboard/snapshots
  • GET /api/v2/dashboard/snapshots
  • POST /api/v2/dashboard/snapshots/compare
  • POST /api/v2/dashboard/snapshots/{snapshot_id}/export
  • GET /api/v2/dashboard/portfolio/compare-periods

CLI:

codegraph dashboard snapshot create --scope project --project my-service --reason "before patch"
codegraph dashboard snapshot list --scope project --project my-service
codegraph dashboard snapshot compare --from-snapshot <older> --to-snapshot <newer> --include-drilldown
codegraph dashboard snapshot export <snapshot_id> --baseline-snapshot <older> --format markdown

Snapshot’ы release gate¶

Release checks могут автоматически создавать pre/post snapshots.

Ключевые настройки:

  • snapshot_release_pre_enabled
  • snapshot_release_post_enabled
  • snapshot_release_immutable
  • snapshot_release_retention_class

Поля ответа release gate:

  • pre_snapshot_id
  • post_snapshot_id
  • snapshot_diff

Portfolio Runtime Operations¶

Portfolio runtime использует один и тот же filtered scope для overview, history, saved view, alerts и export.

Основные portfolio endpoint’ы:

  • GET /api/v2/dashboard/portfolio
  • GET /api/v2/dashboard/projects
  • GET /api/v2/dashboard/red-zone
  • GET /api/v2/dashboard/compliance/heatmap
  • GET /api/v2/dashboard/sca/overview
  • GET /api/v2/dashboard/metrics/mapping
  • GET /api/v2/dashboard/portfolio/compare-periods
  • POST /api/v2/dashboard/export

Saved view и portfolio alerts:

  • GET /api/v2/dashboard/saved-views
  • POST /api/v2/dashboard/saved-views
  • GET /api/v2/dashboard/saved-views/{view_id}
  • DELETE /api/v2/dashboard/saved-views/{view_id}
  • POST /api/v2/dashboard/subscriptions

Операторские ожидания:

  • saved view должен сохранять те же filters и compare set, что видны на portfolio screen
  • portfolio alerts могут использовать либо scope=portfolio, либо scope=saved_view
  • export payload должен нести те же filters, compare set и identity saved view, что и Web

Пользовательские endpoint’ы¶

  • PATCH /api/v2/dashboard/subscriptions/{id}
  • DELETE /api/v2/dashboard/subscriptions/{id}

  • POST /api/v2/dashboard/subscriptions/bootstrap
  • GET /api/v2/dashboard/event-catalog

Operator endpoint’ы¶

  • GET /api/v2/dashboard/deliveries
  • GET /api/v2/dashboard/deliveries/summary
  • GET /api/v2/dashboard/deliveries/pending
  • POST /api/v2/dashboard/deliveries/process-pending

Bootstrap и первые live data¶

/dashboard/notifications для нового пользователя может быть честно пустым. Productized path к первым live data такой:

  1. настройте хотя бы один delivery channel или примите failed/pending local audit records
  2. создайте project-scoped subscription или вызовите bootstrap напрямую
  3. выполните POST /api/v2/dashboard/subscriptions/bootstrap
  4. убедитесь, что GET /api/v2/dashboard/deliveries/summary возвращает ненулевой live_total или pending

CLI-эквиваленты:

codegraph dashboard notifications summary --user-id acceptance-r4 --format json
codegraph dashboard notifications bootstrap --user-id acceptance-r4 --project codegraph --format json

Политики доставки¶

Реализованное поведение:

  • cooldown-based дедупликация
  • defer по quiet hours
  • daily digest queueing
  • critical bypass для deferred policies
  • bounded retry/backoff для critical delivery paths
  • channel-aware redaction для sensitive details

Рутинные проверки¶

Используйте summary и pending API для контроля:

  • числа failed deliveries
  • глубины pending queue
  • концентрации ошибок по каналу
  • соотношения test и real delivery

Правило truthful runtime:

  • test deliveries не равны evidence живого pipeline
  • sales-deck screenshots из frontend/scripts/capture_sales_deck_ui.mjs используют только demo fixtures

Machine access для автоматизации¶

Автоматизация dashboard должна использовать service accounts, а не персональные токены.

Admin API:

  • GET /api/v1/auth/service-accounts/action-catalog
  • POST /api/v1/auth/service-accounts
  • GET /api/v1/auth/service-accounts
  • GET /api/v1/auth/service-accounts/{id}
  • POST /api/v1/auth/service-accounts/{id}/rotate
  • POST /api/v1/auth/service-accounts/{id}/credentials/{credential_id}/revoke
  • POST /api/v1/auth/service-accounts/{id}/deactivate

CLI:

codegraph auth service-account create --owner admin --name ci-bot --template ci --interface api
codegraph auth service-account list --format json
codegraph auth service-account inspect --id <service-account-id>
codegraph auth service-account rotate --id <service-account-id>
codegraph auth service-account revoke --id <credential-id>
codegraph auth service-account deactivate --id <service-account-id>

Machine clients должны передавать:

  • X-API-Key: <service-account-credential>
  • X-CodeGraph-Machine-Contract: <supported-version> в machine-only flow

Эксплуатационные замечания:

  • quotas применяются на уровень service account
  • revoked credentials должны отказывать сразу
  • API и MCP используют одну и ту же модель проверки scope/interface

Резервное копирование и восстановление¶

Backup¶

Остановите API-процесс или используйте SQLite backup:

sqlite3 data/dashboard_snapshots.sqlite ".backup data/dashboard_snapshots.bak"
sqlite3 data/dashboard_subscriptions.sqlite ".backup data/dashboard_subscriptions.bak"

Restore¶

  1. Остановите API-процесс.
  2. Восстановите нужные .sqlite файлы.
  3. Запустите API-процесс.
  4. Проверьте: - /health - dashboard routes - GET /api/v2/dashboard/snapshots - GET /api/v2/dashboard/deliveries/summary

Замечания по reset¶

Не сбрасывайте эти stores без явной причины в production.

  • reset snapshot store удаляет историческое compare evidence
  • reset subscription store удаляет пользовательские подписки
  • reset shared notification DB может также удалить delivery audit и pending queue state

Замечания по масштабированию¶

  • Для фоновой записи предпочтителен один активный snapshot scheduler instance.
  • Несколько API-инстансов допустимы для read traffic и delivery API.
  • Если инстансов несколько, только один должен владеть scheduled snapshot collection и pending-delivery flush.

Типовые инциденты¶

Pending queue продолжает расти¶

Симптомы:

  • GET /deliveries/pending возвращает много overdue items
  • GET /deliveries/summary показывает рост pending

Проверки:

  1. Убедитесь, что scheduler работает.
  2. Вызовите POST /api/v2/dashboard/deliveries/process-pending.
  3. Посмотрите failing channels через GET /deliveries?status=failed.

Падает webhook delivery¶

Симптомы:

  • повторяющиеся failed deliveries с channel=webhook
  • last_error указывает на HTTP auth или сеть

Проверки:

  1. Проверьте notification_webhook_url.
  2. Проверьте notification_webhook_auth_header.
  3. Прогоните POST /subscriptions/test.

Release gate не возвращает snapshot evidence¶

Проверки:

  1. Проверьте snapshot_release_pre_enabled / snapshot_release_post_enabled.
  2. Проверьте API-логи вокруг release_gate.
  3. Убедитесь в наличии прав записи в snapshot DB.

Machine client начал падать после rotation¶

Проверки:

  1. Убедитесь, что новый credential дошёл до вызывающей стороны.
  2. Убедитесь, что старый credential не был отозван раньше rollout.
  3. Проверьте совместимость по X-CodeGraph-Machine-Contract.

Проверочный чек-лист¶

  • Страницы dashboard открываются под /dashboard
  • /api/v2/dashboard/portfolio возвращает данные
  • snapshots можно создавать, читать, сравнивать и экспортировать
  • subscriptions/test успешно работает хотя бы для одного канала
  • subscriptions/bootstrap создаёт или переиспользует реальную project-scoped subscription
  • deliveries/summary и deliveries/pending возвращают осмысленные значения
  • release-gate response включает snapshot evidence при включённой функции
  • путь service-account create/rotate/revoke работает для automation users
