Руководство пользователя: панель мониторинга CISO/CTO

Руководство пользователя: панель мониторинга CISO/CTO¶

Подробное руководство по панели мониторинга CodeGraph — единому интерфейсу контроля безопасности и качества кода, предназначенному для руководителей информационной безопасности (CISO), технических директоров (CTO) и руководителей разработки. Панель мониторинга обеспечивает обзор состояния безопасности, соответствия стандартам и качества кода всех проектов портфеля в реальном времени.

Начало работы¶

Доступ к панели мониторинга¶

Панель мониторинга — это веб-приложение, обслуживаемое сервером API CodeGraph. После запуска сервера откройте браузер и перейдите по адресу:

http://<хост>:<порт>/dashboard

Например, с настройками по умолчанию:

http://localhost:8000/dashboard

По умолчанию загружается страница «Обзор портфеля». Дополнительная настройка не требуется — панель мониторинга использует тот же API CodeGraph, что и интерфейс командной строки и MCP-инструменты.

Структура адресов¶

Все страницы панели мониторинга расположены в базовом пути /dashboard:

Страница Адрес Описание
Обзор портфеля /dashboard Главная страница, все проекты
Детали проекта /dashboard/projects/:name Детальный анализ одного проекта
Уведомления /dashboard/notifications Подписки, каталог событий и журнал доставок
Центр соответствия /dashboard/compliance Межпроектная тепловая карта соответствия
Межрепозиторный анализ /dashboard/cross-repo Зависимости и дублирование кода
Центр анализа состава ПО /dashboard/sca Обзор уязвимостей и зависимостей

Параметр :name в адресе страницы проекта — это имя проекта (кодируется для URL, если содержит специальные символы).

Аутентификация¶

Панель мониторинга использует ту же аутентификацию, что и API CodeGraph. Если настроен JWT или OAuth2, потребуется выполнить вход. При прямом обращении к API также поддерживается аутентификация по ключу через заголовок X-API-Key.

Для автоматизации, CI и интеграционных клиентов предпочтительнее service-account credentials, а не персональные API keys. Machine access документирован в enterprise guide по RBAC и использует одинаковую проверку scope для API и MCP.

Обзор портфеля¶

Обзор портфеля — стартовая страница панели мониторинга. Она представляет высокоуровневую сводку по всем зарегистрированным проектам и выделяет области, требующие немедленного внимания.

Карточки ключевых показателей¶

В верхней части страницы отображаются шесть карточек ключевых показателей:

Показатель Описание Шкала
Средняя оценка здоровья Средняя оценка состояния по всем проектам 0–100
Средняя оценка аудита Средний балл качества аудита 0–10
Соответствие Средний процент соответствия ГОСТ Р 56939 0–100%
Всего замечаний Сумма всех замечаний аудита по проектам Количество (красный, если есть критические)
Уязвимости Общее число уязвимостей анализа состава ПО Количество (красный, если > 5)
Дублирование Число межрепозиторных дублей кода Количество

Когда значение показателя превышает пороговое значение, число становится красным для привлечения внимания.

Карточки проектов¶

Под карточками показателей каждый проект представлен в виде интерактивной карточки. На карточке отображаются:

  • Имя проекта — нажмите для перехода на страницу детализации
  • Язык — язык программирования (метка в верхнем регистре)
  • Уровень риска — цветная точка: зелёная (низкий), жёлтая (средний), оранжевая (высокий), красная (критический)
  • Индикатор оценки — буквенная оценка (от A до F) в правом верхнем углу
  • Полоса оценки здоровья — горизонтальный индикатор прогресса с цветовым кодированием:
  • Зелёный (85+), синий (70–84), жёлтый (55–69), оранжевый (40–54), красный (ниже 40)
  • Оценка аудита и процент соответствия — компактные числа внизу карточки
  • Стрелка тенденции — улучшение, стабильно или ухудшение
  • Индикатор критических замечаний — появляется только при наличии критических замечаний

Фильтры¶

Два фильтра расположены между карточками показателей и сеткой проектов:

  1. Фильтр по языку — выберите язык программирования для отображения только проектов на этом языке. Выпадающий список формируется динамически из загруженных проектов.
  2. Фильтр по уровню риска — выберите минимальный уровень риска (критический, высокий, средний, низкий) для сужения результатов.

Фильтры применяются мгновенно. Сброс фильтра (выбор «Все языки» или «Все риски») возвращает отображение всех проектов.

Диаграмма распределения рисков¶

В правой боковой панели расположена кольцевая диаграмма, показывающая распределение проектов по уровням риска:

  • Зелёный — низкий риск
  • Жёлтый — средний риск
  • Оранжевый — высокий риск
  • Красный — критический риск

Диаграмма обновляется при изменении фильтров.

Готовность к выпуску¶

Под кольцевой диаграммой расположена панель «Готовность к выпуску», отображающая количество проектов с каждым статусом контроля выпуска:

Статус Цвет Значение
pass Зелёный Все проверки контроля выпуска пройдены; выпуск разрешён
warn Оранжевый Некоторые проверки выдали предупреждения; требуется проверка перед выпуском
fail Красный Одна или более блокирующих проверок не пройдены; выпуск запрещён

Красная зона¶

Панель «Красная зона» в нижней части боковой панели содержит список наиболее критичных проблем по всем проектам. Каждое предупреждение содержит:

  • Индикатор серьёзности — критический или высокий
  • Имя проекта — какой проект затронут
  • Сообщение — краткое описание проблемы

Нажмите на элемент красной зоны для перехода на страницу соответствующего проекта. Счётчик в заголовке панели показывает общее количество элементов красной зоны.

Детальная страница проекта¶

Нажмите на карточку любого проекта в обзоре портфеля, чтобы открыть страницу детализации. Формат адреса:

/dashboard/projects/<имя-проекта>

Сводная панель показателей¶

В заголовке страницы отображаются имя проекта, индикатор оценки, точка риска, язык, домен и хеш последнего проаудитированного коммита. Стрелка тенденции в правом верхнем углу показывает, улучшается, стабилен или ухудшается проект.

Под заголовком расположены шесть компактных карточек с ключевыми метриками:

Метрика Описание
Оценка здоровья Составная оценка из 100
Оценка аудита Качество аудита из 10
Соответствие Процент соответствия ГОСТ Р 56939
Контроль выпуска Индикатор статуса (PASS / WARN / FAIL)
Замечания Общее число замечаний аудита (красный, если есть критические)
Покрытие тестами Процент покрытия модульными тестами

Вкладка «Аудит»¶

Вкладка по умолчанию. Содержит четыре панели:

  1. Лепестковая диаграмма 12 измерений аудита — диаграмма, отображающая оценки проекта по 12 измерениям качества. Подробнее см. Лепестковая диаграмма 12 измерений.

  2. Оценки по разделам — вертикальный список всех 12 измерений с горизонтальными полосами оценок (шкала 0–10). Каждая строка содержит номер измерения (Q1–Q12), название и заполненную полосу.

  3. Замечания по серьёзности — сетка 2x2 с количеством замечаний каждого уровня серьёзности (критический, высокий, средний, низкий), каждый с цветным индикатором.

  4. Метрики качества — таблица структурных метрик: - Общее число методов - Мёртвые методы (количество и процент) - Средняя цикломатическая сложность - Максимальная цикломатическая сложность - Покрытие документацией - Циклы зависимостей (число компонент сильной связности)

Вкладка «Соответствие»¶

Две панели расположены рядом:

  1. ГОСТ Р 56939 — полоса оценки и сводка статусов процессов в формате 2x2: - Полное (зелёный) — требования полностью выполнены - Частичное (жёлтый) — требования выполнены частично - Пробел (красный) — требования не выполнены - Н/П (серый) — не применимо

При наличии критических пробелов они перечислены ниже в виде красных меток с идентификаторами процессов (например, 5.7, 5.11).

  1. ГОСТ Р 57580.3 — таблица, отображающая: - Уровень зрелости (из 4) - Реализованные возможности (из 25) - Оценка риска

Вкладка «Контроль выпуска»¶

Одна панель со статусом контроля выпуска, цветным индикатором (PASS/WARN/FAIL) и таблицей метрик:

Поле Описание
Профиль Активный профиль контроля выпуска (gost-56939, standard или minimal)
Блокирующие проблемы Количество блокирующих проблем (красный, если > 0)
Предупреждения Количество неблокирующих предупреждений
Последняя проверка Время последней проверки контроля выпуска

Вкладка «Анализ состава ПО»¶

Две панели:

  1. Зависимости — таблица: - Общее число зависимостей - Прямые зависимости - Устаревшие пакеты - Лицензионные риски (красный, если > 0) - Оценка здоровья анализа состава ПО

  2. Уязвимости — сетка 2x2 с количеством уязвимостей по серьёзности (критический, высокий, средний, низкий).

Вкладка «Тенденции»¶

Вкладка «Тенденции» показывает изменение метрик проекта во времени.

Выбор периода — пять кнопок для выбора временного окна: 7д, 30д, 90д, 180д, 1г.

Индикаторы изменений — четыре компактных индикатора, отображающих изменения оценки здоровья, аудита, соответствия и количества замечаний за выбранный период. Положительные изменения отмечены зелёным, отрицательные — красным. Для индикатора «Замечания» логика инвертирована: уменьшение замечаний отображается как положительное (зелёное) изменение.

График тенденций — линейный график с отображением оценки здоровья, аудита, соответствия и замечаний во времени в рамках выбранного периода.

Лепестковая диаграмма 12 измерений¶

Лепестковая (паутинная) диаграмма имеет 12 осей, по одной на каждое измерение качества. Каждая ось имеет диапазон от 0 до 10. Оценка проекта по каждому измерению отмечается точкой, точки соединяются в многоугольник. Чем больше многоугольник, тем здоровее проект.

Как читать диаграмму:

  1. Оцените общую форму — сбалансированный многоугольник (примерно круглый) указывает на равномерное качество по всем измерениям.
  2. Найдите впадины — любая ось, где многоугольник прогибается внутрь, представляет слабое измерение.
  3. Сравните с максимальной границей — внешний край соответствует оценке 10 по каждому измерению.

Справочник измерений качества¶

№ Измерение Что оценивает
Q1 Архитектура Структура модулей, слоистость, разделение ответственности
Q2 Сложность Цикломатическая сложность, глубина вложенности, длина функций
Q3 Зависимости Число внешних зависимостей, связанность, глубина импорта
Q4 Мёртвый код Недостижимые функции, неиспользуемые методы, доля мёртвого кода
Q5 Дублирование Обнаружение клонов, скопированный код, структурное сходство
Q6 Документация Покрытие документацией, качество комментариев, документация публичного API
Q7 Безопасность Число уязвимостей, результаты анализа помеченных данных, покрытие CWE
Q8 Обработка ошибок Паттерны обработки исключений, распространение ошибок, проверка на null
Q9 Производительность Алгоритмическая сложность, паттерны использования ресурсов
Q10 Тестирование Покрытие тестами, соотношение тестов к коду, плотность утверждений
Q11 Сопровождаемость Читаемость, соглашения об именовании, индикаторы технического долга
Q12 Стиль кода Единообразие форматирования, нарушения линтера, соответствие стилю

Центр соответствия¶

Доступ по адресу /dashboard/compliance. Эта страница предоставляет межпроектный обзор соответствия ГОСТ Р 56939.

В заголовке указаны название стандарта, количество проанализированных проектов и число оцениваемых процессов. Кнопка Экспорт ГОСТ загружает данные о соответствии в формате ГОСТ.

Три карточки ключевых показателей расположены в верхней части:

Показатель Описание
Всего пробелов Число пробелов по всем проектам и процессам (красный, если > 0)
Процессы с пробелами Сколько процессов имеют хотя бы один проект с пробелом (оранжевый, если > 0, показано как X / всего)
Проанализировано проектов Число проектов, включённых в анализ

Чтение тепловой карты¶

Матрица соответствия — это тепловая карта, где:

  • Строки представляют проекты
  • Столбцы представляют процессы ГОСТ Р 56939 (например, 5.1, 5.2, …, 5.14)
  • Ячейки окрашены в зависимости от статуса соответствия:
Цвет Статус Значение
Зелёный ПОЛНОЕ Требования процесса полностью выполнены
Жёлтый ЧАСТИЧНОЕ Требования процесса выполнены частично; необходимы действия
Красный ПРОБЕЛ Требования процесса не выполнены; критический пробел
Серый Н/П Процесс не применим к данному проекту

Как интерпретировать тепловую карту:

  1. Просмотрите столбцы — столбец, который преимущественно красный или жёлтый, указывает на процесс, проблемный для множества проектов. Это организационная проблема, а не проблема конкретного проекта.
  2. Просмотрите строки — строка с множеством красных или жёлтых ячеек указывает на проект, требующий значительной работы по обеспечению соответствия.
  3. Ищите закономерности — если одни и те же процессы являются пробелами в разных проектах, рассмотрите создание общих инструментов или шаблонов для обеспечения соответствия.

Таблица анализа пробелов¶

Под тепловой картой расположена таблица анализа пробелов, в которой перечислены все процессы, имеющие хотя бы один проект со статусом «ПРОБЕЛ». Таблица отсортирована по количеству затронутых проектов (больше всего пробелов — в начале).

Столбец Описание
Процесс Идентификатор процесса (например, 5.11)
Наименование Читаемое наименование процесса
Проекты с пробелом Число проектов, имеющих пробел по данному процессу (показано как X / всего)

Число становится красным, когда более 2 проектов имеют пробел по одному процессу, и оранжевым, когда более 1.

Навигация с детализацией¶

Панель мониторинга поддерживает иерархическую навигацию с детализацией:

Обзор портфеля -> Детали проекта -> Вкладка раздела -> Конкретное замечание
  1. Портфель -> Проект — нажмите на карточку проекта в обзоре портфеля для открытия страницы детализации.
  2. Проект -> Раздел — используйте панель вкладок (Аудит, Соответствие, Контроль выпуска, Анализ состава ПО, Тенденции) для изучения различных аспектов проекта.
  3. Красная зона -> Проект — нажмите на предупреждение красной зоны для перехода к затронутому проекту.

Кнопка «Назад» в браузере работает стандартно. Боковая навигация позволяет в любой момент перейти к центру соответствия, межрепозиторному анализу или центру анализа состава ПО.

Экспорт¶

Панель мониторинга поддерживает экспорт данных в нескольких форматах для подготовки отчётов, аудита и интеграции с внешними системами.

Поддерживаемые форматы¶

Формат Тип содержимого Описание
JSON application/json Машиночитаемые структурированные данные; подходит для интеграции с CI/CD
Markdown text/markdown Человекочитаемый отчёт; подходит для проверки и документации
ГОСТ application/json JSON, структурированный в соответствии с требованиями ГОСТ Р 56939; подходит для подачи регуляторной отчётности
PDF application/pdf Оформленный документ; подходит для отчётности руководству и аудиторских свидетельств

Примеры использования API¶

Экспорт данных портфеля через REST API:

# Экспорт портфеля в формате JSON
curl -X POST http://localhost:8000/api/v2/dashboard/export \
  -H "Content-Type: application/json" \
  -d '{"scope": "portfolio", "format": "json"}' \
  -o portfolio-export.json

# Экспорт одного проекта в формате Markdown
curl -X POST http://localhost:8000/api/v2/dashboard/export \
  -H "Content-Type: application/json" \
  -d '{"scope": "project", "project_name": "my-project", "format": "markdown", "language": "ru"}' \
  -o project-report.md

# Экспорт раздела соответствия в формате ГОСТ
curl -X POST http://localhost:8000/api/v2/dashboard/export \
  -H "Content-Type: application/json" \
  -d '{"scope": "portfolio", "format": "gost", "sections": ["compliance"]}' \
  -o compliance-gost.json

# Экспорт в формате PDF
curl -X POST http://localhost:8000/api/v2/dashboard/export \
  -H "Content-Type: application/json" \
  -d '{"scope": "project", "project_name": "my-project", "format": "pdf", "language": "ru"}' \
  -o project-report.pdf

Конечная точка POST /api/v2/dashboard/export принимает:

Поле Тип Обязательное Описание
scope string Да "portfolio" или "project"
project_name string Если scope = project Имя экспортируемого проекта
format string Да "json", "markdown", "gost" или "pdf"
language string Нет "en" или "ru" (по умолчанию: "ru")
sections string[] Нет Фильтр по конкретным разделам (например, ["compliance"])

Примеры использования CLI¶

# Обзор портфеля в формате JSON
python -m src.cli dashboard export --scope portfolio --format json --output portfolio.json

# Один проект в формате JSON
python -m src.cli dashboard export --scope project --project my-project --format json --output report.json

# Обзор портфеля в табличном формате
python -m src.cli dashboard overview --format table --language ru

# Оценка здоровья проекта
python -m src.cli dashboard health my-project --include-sections --format markdown

# Просмотр тенденций за последние 90 дней
python -m src.cli dashboard trends my-project --period 90d --format table

# Элементы красной зоны (критическая и высокая серьёзность)
python -m src.cli dashboard red-zone --severity critical,high --format table

# Сравнение двух проектов
python -m src.cli dashboard compare project-a project-b --format table

Ограничения¶

  • Экспорт в PDF требует дополнительной зависимости weasyprint. Если она не установлена, конечная точка экспорта вернёт ошибку для формата pdf.
  • Размер файла экспорта ограничен параметром конфигурации dashboard.export_max_pages.
  • Актуальность данных — экспортированные снимки отражают данные на момент экспорта. Если аудит выполняется в данный момент, могут быть включены промежуточные результаты.
  • Крупные портфели — экспорт портфеля с более чем 50 проектами может занять несколько секунд. Используйте фильтр sections для экспорта только нужных данных.

Уведомления¶

Слой уведомлений dashboard теперь является persistent service, а не in-memory prototype. Подписки, delivery audit и deferred deliveries переживают перезапуск процесса.

Основной пользовательский surface — страница /dashboard/notifications, где доступны:

  • управление подписками
  • просмотр versioned event catalog
  • test-send
  • журнал доставок
  • просмотр pending queue
  • ручной flush due pending deliveries

Типы событий¶

Каталог событий versioned и доступен через GET /api/v2/dashboard/event-catalog.

Текущие примеры событий:

Событие Триггер
risk_change заметная деградация health/risk между snapshot’ами
release_gate_fail release gate завершился со статусом fail
report_completed audit report job завершён успешно
compliance_threshold compliance score пересёк настроенный порог
sca_critical увеличился critical SCA exposure
suppression_expiring suppression скоро истекает

Каждая доставка получает correlation ID и, если возможно, ссылку обратно на объект в dashboard.

Хранилище снимков и тенденции¶

Слой snapshot’ов теперь поддерживает ручные baseline’ы, compare/export workflow и release-gate evidence, а не только time-series trends.

Принцип работы¶

Каждый snapshot хранит как метрики, так и provenance-метаданные:

  • scope и scope_ref
  • reason
  • initiator
  • trigger_source
  • analyzer_version
  • rule_version
  • source_ref
  • immutable
  • retention_class

Поддерживаемые scope:

  • project
  • group

Источники создания snapshot’ов:

  • фоновый scheduler
  • ручные вызовы API и CLI
  • pre/post automation в release gate

Плановый сбор данных¶

Если включён snapshot_enabled, scheduler периодически собирает project health и сохраняет snapshots. Тот же scheduler даёт notification service шанс обнаружить события и отправить due pending deliveries.

Ключевые параметры:

Параметр По умолчанию Описание
snapshot_enabled false Включение фонового scheduler
snapshot_interval_minutes 60 Интервал сбора
snapshot_retention_days 365 Порог cleanup для неподдерживаемых snapshots
snapshot_db_path data/dashboard_snapshots.sqlite Путь к SQLite
snapshot_list_limit 100 Максимальный размер list API/CLI
snapshot_release_pre_enabled true Создавать pre-release snapshot
snapshot_release_post_enabled true Создавать post-release snapshot
snapshot_release_immutable false Помечать release snapshots как immutable
snapshot_release_retention_class release Retention class для release snapshots

API тенденций¶

Теперь trend и snapshot API решают разные задачи:

  • GET /api/v2/dashboard/projects/{name}/trends для live trend view
  • GET /api/v2/dashboard/snapshots/{project}/trends для persisted trend history
  • POST /api/v2/dashboard/snapshots для ручного baseline
  • GET /api/v2/dashboard/snapshots для списка baseline’ов
  • POST /api/v2/dashboard/snapshots/compare для сравнения двух baseline’ов
  • POST /api/v2/dashboard/snapshots/{snapshot_id}/export для экспорта snapshot’а или compare report

CLI-эквиваленты:

codegraph dashboard snapshot create --scope project --project my-project --reason "before upgrade"
codegraph dashboard snapshot list --scope project --project my-project
codegraph dashboard snapshot compare --from-snapshot <older> --to-snapshot <newer> --include-drilldown
codegraph dashboard snapshot export <snapshot_id> --baseline-snapshot <older> --format markdown

Хранение и гранулярность¶

Trend store по-прежнему применяет downsampling для длинных периодов, но сохранённые baseline’ы живут как самостоятельные evidence-объекты.

Период Гранулярность
≤ 30 дней Ежедневно
31–180 дней Еженедельно
> 180 дней Ежемесячно

Замечания:

  • snapshots с immutable исключаются из обычного cleanup
  • compare может маркировать измерения как improved, regressed, unchanged
  • optional drilldown previews раскрывают source-level artifacts за агрегированными изменениями

Эксплуатация¶

Release gate теперь snapshot-aware. POST /api/v1/release/check может создавать и pre_snapshot_id, и post_snapshot_id, а ответ способен содержать snapshot_diff.

Это даёт возможность:

  • фиксировать точное состояние до решения о релизе
  • позже экспортировать delta до/после
  • включать snapshot evidence в release-driven notifications

Часто задаваемые вопросы¶

1. Почему упала оценка здоровья моего проекта?¶

Оценка здоровья — это взвешенная составная метрика из пяти компонентов: аудит (30%), соответствие (25%), контроль выпуска (20%), анализ состава ПО (15%) и качество (10%). Снижение может быть вызвано уменьшением любого из этих компонентов. Для расследования:

  1. Откройте страницу детализации проекта и проверьте каждую вкладку на наличие изменений.
  2. Используйте вкладку «Тенденции» для определения момента падения и метрики, которая изменилась.
  3. Распространённые причины: обнаружены новые критические CVE в зависимостях, статус процессов соответствия изменился на «ПРОБЕЛ», не пройдена проверка контроля выпуска или снизилось покрытие тестами.

Подробные формулы расчёта см. в Методология панели мониторинга.

2. Что означает «ПРОБЕЛ» в процессе 5.11?¶

Статус «ПРОБЕЛ» для любого процесса ГОСТ Р 56939 означает, что проект не соответствует требованиям данного процесса. Процесс 5.11 конкретно охватывает тестирование и верификацию. Пробел в процессе 5.11 обычно указывает на недостаточное покрытие тестами, отсутствие документации по тестированию или неполные процедуры верификации. Проверьте вкладку «Соответствие» затронутого проекта и тепловую карту центра соответствия для выявления межпроектных закономерностей.

3. Как сравнить команды или проекты?¶

Используйте команду сравнения в интерфейсе командной строки:

python -m src.cli dashboard compare project-team-a project-team-b --format table

Или используйте страницу обзора портфеля — отфильтруйте по языку или уровню риска для сужения набора проектов, которые хотите сравнить. Карточки ключевых показателей обновятся для отображения отфильтрованного набора.

Для детального сравнения по измерениям используйте параметр --format radar, который генерирует данные для визуализации в виде лепестковой диаграммы.

4. Что означают оценки A/B/C/D/F?¶

Буквенные оценки определяются на основе составной оценки здоровья:

Оценка Диапазон баллов Значение
A 85–100 Отлично — готовность к выпуску в промышленную среду
B 70–84 Хорошо — незначительные замечания, блокирующих проблем нет
C 55–69 Удовлетворительно — ряд замечаний, требующих внимания
D 40–54 Плохо — присутствуют значительные проблемы
F 0–39 Критично — проект не должен быть выпущен

Пороговые значения оценок настраиваются в config.yaml в разделе dashboard:.

5. Что означают уровни риска?¶

Уровни риска — это эксплуатационная классификация, объединяющая оценку здоровья с особыми условиями переопределения:

Уровень риска Условие
Критический Оценка здоровья < 40, ИЛИ наличие критических уязвимостей анализа состава ПО, ИЛИ соответствие < 40%
Высокий Оценка здоровья < 55, ИЛИ статус контроля выпуска = FAIL
Средний Оценка здоровья < 70, ИЛИ статус контроля выпуска = WARN
Низкий Оценка здоровья >= 70 И контроль выпуска = PASS

Уровень риска определяется наивысшим совпадающим условием. Проект с оценкой здоровья 72, но с непройденным контролем выпуска, всё равно классифицируется как проект высокого риска.

6. Как интерпретировать тепловую карту соответствия?¶

Тепловая карта — это матрица, где проекты расположены по строкам, а процессы ГОСТ Р 56939 — по столбцам. Каждая ячейка окрашена:

  • Зелёный (ПОЛНОЕ) — проект полностью соответствует требованиям данного процесса
  • Жёлтый (ЧАСТИЧНОЕ) — частичное соответствие, необходимы улучшения
  • Красный (ПРОБЕЛ) — несоответствие, критический пробел
  • Серый (Н/П) — процесс не применим к данному проекту

Обратите внимание на красные столбцы (массовые пробелы) и красные строки (проекты, требующие наибольшей работы по обеспечению соответствия).

7. Как читать лепестковую диаграмму?¶

Лепестковая диаграмма имеет 12 осей (Q1–Q12), каждая представляет измерение качества с оценкой от 0 до 10. Оценки проекта образуют многоугольник:

  • Большой, округлый многоугольник = высокое, сбалансированное качество
  • Маленький многоугольник = низкое качество в целом
  • Многоугольник с резкими впадинами = слабые места по конкретным измерениям

Сравните форму многоугольника с внешней границей (оценка 10 по каждой оси), чтобы определить, где в первую очередь требуются улучшения.

8. Что означает статус FAIL контроля выпуска?¶

Статус FAIL означает, что одна или более блокирующих проверок контроля выпуска не пройдены. Проект не должен быть выпущен до устранения всех блокирующих проблем. Откройте вкладку «Контроль выпуска» для просмотра числа блокирующих проблем и предупреждений, а также активного профиля. Типичные блокирующие проблемы: критические замечания по безопасности, пробелы соответствия в обязательных процессах и непройденные проверки анализа состава ПО.

9. Как часто обновляются данные панели мониторинга?¶

Данные панели мониторинга обновляются после завершения каждого аудита, проверки соответствия или сканирования анализа состава ПО для проекта. Временная метка в заголовке обзора портфеля указывает, когда данные были агрегированы в последний раз. Для получения обновлений в реальном времени панель мониторинга использует WebSocket-соединение по адресу /api/v2/dashboard/ws, которое передаёт инкрементальные обновления по мере их поступления.

Для запуска обновления вручную повторно выполните соответствующий анализ:

python -m src.cli audit --db /path/to/project.duckdb
python -m src.cli compliance gost-56939
python -m src.cli release check --db /path/to/project.duckdb

10. Как экспортировать данные для аудиторов?¶

Для регуляторных аудиторов, которым нужны отчёты в формате ГОСТ:

  1. Перейдите в центр соответствия и нажмите Экспорт ГОСТ, или
  2. Используйте API:
curl -X POST http://localhost:8000/api/v2/dashboard/export \
  -H "Content-Type: application/json" \
  -d '{"scope": "portfolio", "format": "gost", "sections": ["compliance"], "language": "ru"}' \
  -o audit-report.json
  1. Или используйте интерфейс командной строки:
python -m src.cli dashboard export --scope portfolio --format gost --language ru --output audit-report.json

Для подготовки отчёта в формате PDF для руководства:

python -m src.cli dashboard export --scope project --project my-project --format pdf --language ru --output report.pdf

11. В чём разница между замечаниями аудита и уязвимостями анализа состава ПО?¶

  • Замечания аудита — проблемы, обнаруженные при статическом анализе исходного кода (мёртвый код, сложность, паттерны безопасности и др.). Они выявляются механизмом аудита CodeGraph и организованы по 12 измерениям качества.
  • Уязвимости анализа состава ПО — известные CVE в сторонних зависимостях (библиотеках, пакетах). Они выявляются при анализе состава программного обеспечения и отслеживаются по идентификаторам CVE.

Оба типа влияют на оценку здоровья, но через разные компоненты (аудит — 30%, анализ состава ПО — 15%).

12. Можно ли подавить замечание, чтобы оно не влияло на оценку?¶

Да. Используйте механизм подавления контроля выпуска:

python -m src.cli release suppress --finding-id FINDING-123 --reason "Принятый риск согласно JIRA-456" --ticket JIRA-456

Подавленные замечания исключаются из оценки контроля выпуска, но остаются видимыми в результатах аудита для обеспечения прослеживаемости.

13. Как настроить уведомления в Telegram?¶

  1. Создайте бота Telegram через @BotFather и получите токен.
  2. Добавьте бота в целевой чат или группу.
  3. Задайте переменные окружения: DASHBOARD_TELEGRAM_TOKEN и DASHBOARD_TELEGRAM_CHAT_ID.
  4. Включите планировщик в config.yaml: yaml dashboard: snapshot_enabled: true
  5. Создайте подписку через API: bash curl -X POST http://localhost:8000/api/v2/dashboard/subscriptions \ -H "Authorization: Bearer $TOKEN" \ -H "Content-Type: application/json" \ -d '{"channel": "telegram", "events": ["risk_change", "release_gate_fail", "sca_critical"]}'

14. Как посмотреть исторические тенденции?¶

Используйте конечную точку тенденций из хранилища снимков:

curl http://localhost:8000/api/v2/dashboard/snapshots/my-project/trends?period=90d

Для этого необходимо включить планировщик снимков (snapshot_enabled: true). Без него конечная точка использует актуальные данные из обычного сервиса тенденций, который располагает только данными из истории аудитов.
