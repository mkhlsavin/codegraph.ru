Методология оценки состояния проекта

На дашборде есть два разных уровня оценки: 1. аудит проекта по двенадцати вопросам Q1–Q12, шкала 0–10; 2. итоговый Health Score, шкала 0–100, который.

РуководстваОбновлено: 2026-09-09

На дашборде есть два разных уровня оценки:

  1. аудит проекта по двенадцати вопросам Q1–Q12, шкала 0–10;
  2. итоговый Health Score, шкала 0–100, который объединяет Audit, Compliance, Release, SCA и Quality.

Одно число не заменяет исходные доказательства. Перед решением о выпуске нужно проверить состав оценки, её источник и свежесть. Техническое основание аудита — Code Property Graph. Как GoCPG строит и обогащает этот граф, описано в статье «Как GoCPG строит CPG и чем этот подход отличается от Joern». Модель компонентов, архитектурный DSL, presets, baseline/waiver и release profiles собраны отдельно в руководстве по контролю архитектуры.

Как оценивается аудит Q1–Q12

Каждый раздел объединяет замечания из профильных сценариев и, где это возможно, количественные метрики CPG. Таблица соответствует блоку «Справка → Источник оценки».

Как оценивается аудит Q1–Q12
Раздел Что проверяется Основные сценарии и метрики
Q1 Читаемость и стандарты кодирования Рефакторинг; методы с большим числом параметров.
Q2 Структура модулей и повторное использование Архитектура; циклы зависимостей, нестабильность Мартина.
Q3 Избыточный и трудный в сопровождении код Рефакторинг и техдолг; длинные методы, мёртвый и недостижимый код.
Q4 Масштабируемость Производительность и архитектура; структурные узкие места.
Q5 Производительность на больших объёмах Производительность; средняя и максимальная цикломатическая сложность.
Q6 Архитектура для роста Архитектурный аудит. Надёжного универсального метрического заместителя нет.
Q7 Уязвимости Security и compliance; high-risk hotspots, eval/exec, слабая криптография, секреты в коде.
Q8 Инъекции и утечки данных Security и точки входа; SQL- и shell-injection paths.
Q9 Сопровождаемость Техдолг и рефакторинг; TODO/FIXME, индекс сопровождаемости, ошибки конфигурации.
Q10 Тестируемость и покрытие Runtime line/method coverage и непокрытые методы повышенного риска.
Q11 Сложность связей и расширяемость Архитектура и техдолг; доля сложных методов, глубина наследования.
Q12 Документация Покрытие публичных сущностей документацией и комментариями.

Вклад замечаний

Синтетические замечания, уже полученные из метрик, второй раз в вес по уровню серьёзности не входят. Для остальных используются веса:

Вклад замечаний
Severity Вес
critical 1,00
high 0,70
medium 0,40
low 0,15
info 0,05

Повторные замечания одного уровня имеют убывающий вклад. Если n — номер замечания внутри уровня, начиная с нуля, его вклад равен:

weight(n) = severity_weight / (1 + 0.3 × n)
W = сумма weight(n) по реальным замечаниям раздела
base_section_score = 10 × exp(-0.3 × W)

Так один critical влияет сильнее одного info, но сотня однотипных сообщений не умножает штраф линейно.

Вклад метрик и нехватка данных

После severity-формулы применяется штраф Pq по метрикам раздела:

section_score = round(clamp(base_section_score - Pq, 0, 10), 1)

Для Q1–Q9, Q11 и Q12 штраф ограничен тремя баллами. Q10 рассчитывается отдельно и может дать штраф до девяти баллов. В Q6 метрического штрафа нет: раздел должен быть подтверждён архитектурным сценарием.

Отсутствие данных не означает оценку без замечаний:

  • если ни один исходный сценарий не завершился успешно и нет допустимой метрической основы, раздел получает нейтральные 5,0;
  • если замечаний нет, но есть пригодные метрики, расчёт начинается с 10,0 и применяет метрический штраф;
  • малая выборка первичных замечаний может ограничить максимум раздела 8,0 или 8,8;
  • для метрик-зависимых Q1, Q3, Q5, Q9, Q10, Q11 и Q12 отсутствие total_methods даёт нейтральный штраф 1,5, а не ложные 10,0.

Особое правило Q10

Покрытие методов весит 82%, строк — 18%:

coverage_score = clamp(
  10 × (0.82 × method_coverage + 0.18 × line_coverage)
  - risk_uncovered_penalty,
  0, 10
)
P10 = 10 - coverage_score

risk_uncovered_penalty учитывает непокрытые методы уровней critical/high, источники taint-анализа, точки входа API и критичные для графа методы; общий штраф ограничен 2,5 баллами. Дополнительно действуют fail-safe ограничения:

  • фактическое покрытие при выполнении недоступно — Q10 не выше 5,0;
  • line coverage < 5% и method coverage < 30% — не выше 3,9;
  • line coverage < 20% и method coverage < 60% — не выше 5,9.

Успешное число тестов не подменяет фактическое покрытие при выполнении.

Итоговый Audit

Сначала вычисляется overall_score_raw — среднее двенадцати секций. Затем CodeGraph снижает чувствительность общего числа к повторению одного риска в нескольких секциях. По умолчанию:

blended = 0.30 × overall_score_raw + 0.70 × module_health
audit_score = round(clamp(min(overall_score_raw + 3.5, blended), 0, 10), 1)

module_health — среднее по модулям с весом по числу методов. Для каждого модуля из 10 вычитаются ограниченные штрафы за долю мёртвого кода (до 3), индекс сопровождаемости ниже 80 (до 3), нестабильность Мартина (до 2) и плотность TODO (до 2). Для чистого модуля с индексом сопровождаемости не ниже 90 штраф нестабильности умножается на 0,35. Эти коэффициенты конфигурируемы; для конкретного результата источником истины служат версия конфигурации и сохранённый снимок аудита.

Как оцениваются остальные компоненты

Compliance

Отчёт ГОСТ Р 56939 присваивает каждому применимому процессу статус:

  • full = 1;
  • partial = 0,5;
  • gap = 0;
  • n_a исключается из знаменателя.
compliance_score = 100 × сумма process_value / число применимых процессов

Если применимых процессов нет, результат равен 0, а не 100. Список critical gaps остаётся отдельным доказательством: одинаковый процент не означает одинаковый профиль пробелов.

Release

Release Gate запускает набор проверок выбранного профиля. Каждая проверка имеет severity blocker или warning:

  • любой непройденный blocker → fail;
  • blocker нет, но есть непройденный warning → warn;
  • все проверки пройдены → pass.

Неизвестный профиль, ошибка проверки или отказ авторизации дают запрет по умолчанию. В стандартном профиле critical-замечания запрещены, high-замечания ограничены пятью, средняя цикломатическая сложность — 15, а покрытие должно быть не ниже 55%. Последние две проверки — warnings. Профили gost-56939, standard и minimal имеют разные наборы требований, поэтому рядом со статусом следует читать идентификатор профиля и результаты отдельных проверок.

SCA

SCA-компонент использует количество уязвимостей зависимостей по severity:

sca = clamp(1 - 0.15 × critical - 0.08 × high - 0.02 × medium, 0, 1)

Low и info в эту формулу не входят, но остаются в SCA-отчёте. Формула не заменяет анализ достижимости: она оценивает сохранённый severity summary.

Quality

complexity_norm = min(avg_complexity / 20, 1)
quality = 0.40 × runtime_line_coverage
        + 0.20 × documentation_coverage
        + 0.20 × (1 - dead_code_ratio)
        + 0.20 × (1 - complexity_norm)

Все доли лежат в диапазоне 0–1. Если фактическое покрытие строк недоступно, его вклад равен нулю и причина недоступности сохраняется в score_breakdown.

Итоговый Health Score

Текущая версия score_formula_version — v1. По умолчанию:

health_score = 100 × clamp(
  0.30 × audit/10
  + 0.25 × compliance/100
  + 0.20 × release
  + 0.15 × sca
  + 0.10 × quality,
  0, 1
)

Для Release используются значения pass = 1, warn = 0,5, fail = 0. Установка может переопределить веса, поэтому score_breakdown конкретного ответа важнее значений по умолчанию из документации.

Что означает «Источник оценки»

Блок показывает не ещё одну формулу, а происхождение данных каждой Q-секции:

  • current — секция пересчитана из метрик текущей ревизии;
  • snapshot — текущих метрик недостаточно, использован свежий снимок аудита;
  • stale_snapshot — доступен только устаревший snapshot;
  • n_a — секция неприменима к этому проекту;
  • needs_audit — надёжной текущей основы или снимка нет.

Дашборд пересчитывает только те Q-секции, для которых есть надёжное метрическое соответствие. Например, Q6 остаётся needs_audit без полноценного архитектурного аудита. Snapshot по умолчанию считается свежим не дольше 168 часов, но установка может изменить этот срок. Сверяйте ссылки на источники, идентификатор ревизии и время получения доказательств.

Отдельно поверхность проекта может иметь состояния current, stale, missing, updating, failed или unknown. Высокая оценка на устаревшем либо неизвестном основании не разрешает выпуск.

Когда итог недоступен

Сначала проверяйте health_score_available, затем число. При отсутствии обязательных доказательств CodeGraph возвращает оценку N/A и риск unknown. Стабильные причины включают:

  • audit_snapshot_missing;
  • compliance_report_missing;
  • release_gate_missing;
  • sca_summary_missing.

Недоступный вход — это не нулевой результат. Сначала восстановите или перегенерируйте доказательство.

Оценки и уровни риска

Оценки и уровни риска
Оценка Итоговый балл
A 85 и выше
B 70–84,99
C 55–69,99
D 40–54,99
F ниже 40

Риск учитывает и рабочие сигналы: critical при балле < 40, critical finding или compliance < 40; high при балле < 55 или Release fail; medium при балле < 70 или Release warn; иначе low.

Воспроизводимая проверка

python -m src.cli dashboard health <project> --format json

Проверяйте вместе health_score_available, score_formula_version, score_breakdown, risk_level, снимок аудита и основу анализа. Повторение на той же ревизии доказательств должно дать тот же результат.
