Методология оценки состояния проекта

Это руководство нужно, если показатель дашборда влияет на приоритеты, оценку риска или решение о выпуске. Здесь описано, из чего складывается итоговый.

РуководстваОбновлено: 2026-08-24

Это руководство нужно, если показатель дашборда влияет на приоритеты, оценку риска или решение о выпуске. Здесь описано, из чего складывается итоговый балл, когда его нельзя использовать и почему свежесть доказательств проверяется отдельно.

Текущая версия score_formula_version — v1. Ответ содержит версию и score_breakdown, поэтому пользователю не нужно восстанавливать смысл одного числа по косвенным признакам.

Состав итогового балла

Результат ограничен диапазоном 0–100 и состоит из пяти нормализованных компонентов. Имена компонентов совпадают с ответом API:

  • audit — 30%;
  • compliance — 25%;
  • release — 20%;
  • SCA — 15%;
  • quality — 10%.

Значения по умолчанию заданы в src/config/runtime_sections/unified_config_dashboard.py. Конкретная установка может переопределить их, поэтому для полученного результата нужно смотреть веса в score_breakdown.

Нормализация компонентов

  • Audit: балл аудита по шкале 0–10 делится на 10.
  • Compliance: балл ГОСТ Р 56939 по шкале 0–100 делится на 100.
  • Release: pass равен 1, warn — 0,5, fail или неизвестное значение — 0.
  • SCA: из 1 вычитается 0,15 за каждую критическую уязвимость, 0,08 — за high и 0,02 — за medium; результат ограничивается диапазоном 0–1.
  • У Quality есть внутренние веса: runtime coverage — 40%; documentation coverage — 20%; dead-code ratio — 20%; complexity — 20%. Максимальный штраф за сложность достигается при среднем значении 20.

Если runtime line coverage недоступно, его вклад внутри Quality равен нулю, а причина недоступности остаётся в расшифровке. Нельзя подменять отсутствующее покрытие успешным количеством тестов.

Недоступный балл — не ноль

Сначала проверяйте health_score_available, а затем числовое значение. Если обязательных доказательств нет, CodeGraph возвращает оценку N/A и риск unknown. Причина указана одним или несколькими стабильными кодами:

  • audit_snapshot_missing;
  • compliance_report_missing;
  • release_gate_missing;
  • sca_summary_missing.

Отсутствующий вход не означает плохой, но полный результат. Восстановите или перегенерируйте доказательство, затем повторите запрос.

Оценки и уровни риска

Границы оценок по умолчанию:

Оценки и уровни риска
Оценка Итоговый балл
A 85 и выше
B 70–84,99
C 55–69,99
D 40–54,99
F ниже 40

Уровень риска учитывает дополнительные рабочие сигналы:

  • critical: балл < 40, есть критическое замечание или compliance < 40;
  • high: балл < 55 или release gate имеет статус fail;
  • medium: балл < 70 или release gate имеет статус warn;
  • low: ни одно из условий выше не выполнено.

Поэтому у двух проектов с одинаковым баллом уровень риска может различаться.

Свежесть проверяется отдельно

Корректная формула не доказывает актуальность входных данных. Проверяйте basis анализа и состояние поверхности. UI и API различают current, stale, missing, updating, failed и unknown. Высокая оценка на устаревшем или неизвестном основании не разрешает выпуск.

Воспроизводимая проверка

Выполните:

python -m src.cli dashboard health <project> --format json

Проверьте вместе health_score_available, score_formula_version, score_breakdown, risk_level и basis анализа. Повторная проверка на той же ревизии доказательств должна дать тот же результат.

Источники истины

  • src/api/services/dashboard/aggregation_core/aggregation_scoring_mixin.py — нормализация, вклад компонентов, оценки и риск.
  • src/api/services/dashboard/aggregation_core/aggregation.py — доступность балла, поля ответа и версия формулы.
  • src/config/runtime_sections/unified_config_dashboard.py — веса и пороги по умолчанию.
  • src/api/services/dashboard/surface_state/surface_freshness.py — состояния свежести и данные для восстановления.

Маршруты и пользовательские действия описаны в руководстве пользователя, а телеметрия и оповещения — в руководстве по мониторингу.
