Интеграция ACP

Руководство по интеграции ACP: транспорты, JSON-RPC-методы, авторизация, границы workspace и ограничения approval в CodeGraph.

API ДокументацияОбновлено: 2026-08-24

CodeGraph реализует Agent Client Protocol (ACP) поверх JSON-RPC для интеграции с редакторами. ACP подходит, когда IDE нужны сессии, потоковые agent-turn, диагностика, hover, ограниченный доступ к файлам или терминалу. Каталог MCP-инструментов относится к другому протоколу и здесь не дублируется.

Транспорты и маршруты

Транспорты и маршруты
Транспорт Точка входа Применение
stdio codegraph-acp Локальная IDE запускает отдельный процесс агента.
HTTP POST /api/v1/admin/runtime/acp/rpc Один аутентифицированный JSON-RPC-запрос.
WebSocket WS /api/v1/admin/runtime/acp/ws Двунаправленные запросы и потоковые уведомления.

Управление HTTP-сессиями доступно через GET /api/v1/admin/runtime/acp/sessions и DELETE /api/v1/admin/runtime/acp/sessions/{session_id}. Список фильтруется по текущему пользователю, а при удалении проверяется владелец.

Граница аутентификации

Для HTTP JSON-RPC и маршрутов сессий нужны роль администратора, scope admin:all либо service account со scope scenarios:execute. Обход аутентификации на localhost возможен только при явно включённом параметре local_dev_unauthenticated_surfaces_enabled.

WebSocket принимает bearer access token или API key. Для машинной учётной записи сервер дополнительно проверяет область проекта, версию X-CodeGraph-Machine-Contract, политику интерфейса и настроенные требования mTLS. Аутентификация транспорта завершается до разбора JSON-RPC-параметров; метод authenticate работает внутри уже проверенного соединения.

Инициализация и группы методов

На каждом соединении сначала вызывайте initialize. До инициализации сервер отклоняет другие методы с кодом -32002.

Инициализация и группы методов
Группа Реализованные методы
Сессии authenticate, session/new, session/load, session/prompt, session/cancel
Файлы fs/read_text_file, fs/write_text_file
Терминал terminal/create, terminal/output, terminal/wait_for_exit, terminal/kill, terminal/release
Потоки thread/start, thread/resume, thread/fork, thread/list, thread/archive, thread/compact
Turn turn/start, turn/interrupt
IDE diagnostics/subscribe, diagnostics/unsubscribe, hover/request
Ответ на approval item/fileChange/respondApproval

Во время session/prompt и turn/start сервер может отправлять JSON-RPC-уведомления. Клиент должен обрабатывать session/update и согласованные уведомления diagnostics, hover и approval, не полагаясь на фиксированное число MCP-инструментов.

Ограничение workspace и терминала

Файловые методы требуют абсолютные workspaceRoot и path. Если целевой путь после нормализации не находится внутри корня, сервер возвращает outside workspace root. При записи также запрещены чувствительные фрагменты пути: .git, .env, .ssh, .aws и node_modules.

Терминальные методы используют тот же абсолютный workspaceRoot; cwd должен оставаться внутри него. Команда запускается как argv с shell=False. В исходниках задан ограниченный allowlist команд сборки и чтения; интерпретаторы и оболочки python, powershell, pwsh, cmd, bash, sh и node явно запрещены. Аргументы передаются нативным списком строк без NUL, перевода строки и возврата каретки.

Эти проверки задают границу ACP для path traversal и shell injection. Сетевые маршруты обслуживаются штатной аутентификацией и областью проекта.

Ограничение approval для файловых изменений

Сервер объявляет approval flow и умеет отправлять item/fileChange/requestApproval; клиент отвечает через item/fileChange/respondApproval. Если ответ не поступил до тайм-аута, решение считается отклонённым.

Текущий обработчик fs/write_text_file не вызывает автоматически этот approval bridge. После проверки пути он сразу выполняет запись внутри workspace. Если процесс требует человеческого approval, клиент или внешний workflow должен получить его до открытия write-метода. Само наличие Одобрение конкретной записи подтверждается сохранённым approval перед открытием write-метода.

Восстановление

  1. Проверьте префикс /api/v1/admin/runtime/acp: исторический /acp неактуален.
  2. Проверьте аутентификацию транспорта до разбора JSON-RPC-параметров.
  3. Вызовите initialize, затем создайте или загрузите сессию либо поток.
  4. При ошибке файлового или терминального метода передайте абсолютные workspaceRoot, path и cwd; все цели должны находиться внутри одного корня.
  5. Запрет executable или отсутствие approval — результат политики. Не обходите его командой, составленной для запуска через shell.

Источники истины

  • src/api/routers/collaboration_suite/acp.py — HTTP/WebSocket-маршруты и аутентификация.
  • src/acp/server/core/agent.py — диспетчер методов и проверка инициализации.
  • src/acp/server/routing/handlers.py — ограничения файловой системы и терминала.
  • src/acp/server/routing/approval_bridge.py — запрос approval, тайм-аут и обработка ответа.
  • src/acp/cli.py — локальная stdio-точка входа codegraph-acp.
