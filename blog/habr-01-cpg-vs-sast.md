## Хук

> Самоаудит нашей кодовой базы нашёл 57 небезопасных вызовов функций, 50 захардкоженных секретов и 5 случаев слабой криптографии. Четыре из девяти гипотез безопасности подтвердились. Оценка по измерению «Безопасность» — 4.6 из 10.

Это не результат работы внешнего пентестера. Это данные нашего собственного инструмента — CodeGraph — направленного на самого себя. И самое неприятное: в кодовой базе уже стояли SonarQube и Bandit. Они пропустили больше половины того, что нашёл граф свойств кода.

Почему? Потому что традиционные инструменты анализа безопасности (SAST) работают на уровне **сопоставления шаблонов** — ищут опасные конструкции в синтаксическом дереве. Этот подход видит `strcpy` в коде, но не видит, **откуда пришли данные** и **проходили ли они валидацию**. Отсюда и 91% ложных срабатываний по данным Ghost Security за 2025 год — девять из десяти алертов оказываются пустышками.

В этой статье — на реальных примерах из нашего проекта — покажем, почему сопоставление шаблонов принципиально ограничено и как граф свойств кода решает эту проблему.

## 1. Как работает традиционный анализ безопасности

Классический инструмент (SonarQube, Semgrep, Fortify, Bandit) работает в три шага:

1. **Разбор** — исходный код превращается в синтаксическое дерево
2. **Сопоставление шаблонов** — набор правил ищет опасные конструкции в дереве
3. **Отчёт** — каждое совпадение с шаблоном = алерт

Проблема — в шаге 2. Сопоставление шаблонов видит **синтаксис**, но не видит **семантику**. Оно не знает:

- Откуда пришли данные (пользовательский ввод или константа из конфигурации?)
- Через какие функции они прошли (была ли валидация или санитизация?)
- Достигают ли данные опасной точки (SQL-запрос, системный вызов, вывод в HTML?)

### Пример из нашего кода: ложное срабатывание Bandit

```python
# src/services/cpg/base.py
def execute_query(self, sql: str, params=None):
    result = self.conn.execute(sql, params)
    return result.fetchall()
```

Bandit видит: `execute()` + строковый параметр `sql` → **SQL-инъекция!** (B608)

Но `sql` — это не пользовательский ввод. Это захардкоженный запрос из кода `CPGQueryService`, собранный программно и параметризованный через `params`. Пользовательские данные до этого вызова не добираются — между ними стоят слои валидации, маршрутизации запросов и формирования SQL.

Bandit этого не знает. Он видит `execute(sql)` — и кричит.

## 2. Что такое граф свойств кода

Граф свойств кода (Code Property Graph, CPG) — это **единая структура данных**, объединяющая четыре графа:

| Граф | Что показывает | Зачем нужен |
|------|---------------|-------------|
| Синтаксическое дерево (AST) | Структура кода | Что написано |
| Граф потока управления (CFG) | Порядок выполнения инструкций | Как выполняется |
| Граф программных зависимостей (PDG) | Зависимости по данным и управлению | Откуда что зависит |
| Граф зависимостей по данным (DDG) | Распространение значений переменных | Как значения текут между функциями |

Инженер, знакомый с Roslyn (.NET), узнает в этом паттерн: синтаксическое дерево (`SyntaxTree`) + семантическая модель (`SemanticModel`) + таблица символов. CPG обобщает эту идею: вместо компиляторного API для одного языка — единый граф для 11 языков, доступный через SQL-запросы.

Когда все четыре графа объединены, инструмент может задать вопрос:

> «Существует ли путь от пользовательского ввода до SQL-запроса, который **не проходит** через функцию санитизации?»

Это **анализ потоков заражённых данных** (taint analysis). И он принципиально невозможен на уровне синтаксического дерева.

## 3. Как это работает на нашем проекте

CodeGraph анализирует сам себя. Это позволяет показать не абстрактные примеры, а реальные находки.

### Пример 1: Межпроцедурная цепочка через три файла

Теперь рассмотрим другой метод в том же файле — `run_query`, который, в отличие от `execute_query` из примера выше, **не использует параметризацию**:

```python
# src/api/routers/query.py
@router.post("/query")
async def execute_query(request: QueryRequest):
    result = await cpg_service.run_query(request.sql)  # ← данные от пользователя
    return result

# src/services/cpg/base.py
def run_query(self, sql: str):
    return self.conn.execute(sql)  # ← опасная точка (нет params!)
```

**Традиционный анализ**: `run_query` получает параметр `sql`. Откуда он пришёл? Инструмент не видит, что вызов идёт из API-обработчика. Либо молчит (пропуск), либо кричит на каждый `execute()` (шум).

**Граф свойств кода**: строит цепочку `request.sql` → `execute_query()` → `run_query()` → `conn.execute()`. Путь от источника (`request.sql` — пользовательский ввод) до приёмника (`conn.execute()` — выполнение SQL) существует. Санитизации на пути нет. **Настоящая уязвимость.**

В нашем отчёте аудита она зафиксирована как CWE-89 (SQL-инъекция по классификации MITRE) с приоритетом 0.79.

### Пример 2: Ложный алерт, который граф отсекает

```python
# src/workflow/scenarios/audit_composite.py
def _metrics_cte(self):
    sql = f"""
        WITH methods AS (
            SELECT * FROM nodes_method
            WHERE NOT is_test {self._method_filters}
        )
        SELECT COUNT(*) FROM methods WHERE fan_in = 0
    """
    return self.cpg.execute(sql)
```

**Традиционный анализ**: Видит f-строку → `execute()`. Алерт: SQL-инъекция!

**Граф свойств кода**: Откуда берётся `self._method_filters`? Анализ потоков данных показывает: это свойство объекта `AuditRunner`, которое формируется из `DEFAULT_METHOD_FILTERS` — константы из конфигурационного файла. Пользовательские данные до этого значения не добираются. **Ложное срабатывание отсечено.**

### Пример 3: Обратный вызов — невидимка для шаблонов

```python
# src/api/main.py
app = FastAPI()

@app.middleware("http")
async def add_request_id(request: Request, call_next):
    request_id = request.headers.get("X-Request-ID", str(uuid4()))
    response = await call_next(request)
    response.headers["X-Request-ID"] = request_id
    return response
```

**Традиционный анализ**: `add_request_id` — это обычная функция. Откуда она вызывается? В коде проекта нет `add_request_id()`. Инструмент либо не анализирует декораторы `@app.middleware`, либо не знает, что FastAPI вызовет эту функцию с каждым HTTP-запросом — и `request.headers` содержит данные от пользователя.

**Граф свойств кода**: Декоратор `@app.middleware` расставляет флаг `is_entry_point`. Парсер знает, что это точка входа фреймворка, и строит граф потоков от `request.headers` дальше. Если `request_id` попадёт без валидации в `response.headers` — анализ это зафиксирует.

## 4. Конфигурируемая семантика: 733 отображения для 10 языков

Анализ потоков данных через функции стандартных библиотек — одна из самых сложных задач. Инструмент не имеет исходного кода `strcpy`, `snprintf` или `json.loads`. Как понять, куда текут данные?

CodeGraph решает это через YAML-описания семантики:

```yaml
# configs/semantics/c_stdlib.yaml
function: "strcpy"
from_args: [1]           # Данные текут из аргумента 1 (источник)
to_args: [0]             # Данные текут в аргумент 0 (приёмник)
to_return: false
is_sink: true
sink_type: "buffer_overflow"
global_writes: ["errno"]  # Побочный эффект на глобальную переменную
```

733 таких отображений для 10 языков (C, C++, Go, Python, JavaScript, TypeScript, Java, Kotlin, C#, PHP). Межпроцедурный анализ **точно** моделирует потоки данных через функции стандартных библиотек без доступа к их исходному коду.

Чтобы добавить семантику новой функции — одна строка в YAML. Без перекомпиляции. В Joern, эталонной реализации графа свойств кода, эта информация захардкожена в исходном коде на Scala.

### Пример: побочные эффекты на глобальные переменные

Функция `strtol` в C модифицирует глобальную переменную `errno`. Joern этого не отслеживает (открытая задача #5581). В CodeGraph побочные эффекты описаны через `global_writes`:

```yaml
function: "strtol"
from_args: [0]
to_return: true
global_writes: ["errno"]
```

Межпроцедурный анализ достигающих определений видит, что после вызова `strtol` значение `errno` могло измениться — и учитывает это при построении графа зависимостей.

| Категория | Количество | Примеры |

Четыре из девяти гипотез безопасности, сгенерированных автоматически, подтвердились при проверке — уровень подтверждения 44%.

### Что пропустил Bandit, но нашёл граф

Bandit нашёл 98 предупреждений в нашем проекте — но большинство из них были ложными: `assert` в тестах (B101), привязка к `0.0.0.0` в Docker-окружении (B104), пустые `except` для необязательных импортов (B110). Мы намеренно исключили эти категории через конфигурацию.

Граф свойств кода нашёл то, что Bandit **не может** найти в принципе:

- **Межфайловые цепочки** от API-обработчика до SQL-запроса через 3–4 промежуточных вызова
- **Захардкоженные секреты** не по regexp-шаблону, а по анализу потоков: значение присваивается переменной `password` и передаётся в функцию аутентификации
- **Слабую криптографию с контекстом**: MD5 для хеширования паролей — уязвимость; MD5 для хеширования кеш-ключей — допустимо. Разница — в графе потоков данных

## 6. 190 правил структурного поиска с ограничениями графа

Помимо анализа потоков данных, CodeGraph поддерживает структурный поиск по шаблонам — но, в отличие от Semgrep или grep, **с ограничениями на уровне графа**:

```yaml
# configs/rules/python/py-format-sql.yaml
id: py-format-sql
message: "Форматирование строки SQL через $METHOD — используйте параметризованные запросы"
severity: error
languages: [python]
rule:
  pattern: '$CONN.execute(f"$SQL")'
cpg:
  dataflow:
    from: "$SQL"
    to: "$CONN.execute"
  metrics:
    not_test_file: true
fix: '$CONN.execute("$SQL", params)'
```

Обратите внимание на секцию `cpg:` — шаблон сработает только если анализ потоков данных подтверждает, что `$SQL` содержит внешние данные. Это отсекает ложные срабатывания на захардкоженных запросах.

190 таких правил для 11 языков (C, C++, Go, Python, JavaScript, TypeScript, Java, Kotlin, C#, PHP, PostgreSQL). 25 правил содержат шаблоны автоматического исправления.

## 7. Конвейер из 33 аналитического прохода

Анализ безопасности в CodeGraph — не отдельный инструмент, а часть конвейера из 33 проходов, выполняющихся параллельно:

```
Разбор кода → Типы → Восстановление типов (3 итерации) →
→ Граф потока управления → Доминаторы →
→ Разрешение импортов → Распространение имён вызовов →
→ Граф вызовов → Разрешение вызовов →
→ Потоки данных → Анализ псевдонимов → Достигающие определения →
→ Межпроцедурный анализ (семантика stdlib + глобальные побочные эффекты) →
→ Граф программных зависимостей → Зависимости по данным →
→ Метрики → Структурный поиск шаблонов
```

Каждый проход читает из графа в оперативной памяти (нулевой доступ к базе данных) и пишет результаты в дельта-граф. Зависимые проходы разблокируются мгновенно — без ожидания записи в хранилище.

Для безопасности критичны фазы межпроцедурного анализа (фаза 5b): именно они строят цепочки «источник → санитизация → приёмник» через границы функций и файлов.

## 8. Сравнение подходов

| Аспект | Сопоставление шаблонов (Bandit, Semgrep) | Граф свойств кода (CodeGraph) |
|--------|------------------------------------------|-------------------------------|
| Межпроцедурный анализ | Нет (или ограниченный в рамках файла) | Да, через весь проект |
| Анализ потоков данных | Нет | Да, с учётом семантики stdlib |
| Ложные срабатывания | 80–91% (Ghost Security, 2025) | Отсекаются анализом потоков |
| Обратные вызовы, фреймворки | Не отслеживаются | Синтетические рёбра в графе вызовов |
| Автоматическое исправление | Текстовая подстановка | С учётом контекста графа |
| Языки | Обычно 1–5 | 11 |
| Семантика стандартных библиотек | Нет | 733 YAML-отображений |
| Роль LLM | Компенсирует отсутствие контекста | Дополняет готовые факты из графа |

## Заключение

57 небезопасных вызовов, 50 захардкоженных секретов, 5 случаев слабой криптографии — в проекте, который уже проверялся Bandit и SonarQube. Эти находки стали возможны не потому, что мы написали больше правил, а потому, что сменили **архитектурный подход**: от сопоставления шаблонов с синтаксическим деревом — к анализу потоков данных через граф свойств кода.

Сопоставление шаблонов было адекватным подходом, когда кодовые базы умещались в одном файле. Сегодня, когда уязвимость — это цепочка из 5–10 вызовов через 3 файла, нужен инструмент, который видит **потоки данных**, а не текстовые совпадения.

Граф свойств кода — не замена традиционному анализу, а его эволюция.
