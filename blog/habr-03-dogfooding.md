## Хук

> 35 847 из 41 034 методов имеют fan-in = 0. Восемьдесят семь процентов функций нашей кодовой базы якобы никем не вызываются.

Это была строчка из 17-й итерации отчёта самоаудита CodeGraph — инструмента анализа графа свойств кода, который мы направили на самого себя. Мы точно знали, что это чушь: проект работает, тесты проходят, API отвечает. Но инструмент так не считал.

Через полторы недели тот же инструмент на том же коде показал **ноль**. Не ноль ложных срабатываний при сотнях реальных находок — а ровно ноль: все 44 найденных мёртвых функции оказались действительно мёртвыми, все живые функции были корректно распознаны.

## 1. Постановка задачи: что такое мёртвый код и почему его сложно искать

### Определение

Мёртвый метод — функция, которую никто не вызывает. Формально: `fan_in = 0`, где fan_in — количество входящих рёбер в графе вызовов.

Казалось бы, задача тривиальная: построй граф вызовов, найди вершины с нулевым входящим ребром — готово. На практике всё сложнее.

### Почему grep не работает

Первый инстинкт разработчика — `grep -r "function_name" .` — уже ломается на базовых конструкциях:

```python
# grep найдёт "process" — но это не вызов, а определение
def process(data):
    return transform(data)

# grep НЕ поймёт, что validate вызывается через словарь диспетчеризации
handlers = {
    "validate": validate_input,
    "transform": transform_data,
}
handlers[action](payload)
```

Grep работает с текстом. Граф вызовов работает с **семантикой** — он знает, что `validate_input` передаётся как вызываемая ссылка в словарь, а `handlers[action](payload)` — это косвенный вызов.

### Почему простой граф вызовов тоже не работает

Даже если вы построили граф вызовов, наивный подход `fan_in = 0 → мёртвый` даёт **тысячи** ложных срабатываний:

| Категория | Пример | Почему не мёртвый |
|-----------|--------|-------------------|
| Точки входа фреймворка | `@app.get("/users")` | Вызывается FastAPI, а не вашим кодом |
| Обратные вызовы | `Depends(get_db)` | Вызывается системой внедрения зависимостей |
| Тестовые функции | `test_login_success()` | Вызывается pytest, а не вашим кодом |
| Вложенные функции | `def helper() внутри def main()` | Вызывается из замыкания |
| Динамическая диспетчеризация | `getattr(plugin, method_name)()` | Вызывается через рефлексию |
| Реэкспорт через `__init__.py` | `from .module import func` | Вызывается потребителями пакета |

Для каждой из этих категорий нужен свой механизм — либо фильтрации на уровне запроса, либо обнаружения на уровне парсера. Иначе отчёт бесполезен, и команда перестанет ему доверять.

## 2. Хроника: от 35 тысяч до нуля за 8 этапов

Мы не пришли к нулю за один шаг. Каждый этап выявлял новую категорию ложных срабатываний — и мы итеративно наращивали точность.

### Этап 1: Первый запуск — 35 847 методов с fan-in = 0

25 февраля 2026. Мы в семнадцатый раз запускаем сценарий аудита на собственной кодовой базе CodeGraph. Полный отчёт (v17) — 41 034 метода, 2 170 файлов, общая оценка 4.7 из 10. И вот ключевая строка:

```
Распределение Fan-in:
  0      — 35 847
  1-5    — 4 595
  6-10   — 418
  ...
```

**87% всех функций** имеют нулевой fan-in. Метрика `dead_method_count` (с базовым фильтром `NOT is_test`) показывает ~9 775 — десять тысяч «неиспользуемых» методов.

Мы смотрим на список и видим: `__init__`, `setUp`, `process_request`, обработчики маршрутов FastAPI, фикстуры pytest, замыкания... Очевидно, что граф вызовов массово не разрешает вызовы. Инструмент не готов — но мы получили точную диагностику: **проблема в разрешении импортов**.

### Отступление: как вообще устроено разрешение вызовов

Прежде чем рассказывать об исправлениях, нужно объяснить задачу. Когда парсер видит в коде вызов `Y()`, ему нужно найти **определение** функции `Y` — конкретный метод в конкретном файле. Это и есть **разрешение вызова**: превращение имени в ребро графа.

В статически типизированных языках это тривиально: компилятор знает точный тип. В Python — нет. Функция может быть определена в другом файле, импортирована под другим именем, вызвана через `self.method()` без аннотации типа, или вообще передана как аргумент.

Поэтому алгоритм разрешения вызовов — это **каскад стратегий**, от самой точной к самой приблизительной. Если точная стратегия не сработала, пробуем следующую:

```
1. Точное совпадение полного квалифицированного имени
   "src/services/cpg/base.py:execute_query" → нашли → готово

2. Имя + сигнатура (количество и типы параметров)
   "execute_query(str, dict)" → ищем среди всех методов → нашли → готово

3. Имя + файл (метод с таким именем в том же файле)
   "execute_query" в том же файле → нашли → готово

4. Через карту импортов (для вызовов импортированных функций)
   from X import Y; Y() → находим Y в модуле X → готово

5. Только по имени (если имя уникально во всём проекте)
   "execute_query" — единственная во всём проекте → готово

Не нашли нигде → создаём заглушку (узел-заместитель)
```

Каждая стратегия — это компромисс между точностью и полнотой. Точное совпадение имени никогда не ошибётся, но требует, чтобы вызывающий код знал полный путь к функции. Поиск только по имени найдёт всё, но может перепутать `utils.parse()` из одного модуля с `helpers.parse()` из другого.

Когда мы начали догфуддинг, работали только точное совпадение полного имени, поиск по сигнатуре, по файлу и по уникальному имени. Весь блок «через карту импортов» (стратегия 4 в списке выше) отсутствовал — а в Python **большинство** вызовов идёт именно через импорты.

### Этап 2: Разрешение импортов — ~5 000

Первое крупное исправление: мы добавили четыре стратегии разрешения через импорты, которые закрыли самый массовый источник ложных срабатываний.

Проблема: когда код пишет `from src.services.cpg import CPGQueryService`, а потом вызывает `CPGQueryService()`, алгоритм видел имя `CPGQueryService`, но не мог сопоставить его с определением в файле `src/services/cpg/__init__.py` — потому что не знал о связи между импортом и исходным модулем.

Четыре новых стратегии:

- **Глобальная карта импортов** — при вызове `Y()` смотрим, не был ли `Y` импортирован; если да — ищем определение в модуле-источнике
- **Локальные импорты файла** — ищем среди импортов текущего файла
- **Разрешение по модульному имени** — разбиваем `src.services.cpg.CPGQueryService` на модуль (`src.services.cpg`) и имя (`CPGQueryService`), ищем файл по модулю
- **Преобразование пути импорта в путь файла** — превращаем `src/services/cpg.execute_query` в путь файла `src/services/cpg.py` и ищем в нём функцию `execute_query`

**Снижение: почти вдвое.**

### Этап 3: Порядок создания заглушек — ~3 500

Тонкая ошибка в конвейере: заглушки (узлы-заместители для неразрешённых вызовов) создавались **до** завершения разрешения типов. Конструктор `ClassName()` должен разрешаться в метод `__init__`, но заглушка `ClassName` перехватывала вызов раньше — и алгоритм останавливался, считая вызов «разрешённым» в заглушку.

Исправление: создание заглушек перенесено на этап **после** разрешения типов.

**Снижение: ~1 500 ложных срабатываний.**

### Этап 4: Разрешение self/cls, индекс классов, связывание конструкторов — ~2 500

Пять целевых исправлений в алгоритме разрешения и проходе восстановления типов:

**Распространение self/cls/super.** Когда Python-метод пишет `self.process()`, алгоритму нужно знать тип `self`. Мы добавили в таблицу символов каждого метода привязки:
```
self  → ClassName (класс, в котором определён метод)
cls   → ClassName (для @classmethod)
super → ParentClass (из цепочки наследования)
```

Это позволило разрешать `self.process()` → `ClassName.process()` — вместо безнадёжного поиска по голому имени `process`.

**Индекс методов классов.** Новая стратегия разрешения: для каждого класса хранится полный список его методов с учётом наследования. При вызове `self.method()` сначала ищем `method` среди методов класса (быстро и точно), и только потом — в более слабых стратегиях по имени и файлу.

**Прямое связывание конструкторов.** Вызов `ClassName()` теперь напрямую связывается с `ClassName.__init__()` — это специализированная стратегия, которая не требует поиска по имени и не может промахнуться.

**Заглушки типа `<returnValue>`.** Для неразрешённых вызовов создаются узлы вида `CPGQueryService.execute.<returnValue>`. Зачем? Даже если мы не знаем точный тип возврата `execute()`, мы знаем, что это «что-то, что вернул `CPGQueryService.execute`». Если дальше по коду этот результат используется для вызова `.fetchall()`, на следующей итерации восстановления типов появится информация для разрешения.

**Три итерации вместо двух.** Увеличение количества итераций восстановления типов с 2 до 3 закрыло случаи, когда тип выводится через два промежуточных вызова: `A → B → C`, где тип `C` можно определить только после того, как восстановлен тип `B`.

**Снижение: ~1 000 ложных срабатываний.**

### Этап 5: Фильтры V25–V27 — ~600

К этому моменту граф вызовов стал значительно точнее, но оставались категории ложных срабатываний, которые невозможно устранить на уровне графа — потому что вызывающий код находится **за пределами** анализируемого проекта (фреймворки, среда выполнения тестов).

Мы добавили три уровня фильтрации в SQL-запрос аудита:

**V25: Точки входа.** Парсер расставляет флаг `is_entry_point` по 8 стратегиям (декораторы, имена, пути файлов, таблицы диспетчеризации, экспорты, обратные вызовы, миграции, жизненный цикл). Запрос исключает помеченные функции.

**V26: Классовая достижимость.** Если в классе есть хотя бы один метод с `fan_in > 0` (конструктор, фабрика), все остальные методы класса исключаются — класс используется, значит, его методы тоже доступны.

**V27: Вложенные функции.** Парсер расставляет флаг `is_nested` для функций, определённых внутри других функций. Замыкания всегда имеют `fan_in = 0`, потому что граф вызовов не строит рёбра внутри области видимости функции.

**V27 оказался самым эффективным фильтром: снижение с 614 до ~200 (67% отсечённых ложных срабатываний).**

### Этап 6: Эвристики модулей V28–V29 — ~340

Два эвристических фильтра для модулей с динамической диспетчеризацией:

**V28: Полностью мёртвые модули.** Если **все** функции файла имеют `fan_in = 0` — это не файл из мёртвых функций, а модуль, который целиком вызывается через рефлексию или фреймворковые механизмы (плагины доменов, обработчики протоколов).

**V29: Модули с низкой жизнеспособностью.** Модули с 5 и более методами, из которых менее 40% имеют хотя бы один вызов. Та же логика: если большинство функций модуля «мёртвые», скорее всего модуль диспетчеризуется динамически.

### Этап 7: Распознавание паттернов диспетчеризации — ~50

Вместо эвристической фильтрации целых модулей — точечное распознавание конкретных паттернов в парсере:

**Таблицы диспетчеризации в словарях.** Конструкция `{"scenario_02": security_workflow}` теперь создаёт синтетическое ребро вызова от словаря к `security_workflow`.

**Обратные вызовы фреймворков.** Функции, передаваемые как аргументы в `Depends()`, `Field(default_factory=)`, `add_task()`, `add_node()`, `register()` — всё это теперь создаёт рёбра вызовов.

**Ленивые импорты.** Конструкция `from X import Y` внутри тела функции — это почти всегда вызов `Y()` несколькими строками ниже. Создаётся синтетическое ребро.

**Точки входа CLI.** Функции `run_*_command`, `handle_*_command` в каталогах `/cli/` помечаются как точки входа.

**Затенение TYPE_DECL.** Импорт `from .tools.callgraph import register_tools` создаёт узел `TYPE_DECL` (объявление типа) в файле-импортёре. Этот узел затенял реальную функцию `METHOD` в индексе полных квалифицированных имён. Исправление: в индексах по имени и файлу хранятся только `METHOD`, в индексе точных полных имён — все типы, но `METHOD` имеет приоритет.

### Этап 8: Финальные 6 ошибок парсера — 0

Оставшиеся ~50 ложных срабатываний привели к обнаружению шести ошибок в извлечении вызовов и разрешении имён. После их исправления, удаления 44 действительно мёртвых функций и пересборки базы данных — **dead_method_count = 0**.

## 3. Девять ошибок, которые вскрыл догфуддинг

Самая ценная часть процесса — не удалённый мёртвый код, а **обнаруженные ошибки инструмента**. Каждое ложное срабатывание — это живая функция, которую парсер не связал с вызовом. Значит, граф вызовов неполон — и не только для нашего проекта, а для **всех** проектов.

### Ошибка 1: Невидимые вызовы в списковых включениях

```python
results = [transform(item) for item in data if validate(item)]
#          ↑ transform()                        ↑ validate()
#          Оба вызова были невидимы для графа вызовов
```

Функция `extractArgumentValue` в парсере создавала узел «включение» и **возвращала управление без рекурсии** в дочерние выражения. Вызовы `transform()` и `validate()` внутри конструкции `for ... in ... if ...` оставались без рёбер в графе.

**Исправление:** Добавлена рекурсия в дочерние выражения, включая ветви `for_in_clause` и `if_clause`.

### Ошибка 2: Вызовы внутри f-строк в операторе return

```python
def get_label(path):
    return f"Результат: {format_path(path)}"
    #                     ↑ format_path() — невидим для графа
```

Ветка обработки строковых литералов в `extractReturn` создавала узел `LITERAL`, не проверяя, содержит ли строка интерполяцию. Для f-строк нужно делегировать обработку в `walkNode`, который умеет извлекать вызовы из интерполяционных выражений.

**Исправление:** Проверка `nodeHasInterpolation()` перед обработкой; для f-строк — делегирование в рекурсивный обход.

### Ошибка 3: Вызовы внутри `await`

```python
result = await fetch_data(url)
#               ↑ fetch_data() — невидим
```

Узел `await` в рекурсивном обходе дерева был помечен флагом `skipRecurse = true`. Логика: `await` — просто обёртка. Но `skipRecurse` подавляла рекурсию в дочерние узлы, и вызов функции терялся. Та же проблема затронула `yield` и `yield from`.

**Исправление:** Убран флаг для выражений, которые могут содержать вызовы.

### Ошибка 4: Условные выражения

```python
handler = validate(x) if check(x) else default(x)
#         ↑ validate()    ↑ check()    ↑ default() — все три невидимы
```

Конструкция `conditional_expression` обрабатывалась как простое выражение без рекурсии.

### Ошибка 5: Конкатенация f-строк

```python
query = f"SELECT * FROM {table}" + f" WHERE {build_condition(params)}"
#                                            ↑ build_condition() — невидим
```

При обработке бинарной операции `+` между двумя f-строками вторая строка обрабатывалась как обычный литерал.

### Ошибка 6: Реэкспорт через `__init__.py`

```python
# src/workflow/__init__.py
from .orchestration.copilot import MultiScenarioCopilot
__all__ = ["MultiScenarioCopilot"]
```

Парсер помечал `MultiScenarioCopilot` как точку входа, но не создавал **ребро вызова** от модульного метода `__init__.py` к импортированной функции. `fan_in` оставался нулевым.

**Исправление:** Добавлено отслеживание импортов на уровне модуля. При обработке `__all__` для каждого реэкспортируемого имени, которое является импортом, создаётся синтетическое ребро вызова.

### Ошибки 7–9: Разрешение вызовов — TYPE_DECL против METHOD

Три связанные ошибки в алгоритме разрешения вызовов:

```python
# src/mcp/server.py
from .tools.hotspots import register_hotspot_tools
register_hotspot_tools(server)  # ← вызов не находил целевую функцию
```

Когда Python импортирует функцию (`from X import Y`), парсер создаёт два узла: `TYPE_DECL` (объявление импорта) в файле-импортёре и `METHOD` (реальная функция) в файле-источнике. Алгоритм находил `TYPE_DECL` первым и останавливался.

Три исправления:

1. **Индекс полных имён предпочитает METHOD.** При загрузке индекса `METHOD` перезаписывает `TYPE_DECL` с тем же полным квалифицированным именем.

2. **Отложенный запасной вариант.** Если точное совпадение указывает на `TYPE_DECL`, сохраняем как запасной вариант и пробуем стратегии, предпочитающие `METHOD`.

3. **Преобразование пунктирных путей.** Импорты создают полное имя через точки: `src.mcp.tools.hotspots.register_hotspot_tools`. Стратегия разрешения по файловому пути ожидала формат с косыми чертами: `src/mcp/tools/hotspots.register_hotspot_tools`. Добавлено автоматическое преобразование между форматами.

## 4. Восстановление типов: ключ к точному графу вызовов

### Почему типы важны для обнаружения мёртвого кода

Точность обнаружения мёртвого кода напрямую зависит от полноты графа вызовов. А полнота графа вызовов зависит от **разрешения типов** — способности определить, какую именно функцию вызывает выражение `self.service.execute()`.

В статически типизированных языках компилятор знает тип каждой переменной. В Python типы нужно **восстанавливать** из контекста — и это одна из самых сложных задач статического анализа.

### Трёхитерационный адаптивный алгоритм

CodeGraph использует итерационный алгоритм, вдохновлённый подходом Joern, но расширенный механизмом сходимости и заглушками возвращаемых типов:

**Итерация 0 — внутрипроцедурный анализ:**
```python
config = UnifiedConfig()         # → config: UnifiedConfig (вызов конструктора)
db = DuckDBClient(path)          # → db: DuckDBClient (вызов конструктора)
self.service = CPGQueryService() # → self.service: CPGQueryService (поле объекта)
def process(data: str) -> int:   # → data: str, return: int (аннотации)
```

Источники: вызовы конструкторов, аннотации, присваивания `self.field`, проверки `isinstance`, база знаний типов стандартной библиотеки.

**Итерация 1 — межпроцедурное распространение:**
```python
result = analyzer.analyze(query)  # → тип result = тип возврата analyze()
client = create_client()          # → тип client = тип возврата create_client()
```

Для неразрешённых вызовов создаются заглушки: `CPGQueryService.execute.<returnValue>`. Даже без точного типа возврата это несёт семантику — имя вызываемого метода — и позволяет распространять частичную информацию дальше.

**Итерация 2+ — сходимость:**
Повторяем, пока прирост новых типов не упадёт ниже 1% от предыдущей итерации. На практике 2–3 итераций достаточно.

### Распространение квалифицированных имён вызовов

Отдельный проход, выполняющийся **после** восстановления типов и **до** построения графа вызовов, переписывает полные имена:

```
До:    self.cpg.execute_query() → "cpg.execute_query:ANY(ANY)"
После: self.cpg.execute_query() → "CPGQueryService.execute_query:ANY(ANY)"
```

Алгоритм поддерживает цепочки полей:
```python
self.config.db.connection.execute()
# UnifiedConfig → db: DatabaseConfig → connection: Connection → execute()
```

Это критически важно для этапа 4 нашей хроники: без квалифицированных имён алгоритм построения графа вызовов не может отличить `config.get()` одного класса от `config.get()` другого.

## 5. Чем подход CodeGraph отличается от Joern

[Joern](https://joern.io) — эталонная реализация CPG-анализа, на которую мы ориентировались при проектировании. Вот ключевые архитектурные решения, в которых мы пошли другим путём.

### Нулевой SQL в аналитических проходах

В Joern проходы могут обращаться к базе данных. В CodeGraph это **архитектурно запрещено**: каждый проход читает из графа в оперативной памяти и пишет в дельта-граф. Запрет проверяется автоматическим тестом, который сканирует исходный код всех проходов на наличие SQL-запросов.

Зачем: дельта-граф каждого прохода применяется к графу в памяти мгновенно (микросекунды), а запись в DuckDB происходит асинхронно в фоне. Если бы проходы читали из базы, они бы не видели данных от предшествующих проходов — и пришлось бы ждать завершения записи.

Результат: проходы выполняются параллельно в виде направленного ациклического графа (DAG) зависимостей, зависимые проходы разблокируются сразу после применения дельты, без ожидания ввода-вывода.

### Конфигурируемая семантика потоков данных

Joern описывает семантику стандартных библиотек (какие аргументы куда текут) в коде на Scala. CodeGraph использует YAML-конфигурации:

```yaml
function: "strcpy"
from_args: [1]           # Данные текут из аргумента 1
to_args: [0]             # Данные текут в аргумент 0
to_return: false
is_sink: true
sink_type: "buffer_overflow"
global_writes: ["errno"]  # Побочный эффект на глобальную переменную
```

567 таких отображений для 9 языков. Чтобы добавить новую функцию — достаточно строки в YAML, без перекомпиляции.

### Исправленные ошибки Joern

В процессе работы мы обнаружили и исправили три ошибки, которые в Joern фигурируют как открытые задачи:

**#5374 — пропущенные определения переменных в графе программных зависимостей (PDG).** Этот граф не содержал рёбер достигающих определений для объявлений переменных.

**#5693 — ложные зависимости по данным в логическом И.** Выражение `if (a && b)` создавало ложное ребро `b → a`.

**#5581 — пропущенные побочные эффекты на глобальные переменные.** Функция `strtol` модифицирует `errno`, но межпроцедурный анализ этого не учитывал. В CodeGraph побочные эффекты описаны через `global_writes`/`global_reads` в YAML-семантике.

### Инкрементальное обновление графа

Joern при каждом изменении кода перестраивает граф **с нуля**. На крупных проектах это минуты ожидания — и повод не запускать анализ после каждого коммита.

CodeGraph работает **инкрементально**: при повторном запуске парсер вычисляет разницу через `git diff`, обрабатывает только изменённые файлы и обновляет затронутые узлы и рёбра в существующей базе. Поддерживается отслеживание веток и слияний. Есть режим наблюдения за файловой системой (`watch`) с обновлением графа в реальном времени при сохранении файла.

На практике это означает, что после первичной индексации (85 секунд для нашей кодовой базы из 1 183 файлов) последующие обновления занимают **секунды**, а не минуты.

### Поддержка 1С:Предприятие

Отдельная тема, заслуживающая собственной статьи: CodeGraph — единственный инструмент CPG-анализа, поддерживающий язык **1С:Предприятие** (BSL). Joern не поддерживает 1С; открытых аналогов мы не нашли.

Для российского рынка, где 1С — де-факто стандарт автоматизации бизнес-процессов, это означает возможность применять полноценный анализ потоков данных, поиск уязвимостей и обнаружение мёртвого кода к кодовым базам, которые раньше были недоступны для CPG-инструментов. Подробный разбор — в следующей статье.

## 6. Архитектура обнаружения мёртвого кода

### Конвейер из 31 прохода

CodeGraph строит граф свойств кода через конвейер из 31 аналитического прохода:

```
Фаза 1: Метаданные → Файлы → Пространства имён
Фаза 2: Типы → Наследование → Связи параметров
Фаза 2.5: Восстановление типов (3 адаптивных итерации)
Фаза 3: Граф потока управления → Доминаторы → Зависимости по управлению
Фаза 3.5: Разрешение импортов
Фаза 3.75: Распространение имён вызовов (Joern-стиль)
Фаза 4: Граф вызовов → Разрешение вызовов
Фаза 4.5: Межъязыковые вызовы (CGO, ctypes, cffi)
Фаза 5: Потоки данных → Анализ псевдонимов → Достигающие определения
Фаза 5b: Межпроцедурный анализ (семантика stdlib + глобальные побочные эффекты)
Фаза 6: Распространение типов → Распространение типов возврата
Фаза 7: Граф программных зависимостей → Зависимости по данным
Фаза 8: Связывание → Виртуальные таблицы
Фаза 9: Метрики методов → Связи комментариев → Вложенность
```

Для обнаружения мёртвого кода критичны фазы 2.5 (восстановление типов), 3.5 (импорты), 3.75 (квалифицированные имена) и 4 (граф вызовов). Именно в этих фазах были сосредоточены наши исправления.

### Пятиуровневая фильтрация ложных срабатываний

Итоговый SQL-запрос использует каскад фильтров:

| Уровень | Фильтр | Что отсекает | Вклад |
|---------|--------|-------------|-------|
| V25 | Точки входа (`is_entry_point`) | Обработчики маршрутов, CLI, обратные вызовы | ~2 000 |
| V26 | Классовая достижимость | Методы в классах с вызываемыми конструкторами | ~50 |
| V27 | Вложенные функции (`is_nested`) | Замыкания и внутренние функции | **~400** |
| V28 | Полностью мёртвые модули | Модули, где все функции имеют fan_in = 0 | ~150 |
| V29 | Низкая жизнеспособность | Модули с 5+ методами и <40% живых | ~50 |

### Восемь стратегий обнаружения точек входа

Флаг `is_entry_point` расставляется парсером по восьми стратегиям:

1. **По декораторам** — `@app.get`, `@router.post`, `@celery.task`, `@click.command`, `@server.tool`
2. **По именам функций** — `*_workflow`, `is_*_query`, `format_*`, `enrich_*`, `run_*_command`
3. **По путям файлов** — `conftest.py`, `dependencies.py`, `domains/`, `cli/`
4. **По таблицам диспетчеризации** — `{"scenario_02": security_workflow}` → синтетическое ребро
5. **По экспортам `__all__`** — перечисленные функции помечаются как точки входа
6. **По обратным вызовам фреймворков** — `Depends(func)`, `Field(default_factory=func)`, `add_task(func)`
7. **По миграциям** — `upgrade()`, `downgrade()` в файлах Alembic
8. **По жизненному циклу** — `setUp`, `tearDown`, `__enter__`, `__exit__`

### Урок 1: 5 800 тестов не заменяют один запуск на реальном коде

У нас было более 5 800 тестов. Все проходили. Но ни один не тестировал «списковое включение внутри аргумента функции, содержащее вызов в условии `if`». Такие комбинации создаются не по учебнику — они появляются сами в живом коде.

### Урок 2: Каждое ложное срабатывание — бесплатная диагностика

Когда инструмент говорит «функция мёртвая», а вы знаете, что она вызывается — это **бесценная** информация. Это значит, что граф вызовов неполон. Не добавляйте функцию в список исключений — ищите корневую причину. Последние 50 ложных срабатываний привели нас к 9 ошибкам парсера, которые улучшили точность для **всех** проектов.

### Урок 3: Уровни фильтрации — не роскошь, а необходимость

Без фильтров V25–V29 даже идеальный граф вызовов покажет тысячи ложных срабатываний. Точки входа фреймворков, замыкания, модули с динамической диспетчеризацией — всё это невозможно устранить на уровне парсера. Нужна **многоуровневая** система с чёткой семантикой каждого уровня.

### Урок 4: Фантомы в базе данных

Инкрементальное обновление не удаляет узлы удалённых функций. После удаления кода **всегда** пересобирайте базу с нуля: `rm database.duckdb && gocpg parse ...`

### Урок 5: TYPE_DECL — ловушка для графа вызовов

Когда Python импортирует функцию, парсер создаёт `TYPE_DECL` в файле-импортёре. Если индекс не различает `TYPE_DECL` и `METHOD`, вызовы начинают указывать на объявления импортов вместо реальных функций — и цепочки вызовов разрываются. Это самая коварная ошибка из всех девяти.

## Заключение

35 847 методов с fan-in = 0 из 41 034 — восемьдесят семь процентов. Первый самоаудит выглядел как приговор. Но это оказалось не приговором, а **техническим заданием**: системный список всего, что инструмент не умеет.

Путь от 9 775 до 0 — это не история про удаление мёртвого кода. Это история про то, как **один метод тестирования** — использование инструмента на самом себе — обнаружил больше ошибок, чем 5 800 юнит-тестов.

Девять ошибок парсера затрагивали не экзотические конструкции, а повседневный Python: списковые включения, f-строки, `await`, условные выражения, реэкспорт через `__init__.py`. Это конструкции, которые есть в любой кодовой базе. Без догфуддинга они продолжали бы незаметно занижать полноту графа вызовов.

Числа 9 775 → 5 000 → 3 500 → 2 500 → 600 → 340 → 50 → 0 — это не теоретические расчёты. Это реальные замеры на реальном проекте, каждый из которых стоил конкретного исправления в конкретном файле.

44 удалённые функции и 1 800 строк мёртвого кода — приятный побочный эффект. Настоящая ценность — в 9 исправлениях парсера и 5 уровнях фильтрации, которые теперь работают для **каждого** проекта, анализируемого CodeGraph.
