## Хук

> Постобработка занимала больше времени, чем сам анализ. Каждый запуск парсера заканчивался Python-скриптом, который выполнял DROP TABLE, ALTER TABLE и пересоздавал 733 тысячи строк с нуля. Блокировки на файле базы, 100% загрузка диска, ни одного инкрементального обновления.

Это был февраль 2025 года. CodeGraph уже имел работающий конвейер анализа: 21 аналитический сценарий, гибридный поиск по векторной и графовой базам, интеграция с языковыми моделями. Для построения графа свойств кода мы использовали [Joern](https://joern.io) — эталонную реализацию CPG-анализа, созданную в университете Падерборна.

Joern делал своё дело. И всё же через полгода использования мы выбросили его и написали собственный парсер с нуля — на Go, с tree-sitter, с записью в DuckDB. 31 аналитический проход. 11 языков. Поддержка 1С:Предприятие, которой нет ни у одного открытого CPG-инструмента.

В этой статье — почему Joern нас не устроил, как идеи ast-grep повлияли на архитектуру и что мы получили в результате.

## 1. Что нас не устроило в Joern

### Проблема 1: виртуальная машина Java как обязательная зависимость

Joern написан на Scala и работает поверх JVM (Java Virtual Machine). Для наших задач это означало:

- **Развёртывание**: вместо одного исполняемого файла — Java-среда, загрузка пакетов, настройка heap-памяти
- **Время запуска**: холодный старт JVM добавлял секунды ещё до начала парсинга
- **Контейнеризация**: Docker-образ с JVM весит сотни мегабайт; Go-бинарник — десятки

Для инструмента, который должен запускаться при каждом коммите и встраиваться в CI/CD, это существенная разница.

### Проблема 2: Проприетарный формат хранения

Joern хранит граф в flatgraph — собственном бинарном формате с API на Scala. Чтобы задать вопрос графу, нужно либо писать на Joern-специфичном диалекте Scala (CPGQL), либо экспортировать данные в другой формат.

Мы хотели **SQL**. Наш Python-бэкенд, аналитические сценарии, API — всё работает с DuckDB через стандартные SQL-запросы. Между Joern и нашим кодом стоял слой совместимости (`compatibility.py`), который после каждого запуска парсера выполнял:

```
DROP TABLE IF EXISTS call_containment;
CREATE TABLE call_containment AS SELECT ... — 733 000 строк
ALTER TABLE nodes_method ADD COLUMN embedding FLOAT[];
ALTER TABLE nodes_method ADD COLUMN ast_hash VARCHAR;
UPDATE nodes_method SET ast_hash = ... — ещё 40 000 строк
```

Блокировки файла базы данных, 100% загрузка диска, невозможность параллельного доступа. На нашей кодовой базе (41 034 метода) этот этап постобработки занимал больше времени, чем сам парсинг.

### Проблема 3: Отсутствие инкрементальных обновлений

Joern при каждом запуске строит граф **с нуля**. Изменили один файл — перестройте весь проект. На нашей Python-кодовой базе из 1 183 файлов полный проход Joern занимал около 100 секунд. Это терпимо раз в день, но неприемлемо при каждом коммите или в режиме реального времени.

### Проблема 4: Неполный граф для Python

Когда мы сравнили выходные данные Joern и нашего парсера на одной и той же кодовой базе (996 Python-файлов `src/`), обнаружились системные пробелы:

| Что пропущено | Joern | GoCPG |
|---------------|-------|-------|
| Комментарии | **0 узлов** | 24 092 |
| Узлы импортов | **0 узлов** | 10 468 |
| Аннотации (декораторы) | **0 узлов** | 1 451 |

Joern (`pysrc2cpg`) **не извлекает комментарии** — а они нужны нам для сценариев документации, обнаружения TODO/FIXME и привязки документации к методам. Joern **не создаёт узлы импортов** — а без них невозможно точно разрешать вызовы через `from X import Y`. Joern **игнорирует декораторы** как аннотации — а в Python декоратор `@app.get("/users")` — это точка входа фреймворка, без которой функция попадает в ложные срабатывания обнаружения мёртвого кода.

### Проблема 5: Граф вызовов с 18-кратным завышением

У Joern для Python есть `NaiveCallLinker` — стратегия, которая связывает каждый вызов со **всеми** функциями с таким же именем. На нашей кодовой базе это дало 15,9 миллиона рёбер графа вызовов. Наш парсер, использующий каскад из 6 стратегий разрешения (от точного совпадения полного имени до поиска через карту импортов), дал 867 тысяч — **в 18 раз меньше** и значительно точнее.

Когда граф вызовов завышен в 18 раз, любой анализ поверх него — анализ потоков данных, обнаружение мёртвого кода, оценка связности — даёт искажённые результаты.

### Проблема 6: Только внутрипроцедурный анализ потоков данных

Joern выполняет анализ достигающих определений **внутри одной функции**. Вызовы других функций — чёрный ящик. Поток `request.sql → run_query(sql) → conn.execute(sql)` через три файла Joern не отслеживает.

Мы хотели **межпроцедурный анализ**: если функция `strtol` записывает в глобальную переменную `errno`, а вызывающий код читает `errno` после вызова — это зависимость по данным, и граф должен её отражать.

## 2. Решение: собственный парсер на Go + tree-sitter + DuckDB

27 января 2026 года мы начали GoCPG — собственный генератор графа свойств кода. Архитектурные решения были продиктованы конкретными проблемами Joern.

### Почему Go

| Проблема Joern | Решение GoCPG |
|----------------|---------------|
| JVM-зависимость | Один нативный бинарник, 0 зависимостей при запуске |
| Медленный старт | Мгновенный запуск нативного процесса |
| Последовательные проходы | Горутины + параллельный конвейер на основе графа зависимостей |
| Сложная контейнеризация | Статически слинкованный бинарник, образ ~50 МБ |

### Почему tree-sitter

Для разбора исходного кода нам нужен был единый фундамент, работающий для всех языков. [Tree-sitter](https://tree-sitter.github.io/tree-sitter/) — библиотека инкрементального разбора, разработанная в GitHub (теперь — часть экосистемы Zed). Ключевые свойства:

- **Конкретное синтаксическое дерево** (CST) — сохраняет всю информацию исходного кода, включая комментарии и пробелы. В отличие от абстрактного синтаксического дерева (AST), ничего не теряется — а значит, можно и анализировать, и точно переписывать код
- **Зрелые грамматики** для 30+ языков — поддерживаются сообществом, обновляются регулярно
- **Единый интерфейс** — один и тот же код обхода дерева работает для Python, Java, C++
- **Скорость** — нативная C-библиотека, интеграция с Go через CGO (механизм вызова C-кода из Go)

Для 10 из 11 поддерживаемых языков (C, C++, Python, JavaScript, TypeScript, Java, Kotlin, C#, PHP, 1С) мы используем tree-sitter. Для Go — собственный парсер `go/parser` из стандартной библиотеки, который даёт полную информацию о типах бесплатно.

### Почему DuckDB

Вместо проприетарного формата — **колоночная аналитическая СУБД** с полноценным SQL:

- Python-бэкенд читает граф стандартными SQL-запросами — без промежуточных слоёв и постобработки
- Колоночное хранилище оптимально для аналитических запросов по миллионам рёбер
- DuckDB поддерживает расширение DuckPGQ для графовых запросов — рекурсивные обходы, поиск путей, определение связных компонентов

Результат: после команды `gocpg parse` база данных **полностью готова к использованию**. Никаких `DROP TABLE`, `ALTER TABLE`, `UPDATE ... SET`. Слой совместимости (`compatibility.py`) удалён.

## 3. Как ast-grep повлиял на архитектуру

[ast-grep](https://ast-grep.github.io/) — инструмент структурного поиска по коду, созданный Herrington Darkholme. Написан на Rust, использует tree-sitter для разбора. Ключевая идея: **искать код по структуре, а не по тексту**.

Вместо регулярных выражений — шаблоны, которые понимают синтаксис:

```yaml
# ast-grep: найти все вызовы strcpy с любыми аргументами
pattern: "strcpy($DST, $SRC)"
```

Где `$DST` и `$SRC` — **метапеременные**, которые захватывают любой узел синтаксического дерева. Это не текстовая подстановка — это сопоставление деревьев.

### Что мы взяли у ast-grep

| Идея | Реализация в GoCPG |
|------|---------------------|
| Метапеременные `$VAR`, `$$$VARS`, `$_` | Захват одного узла, последовательности узлов, произвольного узла |
| Составные правила `all`, `any`, `not` | Логические комбинации шаблонов |
| Структурные отношения `inside`, `has`, `follows` | Поиск с учётом вложенности и порядка |
| Формат правил в YAML | Декларативные, версионируемые, расширяемые |
| Шаблоны исправлений `fix:` | Подстановка метапеременных в шаблон замены |
| Оптимизация `potential_kinds` | Предвычисленный набор типов узлов для пропуска за O(1) |

### Где GoCPG идёт дальше

ast-grep работает с **одним файлом**. Он видит синтаксическое дерево, но не знает, откуда пришли данные, кто вызывает функцию и какого типа переменная. GoCPG расширяет структурный поиск **ограничениями на уровне графа свойств кода**:

```yaml
id: py-format-sql
pattern: '$CONN.execute(f"$SQL")'
cpg:
  dataflow:
    from: "$SQL"
    to: "$CONN.execute"
  metrics:
    not_test_file: true
fix: '$CONN.execute("$SQL", params)'
```

Секция `cpg:` — это то, чего нет ни у ast-grep, ни у Semgrep, ни у любого другого инструмента поиска по шаблонам. Шаблон сработает, **только** если анализ потоков данных подтверждает, что `$SQL` содержит внешние данные. На захардкоженных запросах — молчание.

| Возможность | ast-grep | GoCPG |
|-------------|----------|-------|
| Потоки данных | Нет | Достигающие определения, граф зависимостей |
| Граф вызовов | Нет | Полный проект, межфайловый |
| Информация о типах | Нет | Восстановление типов, наследование |
| Межфайловый анализ | Нет | Весь проект в DuckDB |
| Анализ заражённых данных | Нет | Межпроцедурное распространение |
| Инкрементальность | Нет | Отслеживание по `git diff` + хеш дерева |

Мы спроектировали систему как **строго более мощное надмножество** ast-grep: существующие YAML-правила ast-grep работают с минимальной адаптацией, а секция `cpg:` добавляет возможности, принципиально невозможные на уровне синтаксического дерева.

## 4. Архитектура конвейера: 31 проход, 0 SQL

### Принцип «нулевого SQL в проходах»

В Joern аналитические проходы могут обращаться к базе данных. Мы запретили это **на уровне архитектуры**: каждый проход читает из графа в оперативной памяти (`CPGGraph`) и записывает результаты в дельта-граф (`DiffGraph`). Запрет проверяется автоматическим тестом, который сканирует исходный код всех проходов на наличие SQL-строк.

Зачем: если проход читает из базы, он не видит результатов предыдущих проходов — те ещё не записаны. Пришлось бы ждать сброса данных на диск после каждого прохода. Вместо этого:

```
Проход A записывает в DiffGraph →
  DiffGraph применяется к CPGGraph в памяти (микросекунды) →
    Проход B видит данные A мгновенно
    ‖ Запись в DuckDB идёт асинхронно в фоне
```

### Параллельный конвейер на основе графа зависимостей

31 проход организован в направленный ациклический граф зависимостей. Каждый проход запускается в отдельной горутине, как только все его зависимости завершены. На практике до 8 проходов выполняются одновременно.

```
Фаза 1: Метаданные → Файлы → Пространства имён
Фаза 2: Типы → Наследование → Восстановление типов (3 адаптивных итерации)
Фаза 3: Граф потока управления → Доминаторы → Зависимости по управлению
Фаза 3.5: Разрешение импортов → Распространение имён вызовов
Фаза 4: Граф вызовов → Разрешение вызовов → Межъязыковые вызовы
Фаза 5: Потоки данных → Анализ псевдонимов → Достигающие определения
Фаза 5b: Межпроцедурный анализ (семантика stdlib + глобальные побочные эффекты)
Фаза 6: Распространение типов → Граф программных зависимостей
Фаза 7: Связывание → Виртуальные таблицы
Фаза 8: Метрики → Структурный поиск шаблонов → Находки
```

Для записи в DuckDB используются два режима: транзакционный `INSERT` для малых пакетов и потоковый `Appender API` для больших — последний в 30–60 раз быстрее на пакетах свыше 5 000 узлов.

### Инкрементальные обновления через git

При повторном запуске GoCPG не перестраивает граф с нуля. Алгоритм:

1. Читает `cpg_git_state` — таблицу с хешами коммитов и состоянием веток
2. Вычисляет `git diff` между последним проанализированным коммитом и текущим
3. Обрабатывает только изменённые файлы: удаляет старые узлы и рёбра, создаёт новые
4. Перезапускает затронутые проходы (потоки данных, граф вызовов)

Результат: первичная индексация нашей кодовой базы (1 183 файла) занимает 85 секунд. Последующие обновления после одного-двух изменённых файлов — **секунды**.

Есть режим наблюдения (`watch`): GoCPG следит за файловой системой и обновляет граф при каждом сохранении файла. Для разработчика в IDE — граф всегда актуален.

## 5. Поддержка 11 языков: от C до 1С

### Единый интерфейс фронтенда

Каждый язык реализует одинаковый интерфейс: разбор файла → обход дерева (`walkNode`) → создание узлов и рёбер графа. Для 10 языков это tree-sitter + рекурсивный экстрактор. Для Go — стандартный `go/parser` с полной информацией о типах.

```
pkg/frontend/
├── c/          — tree-sitter, compile_commands.json
├── cpp/        — tree-sitter, шаблоны, пространства имён
├── go/         — go/parser (полное разрешение типов)
├── python/     — tree-sitter, декораторы, таблицы диспетчеризации
├── javascript/ — tree-sitter, JSDoc, обратные вызовы
├── typescript/ — tree-sitter, обобщённые типы, аннотации
├── java/       — tree-sitter, аннотации, обобщённые типы
├── kotlin/     — tree-sitter + нестандартные привязки
├── csharp/     — tree-sitter + нестандартные привязки
├── php/        — tree-sitter, пространства имён, трейты
└── onec/       — собственный лексер/парсер (русские ключевые слова)
```

### Нестандартные привязки tree-sitter

Три языка — Kotlin, C# и 1С — используют локально встроенные исходники tree-sitter с прямыми объявлениями функций (forward declarations) вместо `#include "parser.c"`. Причина: Go компилирует C-файлы независимо для каждого пакета, и два пакета не могут подключить один и тот же `parser.c` — возникнет ошибка дублирования символов.

Это нетривиальная инженерная задача, которая стоила нам нескольких дней отладки на macOS, где линкер строже, чем на Linux.

### 1С:Предприятие — язык без открытых CPG-инструментов

Для 1С мы написали **собственный лексер и парсер** — не существует зрелой грамматики tree-sitter для языка с русскими ключевыми словами (`Если`, `Тогда`, `КонецЕсли`, `Функция`, `Процедура`).

Реализация: `pkg/frontend/onec/` — 8 файлов на Go:
- Двуязычная поддержка (русские и английские ключевые слова)
- 152 встроенных заглушки типов стандартной платформы
- Полная интеграция с семантическим анализом (проходы восстановления типов, граф вызовов, потоки данных)

На российском рынке, где 1С — де-факто стандарт автоматизации бизнес-процессов, это означает возможность впервые применить полноценный CPG-анализ к кодовым базам, которые раньше были доступны только для текстового поиска.

## 6. Хроника: от первого коммита до паритета с Joern

### Январь 2026: фундамент

**27 января** — первый коммит: `feat: add GoCPG — high-performance Go CPG generator`. Начальный набор: 11 языков, tree-sitter-фронтенды, запись в DuckDB, базовый конвейер проходов.

**31 января** — три ключевых релиза за один день:
- Достигнут 95% паритет с Joern для C++ (шаблоны, пространства имён, классы)
- Достигнут 95% паритет для 1С:Предприятие (собственный лексер/парсер)
- Паритет для Java и Kotlin

### Февраль 2026: паритет и оптимизация

**2 февраля** — начало работы над JavaScript/TypeScript: паритет вырос с 30% до 73%.

**4 февраля** — ускорение парсинга Python в **36 раз**: с 1 489 секунд до 41 секунды на 959 файлах. Основная причина: переход от транзакционных `INSERT` к потоковому `Appender API` для DuckDB.

**7 февраля** — `Joern parity v5`: 100% совпадение на тестируемых метриках. Все 13 выявленных расхождений закрыты.

**18 февраля** — исправление ошибки дублирования символов tree-sitter на macOS. Решение: прямые объявления функций вместо включения исходников.

**21 февраля** — удаление всего наследия Joern: 3 900 строк — Scala-парсер, валидатор CPGQL, экспортные скрипты, слой совместимости.

**23 февраля** — реализация `CallFQNPropagationPass` (распространение квалифицированных имён вызовов в стиле Joern) и `DynamicCallLinkerPass` (виртуальная диспетчеризация + связывание конструкторов).

### Март 2026: догфуддинг

## 8. Выученные уроки

### Урок 1: Не расширяй — замени

Мы потратили месяцы на обёртки вокруг Joern: слой совместимости, экспортные скрипты, конвертеры. Каждый из них решал одну проблему и создавал две новых. Фундаментальные ограничения (JVM, проприетарный формат, отсутствие инкрементальности) не решаются обёрткой.

Когда ваш инструмент требует 733 000 строк постобработки после каждого запуска — это не инструмент, который нуждается в доработке. Это фундамент, который нуждается в замене.

### Урок 2: Пиши на языке развёртывания

Go был выбран не из эстетических предпочтений. Один статически слинкованный бинарник без зависимостей — это конкретное преимущество при развёртывании в изолированных средах, в Docker-контейнерах и в CI/CD-конвейерах. Горутины — конкретное преимущество для параллельного конвейера проходов.

### Урок 3: tree-sitter + расширение лучше, чем с нуля

Мы не писали грамматики для 10 языков. Мы взяли зрелые, поддерживаемые сообществом грамматики tree-sitter и написали поверх них **экстракторы CPG**. Обновление грамматики C с v0.23.5 до v0.24.1 — это обновление зависимости, а не переписывание парсера.

Исключение — 1С:Предприятие. Когда зрелой грамматики нет, собственный лексер/парсер — единственный вариант.

### Урок 4: ast-grep показал путь, CPG расширил его

Идея «ищи код по структуре, а не по тексту» — мощная. ast-grep доказал, что YAML-правила с метапеременными — удобный и понятный формат. Но ast-grep работает с одним файлом и не знает о потоках данных.

Мы взяли синтаксис ast-grep как основу и расширили его секцией `cpg:` — ограничениями, которые используют полный граф свойств кода. Результат: 190 правил для 11 языков, 25 из которых содержат шаблоны автоматического исправления.

### Урок 5: Догфуддинг важнее паритета

Мы стремились к 100% паритету с Joern по числу узлов и рёбер. Это было полезно как инженерная дисциплина, но **настоящие** ошибки вскрылись не при сравнении цифр, а при использовании инструмента на самом себе. Девять ошибок парсера, которые мы нашли при догфуддинге (статья 3 этой серии), не обнаружил ни один тест паритета — потому что Joern допускал те же ошибки.

## Заключение

Joern — хороший инструмент. Без него не было бы концепции CPG, на которой стоит вся наша архитектура. Мы не «уходили от Joern» — мы **переросли** его ограничения.

JVM, проприетарный формат хранения, отсутствие инкрементальности, неполный граф для Python, 18-кратно завышенный граф вызовов, только внутрипроцедурный анализ потоков данных — каждая из этих проблем по отдельности решаема обёрткой. Все вместе — нет.

GoCPG — это 31 аналитический проход с нулевым доступом к SQL, параллельный конвейер на основе графа зависимостей, запись в DuckDB без постобработки, инкрементальные обновления через git, 11 языков (включая 1С:Предприятие), 567 YAML-отображений семантики стандартных библиотек и 190 правил структурного поиска с ограничениями на уровне графа.

От первого коммита до полного паритета с Joern — 11 дней. От паритета до `dead_method_count = 0` на собственной кодовой базе — ещё 3 недели. Это не теоретические числа — это реальная хроника, задокументированная в истории коммитов.

Следующий шаг — подробный разбор поддержки 1С:Предприятие: как мы написали лексер для языка с русскими ключевыми словами и что CPG-анализ может дать экосистеме 1С.
