## Введение

> Клод написал 47 файлов за сессию. 1 892 строки. Два новых сценария, рефакторинг шести обработчиков, миграция конфига. 38 минут.
>
> Каждый коммит — автоматический CPG-анализ. Каждый промпт — обогащение контекстом из графа. Каждый пул-реквест — радиус поражения и оценка риска.
>
> Не потому что мы не доверяем ИИ. А потому что мы не доверяем **никакому** генератору кода без автоматической верификации. Включая себя.

Термин «вайбкодинг» придумал Андрей Карпати: пишешь промпт — получаешь код — принимаешь результат, не всегда вчитываясь. Модель — генератор. Разработчик — проверяющий. Если повезёт.

Проблема не в модели. Проблема в отсутствии конвейера верификации. Линтеры ловят синтаксис. Тесты ловят поведение. Но никто не ловит *структурную деградацию* — рост цикломатической сложности, расширение радиуса поражения, дрейф числовых утверждений в документации.

Мы в CodeGraph решили: если вайбкодинг неизбежен — его надо обвязать графом свойств кода. Не запретить ИИ — а сделать так, чтобы каждый артефакт, порождённый моделью, проходил через CPG-конвейер автоматически, без ручного запуска, в реальном времени.

Эта статья — подробное руководство, как мы это устроили. Пять хуков в ИИ-ассистенте, три git-хука, конвейер непрерывной интеграции, валидатор числовых утверждений и отслеживание тренда качества по коммитам. Всё на реальной кодовой базе CodeGraph (42 тыс. методов, 2 170 файлов, 11 языков).

## 1. Вайбкодинг — что это и почему пугает техлидов

### Масштаб

По данным GitHub (2025): Copilot генерирует 46% нового кода в репозиториях, где он включён. По нашим собственным замерам: в сессиях ИИ-ассистента на кодовой базе CodeGraph модель пишет 50–70% строк. Оставшиеся 30–50% — промпты, проверка, правки.

Это уже не эксперимент. Это основной режим работы.

### Проблема

Ручная проверка не масштабируется. Один техлид физически не может проверить 1 892 строки за 38 минут — а именно столько генерирует ИИ-ассистент за типичную сессию рефакторинга.

Три типичных провала вайбкодинга без контроля:

1. **Рост сложности**: модель дублирует логику вместо вынесения в общий метод. Цикломатическая сложность растёт, разветвлённость расширяется — и никто не замечает до следующего релиза.
2. **Каскадные поломки**: изменение в одном обработчике ломает 12 вызывающих. Модель не видит граф вызовов — видит только файл.
3. **Документационный дрейф**: модель добавляет сценарий 22 — а в документации по-прежнему «21 сценарий». В [статье 8](habr-08-meta-audit.md) мы нашли 14 таких расхождений за один вечер.

### Тезис

> Вайбкодинг без контроля = технический долг.
> Вайбкодинг с CPG-конвейером = скорость + качество.

Дальше — конкретная архитектура.

## 2. Конвейер — пять хуков, один граф

### Архитектура

ИИ-ассистент (в нашем случае — Claude Code) поддерживает пять типов хуков — точек вмешательства в жизненный цикл сессии. Каждый хук получает JSON на вход, возвращает JSON на выход. Если в ответе есть дополнительный контекст — он встраивается в диалог.

Мы используем все пять:

```
Сессия разработчика
    │
    ▼
[Старт сессии] ──► CPG-контекст: 42 тыс. методов, 2 170 файлов, ЦС 4.2
    │
    ▼
[Отправка промпта] ──► «рефакторинг CommitAnalyzer»
                       + CPG: определён в commit_analyzer.py:34,
                         ЦС=8, разветвлённость=5
    │
    ▼
[Перед инструментом: правка] ──► ⚠ analyze_commit: ЦС=15, 3 TODO
    │
    ▼
ИИ-ассистент пишет код
    │
    ▼
[После инструмента: git commit] ──►
    Фаза 1: проверка свежести CPG (2с)
    Фаза 2: инкрементальное обновление графа (3с)
    Фаза 3: анализ качества + радиус поражения (8с)
    ──► отчёт встраивается в диалог
    │
    ▼
[Завершение] ──► пост-анализ: упомянутые файлы, всплески сложности
    │
    ▼
[git push → пул-реквест] ──►
    CI/CD: SARIF-аннотации, метрики в комментарии к пул-реквесту
```

### Конфигурация

Все хуки описаны в `.claude/settings.json`:

```json
{
  "hooks": {
    "SessionStart": [{
      "hooks": [{
        "type": "command",
        "command": "python .claude/hooks/session_context.py",
        "timeout": 10000
      }]
    }],
    "UserPromptSubmit": [{
      "hooks": [{
        "type": "command",
        "command": "python .claude/hooks/enrich_prompt.py",
        "timeout": 15000
      }]
    }],
    "PreToolUse": [{
      "hooks": [{
        "type": "command",
        "command": "python .claude/hooks/pre_tool_use.py",
        "timeout": 8000
      }]
    }],
    "PostToolUse": [{
      "matcher": "Bash",
      "hooks": [{
        "type": "command",
        "command": "python .claude/hooks/commit_analysis.py",
        "timeout": 60000
      }]
    }],
    "Stop": [{
      "hooks": [{
        "type": "command",
        "command": "python .claude/hooks/post_analysis.py",
        "timeout": 10000
      }]
    }]
  }
}
```

Каждый хук — независимый Python-скрипт. Общая инфраструктура в `_utils.py`: чтение входных данных, вывод JSON, разрешение активного проекта из `config.yaml`, выполнение SQL через `gocpg query`.

Ключевой принцип: **хуки не блокируют генерацию**. Первые три добавляют контекст *до* того, как модель начнёт писать. Последние два анализируют *после*. Модель работает в полную силу — а конвейер страхует результат.

## 3. Глубокое погружение: анализ коммита

Главный хук — `commit_analysis.py`. Запускается после каждого `git commit` внутри ИИ-ассистента. Бюджет: 58 секунд (60с лимит минус 2с запас).

### Четыре фазы

| Фаза | Бюджет | Что делает |
|------|--------|------------|
| 1. Свежесть CPG | 2с | Сравнивает хеш коммита в `cpg_git_state` с текущим `HEAD` |
| 2. Обновление | 40с | Если CPG устарел — `gocpg update` инкрементально |
| 3. Качество | 8с | ЦС, разветвлённость, TODO/FIXME, отладочный код, устаревшие методы |
| 4. Радиус поражения | 8с | Кто вызывает изменённые методы? Какие интерфейсы затронуты? |

### Как это работает

```python
# Упрощённый поток (реальный код в src/dogfooding/commit_analyzer.py)

# Фаза 1: изменённые файлы
files = git_diff("HEAD~1", "HEAD")  # ["src/dogfooding/commit_analyzer.py", ...]

# Фаза 2: методы в этих файлах (из CPG)
methods = duckdb.execute("""
    SELECT full_name, cyclomatic_complexity, fan_in, fan_out,
           has_todo_fixme, has_debug_code, has_deprecated
    FROM nodes_method
    WHERE filename LIKE '%commit_analyzer.py%'
    ORDER BY cyclomatic_complexity DESC
""")

# Фаза 3: качество
high_cc = [m for m in methods if m.cc > 10]
blast    = duckdb.execute("""
    SELECT callee_full_name, containing_method_full_name
    FROM call_containment
    WHERE callee_full_name IN (...)
""")
```

### Что видит модель после коммита

```
## Отчёт анализа коммита
**Итого:** 4 файла, 12 методов, 1 метод с высокой сложностью,
           8 затронутых вызывающих
**Состояние CPG:** актуален

**Влияние изменений:**
- `CommitAnalyzer.analyze_commit`: ЦС 8→12 (+4)
- `format_report_markdown`: разветвлённость 5→3 (-2)

**Методы с высокой сложностью:**
- `analyze_blast_radius` (ЦС: 14)

**Радиус поражения:** 8 вызывающих затронуто
- `analyze_commit` вызывается из: `_run_analyze`, `_run_report`,
  `commit_analysis.run_with_duckdb`

*Анализ завершён за 1 340 мс*
```

Модель *видит* этот отчёт и учитывает его в следующем ответе. Если сложность выросла — модель знает. Если радиус поражения широкий — модель предупредит. Без дополнительных промптов от человека.

### Дельты: до и после

Особенно полезна таблица дельт: метрики *до* коммита в сравнении с метриками *после*. Реализация в `_compute_deltas()`: перед обновлением CPG сохраняем текущие метрики изменённых методов, после обновления — сравниваем.

```
ЦС 8→12 (+4)     — усложнение, обратить внимание
Развет. 5→3 (-2)  — упрощение, хорошо
```

## 4. Обогащение промпта — контекст ДО генерации

Пост-анализ ловит проблемы *после*. Обогащение промпта предотвращает их *до*.

### Как работает обогащение

1. Пользователь пишет: «рефакторинг CommitAnalyzer»
2. Хук извлекает сущности из текста: `CommitAnalyzer` (CamelCase), `commit_analyzer` (если есть snake_case)
3. Для каждой сущности — SQL-запрос к CPG:

```sql
SELECT full_name, filename, cyclomatic_complexity, fan_in, fan_out
FROM nodes_method
WHERE full_name LIKE '%CommitAnalyzer%'
ORDER BY cyclomatic_complexity DESC
LIMIT 5
```

4. Результат встраивается в контекст:

```
Контекст CPG для CommitAnalyzer:
- src/dogfooding/commit_analyzer.py:34  — CommitAnalyzer.__init__ (ЦС: 1)
- src/dogfooding/commit_analyzer.py:55  — CommitAnalyzer.get_changed_files (ЦС: 3)
- src/dogfooding/commit_analyzer.py:324 — CommitAnalyzer.analyze_commit (ЦС: 8)
```

### Дополнительно: проверка видимости через интерфейсы

С версии v3 конвейера хук `enrich_prompt.py` обогащает контекст информацией о том, через какие интерфейсы доступен редактируемый код:

```
Внешняя видимость CommitAnalyzer:
- CLI: `dogfood analyze` → _run_analyze → CommitAnalyzer.analyze_commit
- REST API: нет (внутренний модуль)
```

Если метод вызывается из REST API — модель увидит это *до* начала генерации и будет осторожнее с обратной совместимостью.

### Без контекста и с контекстом

**Без CPG** (наивный вайбкодинг):
- Промпт: «рефакторинг CommitAnalyzer»
- Модель: ищет файл, читает, предлагает изменения. Не знает: кто вызывает `analyze_commit`? какова сложность? есть ли TODO?

**С CPG**:
- Промпт: то же самое
- Контекст: ЦС=8, разветвлённость=5, 3 TODO/FIXME, 8 прямых вызывающих
- Модель: *знает* структуру до начала генерации. Предлагает изменения с учётом радиуса поражения.

Бюджет: 10с (3с на сущность, максимум 3 сущности). Реальное время: 1–3с.

## 5. Git-хуки — фоновое обновление CPG

### Проблема

CPG устаревает после каждого коммита. Если при коммите №N парсер нашёл 42 000 методов, а коммит №N+1 добавил новый файл — CPG больше не актуален. Анализ на устаревшем CPG даёт неточные результаты.

### Решение: gocpg hooks install

```bash
$ gocpg hooks install --repo=. --db=data/projects/codegraph.duckdb
✓ Установлен хук post-commit
✓ Установлен хук post-merge
✓ Установлен хук post-checkout
```

Три git-хука, одна задача: после каждого коммита, слияния и переключения ветки — запуск `gocpg update` в фоновом режиме. Разработчик не ждёт.

### Тайминги

| Операция | Время |
|----------|-------|
| Полный парсинг (42 тыс. методов) | ~85с |
| Инкрементальное обновление (1–5 файлов) | 2–5с |
| Инкрементальное обновление (10–20 файлов) | 5–12с |

Инкрементальный режим определяется автоматически: если в БД есть таблица `cpg_git_state` с записями — GoCPG парсит только изменённые файлы (`git diff --name-only`). Если БД не существует — полный парсинг.

### Асинхронный режим

Конфигурация в `config.yaml`:

```yaml
gocpg:
  hooks:
    hook_types: "post-commit,post-merge,post-checkout"
    async_hooks: true
```

`async_hooks: true` — хук запускает `gocpg update` в фоне. Разработчик продолжает работу. К моменту следующего коммита CPG, как правило, уже обновлён.

## 6. Непрерывная интеграция — верификация пул-реквестов

### Конвейер gocpg-analysis.yml

Всё, что работает локально, воспроизводится в CI. Конвейер `.github/workflows/gocpg-analysis.yml` запускается на каждый пул-реквест:

```yaml
# Упрощённая структура
jobs:
  analyze:
    steps:
      - name: Сборка GoCPG
        run: CGO_ENABLED=1 go build -o gocpg ./cmd/gocpg

      - name: Восстановление кешированного CPG
        uses: actions/cache@v4
        with:
          key: cpg-${{ github.base_ref }}-${{ hashFiles('src/**') }}

      - name: Инкрементальное обновление CPG
        run: ./gocpg ci-update --base-ref origin/${{ github.base_ref }}

      - name: Публикация метрик в комментарий к пул-реквесту
        # файлов_изменено, узлов_добавлено, время_мс, попадание_в_кеш

  security-review:
    needs: analyze
    steps:
      - name: Анализ безопасности
        run: python -m src.cli exec --db $DB --base-ref ...
              --sarif-file out.sarif --comment-file comment.md

      - name: Загрузка SARIF
        uses: github/codeql-action/upload-sarif@v3
```

### Кеширование

Ключ кеша: `cpg-{базовая_ветка}-{хеш_исходников}`. При повторных пушах в тот же пул-реквест — CPG обновляется инкрементально, экономя 80–90% времени парсинга.

### Что видит рецензент пул-реквеста

1. **Комментарий с метриками**: файлов изменено, узлов добавлено, время обновления, попадание в кеш
2. **SARIF-аннотации**: уязвимости безопасности прямо в диффе, кликабельные маркеры рядом с проблемными строками
3. **Радиус поражения**: какие модули затронуты изменениями

Рецензент не анализирует 47 файлов вручную. Он смотрит на CPG-метрики и SARIF-маркеры.

## 7. Недостающий кусок — валидация числовых утверждений

### Обещание из статьи 8

В [статье 8](habr-08-meta-audit.md) мы нашли 14 расхождений между документацией и кодом. «120+ типов CWE» — а в базе 58. «90+ обработчиков» — а в коде 97. Мы починили числа вручную и пообещали: «в следующей статье — автоматический предкоммитный хук».

Обещание выполнено.

### Валидатор утверждений

Ядро решения — `src/dogfooding/claims_validator.py`. Принцип: маркдаун-файлы содержат утверждения вида «42 обработчика» или «95+ правил». Валидатор извлекает число и ключевое слово, сопоставляет ключевое слово с SQL-запросом к CPG и сравнивает.

```python
# Извлечение: регулярное выражение находит "число [+] ключевое_слово"
# "95 обработчиков" → заявлено=95, слово="обработчиков", допуск=нет
# "90+ scenarios"   → заявлено=90, слово="scenarios",    допуск=да

# Сопоставление слово → SQL (из config.yaml, не хардкод):
rules:
  - keywords: ["handlers", "обработчиков", "обработчики"]
    sql: "SELECT COUNT(DISTINCT full_name) FROM nodes_method
          WHERE full_name LIKE '%Handler%handle%'"
  - keywords: ["scenarios", "сценариев", "сценарии"]
    sql: "SELECT COUNT(DISTINCT ...) FROM nodes_method
          WHERE full_name LIKE '%scenario%' AND full_name LIKE '%handle%'"
```

Двуязычные ключевые слова (русские + английские). Толерантность: «90+» считается корректным, если фактическое значение >= 90.

### Демонстрация

```bash
$ python -m src.cli dogfood validate-claims --path docs/landing/blog/
РАСХОЖДЕНИЕ: habr-01-cpg-vs-sast.md:42
  Заявлено: 95 обработчиков
  Реально:  97
  SQL:      SELECT COUNT(DISTINCT full_name) FROM nodes_method WHERE...

ОК: habr-08-meta-audit.md
  Все 6 числовых утверждений подтверждены

---
Файлов: 9 | Утверждений: 23 | ОК: 22 | Расхождений: 1 | Время: 847мс
```

За 847 миллисекунд — проверка всех числовых утверждений в 9 статьях серии. Одно расхождение найдено автоматически.

### Конфигурация правил

Все сопоставления ключевое слово → SQL хранятся в `config.yaml`. Добавить новое правило = одна запись в YAML. Ноль строк Python.

## 8. Сквозная демонстрация: валидация пользовательских историй

Разделы 3–7 описывали отдельные механизмы. Раздел 8 — это *реальная* многочасовая сессия, где CPG-конвейер работал от первого промпта до финального отчёта. Четыре итерации. Четыре бага, невидимых юнит-тестам. Обнаруженных только благодаря графу.

### Задача

Разработать механизм приёмки пользовательских историй: для каждой из 83 выполненных историй проверить, что функциональность доступна хотя бы через один из пяти интерфейсов (CLI, REST API, TUI, MCP, ACP).

### Версия 1: полный провал

ИИ-ассистент создал `StoryValidationRunner` (450 строк) по образцу существующего `AuditRunner` — образец был подставлен хуком обогащения промпта. 39 юнит-тестов — все прошли. Первый запуск:

```
Историй: 83 | Полное покрытие: 0 | Частичное: 0 | Нет покрытия: 83
```

Ноль из 83. Полный провал. При этом — 39 из 39 юнит-тестов зелёные.

**Баг №1: разделители путей.** CPG хранит пути в формате Windows (`src\cli\`), а SQL-запросы использовали Unix-разделители (`src/cli/`). Ни один путевой шаблон не совпал. Юнит-тесты с моками не содержат реальных путей.

**Баг №2: незарегистрированный сценарий.** Оркестратор пытался вызвать S01 (онбординг) через `ScenarioInvoker`, но S01 — интерактивный сценарий, не зарегистрированный для пакетного вызова.

Оба бага были обнаружены *одним запуском на реальном CPG*. Один SQL-запрос показал формат путей:

```sql
SELECT DISTINCT SUBSTR(filename, 1, 20) FROM nodes_method LIMIT 10;
```

### Версия 4: борьба с ложными срабатываниями

Седьмая история подряд показывала «высокий» уровень доверия по REST API через функцию `get_acp_transport` в `acp.py`. Это *ложное* срабатывание: функция отвечает за ACP-транспорт, а не за RBAC, OAuth или аудит.

**Баг №3: усечение путей в регулярном выражении.** Выражение `src/\w+/` извлекало только первый сегмент пути — `src/api/` из `src/api/auth/acp.py`. Любая функция в `src/api/` матчилась с высоким доверием.

**Баг №4: отсутствие стоп-слов.** Общие слова вроде «analysis» матчили MCP-инструменты, не связанные с историей.

Исправления: полные пути в регулярных выражениях, список исключаемых файлов, стоп-слова. Вынос 30+ констант в конфигурацию.

## 9. 13 механизмов код-ревью

По итогам сессии валидации мы расширили конвейер с 5 хуков до 13 механизмов. Каждый привязан к конкретному хуку и решает конкретную задачу.

### Высокий приоритет

| № | Механизм | Где работает | Что делает |
|---|---------|-------------|------------|
| 1 | Проверка влияния на интерфейсы | Хук пост-коммита | Предупреждает, если изменённый метод виден через REST API, CLI, MCP |
| 2 | Проверка полноты регистрации | Хук перед правкой | Если добавляется новый обработчик — есть ли он в реестре сценариев? |
| 3 | Обнаружение межмодульных зависимостей | Хук пост-коммита | Предупреждает, если изменение в `workflow/` затрагивает `api/` |
| 4 | Реальный diff в анализе пул-реквеста | Обработчик PR | Анализирует реальные изменённые файлы через `git diff`, а не угадывает |

### Средний приоритет

| № | Механизм | Где работает | Что делает |
|---|---------|-------------|------------|
| 5 | Видимость через интерфейсы | Обогащение промпта | Показывает, через какие интерфейсы доступен метод — *до* генерации |
| 6 | Повышение риска для публичных API | Калькулятор рисков | API-поверхность увеличивает оценку риска на 15% |
| 7 | Отслеживание вызывающих через интерфейсы | Анализ сигнатур | Если меняется сигнатура метода — проверяет, кто его вызывает из интерфейсов |

## 10. Тренд качества

Разовый анализ коммита полезен. Но техлиду нужна *динамика*: растёт ли сложность? Появляется ли мёртвый код? Сколько TODO накопилось за спринт?

### Таблица истории качества

Таблица в том же DuckDB, что и CPG:

```sql
CREATE TABLE IF NOT EXISTS cpg_quality_history (
    commit_hash   VARCHAR,
    timestamp     TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    branch        VARCHAR,
    total_methods INT,
    total_files   INT,
    avg_cc        FLOAT,
    max_cc        INT,
    high_cc_count INT,
    dead_methods  INT,
    todo_count    INT,
    debug_count   INT
)
```

После каждого успешного анализа коммита `CommitAnalyzer` автоматически вызывает `record_snapshot()` — сбор метрик по всему CPG и запись в историю. Ноль дополнительных команд.

### Тренд

```bash
$ python -m src.cli dogfood trend --commits 5
Коммит       Дата         Методы   Средн.ЦС   Мёртв  Выс.ЦС   TODO
```

## 11. Пять уроков

За три месяца использования конвейера мы сформулировали пять принципов:

### 1. Скорость хука < бюджета генерации

Если хук работает 30 секунд, а генерация — 10 секунд, разработчик отключит хук. Наши бюджеты: старт сессии 8с, отправка промпта 10с, перед инструментом 6с, после инструмента 58с (из них 40с — обновление CPG, которое всё равно пришлось бы делать). Реальное время: обычно 1–5с.

### 2. Контекст ДО генерации > проверка ПОСЛЕ

Обогащение промпта предотвращает ошибки. Пост-анализ находит. Предотвращение дешевле. Обогащение (10с) экономит целый цикл генерации-проверки-переделки (минуты).

### 3. Граф > линтер

Линтер видит файл. Граф видит систему. Радиус поражения, разветвлённость, вложенность вызовов — эти метрики невозможно получить из одного файла. CPG строит граф свойств *всей* кодовой базы — и хуки используют его за миллисекунды.

### 4. Один `setup` — и забыл

```bash
$ python -m src.cli dogfood setup --repo . --db data/projects/codegraph.duckdb
```

Одна команда устанавливает: git-хуки (3 шт.), хуки ИИ-ассистента (5 шт.), проверяет CPG, загружает правила валидации. Дальше конвейер работает автоматически. Если разработчик не знает о хуках — он всё равно защищён.

### 5. Асинхронность — ключ к внедрению

Синхронные хуки блокируют работу. Наш конвейер: git-хуки работают в фоне, CPG обновляется асинхронно, хук пост-коммита — единственный синхронный (и то — 58с бюджета хватает на инкрементальное обновление + анализ). Разработчик не ждёт.

## 12. Как воспроизвести

Три шага для любого проекта:

### Шаг 1: Парсинг кодовой базы

```bash
# Установка GoCPG (Go 1.26+, CGO для tree-sitter)
cd gocpg && CGO_ENABLED=1 go build -o gocpg.exe ./cmd/gocpg

# Парсинг
./gocpg parse --input=/path/to/your/code --output=project.duckdb --lang=python
```

GoCPG поддерживает 11 языков: C, C++, Go, Python, JavaScript, TypeScript, Java, Kotlin, C#, PHP, 1C:Предприятие.

### Шаг 2: Установка конвейера

```bash
# Одна команда
python -m src.cli dogfood setup --repo /path/to/repo --db project.duckdb

# Что произойдёт:
# ✓ Git-хуки: post-commit, post-merge, post-checkout
# ✓ Хуки ИИ-ассистента: 5/5 настроены
# ✓ CPG: свежесть проверена
# ✓ Валидация утверждений: правила загружены
```

### Шаг 3: Работайте как обычно

```bash
# Вайбкодинг с автоматической верификацией
claude  # Запуск ИИ-ассистента

# Проверка тренда
python -m src.cli dogfood trend --commits 10

# Валидация числовых утверждений
python -m src.cli dogfood validate-claims --path docs/

# Валидация пользовательских историй
python -m src.cli dogfood validate-stories --db project.duckdb
```

Всё. Конвейер включается автоматически. Каждый коммит анализируется. Каждый промпт обогащается. Каждый пул-реквест верифицируется.

> Вычислимый факт не соврёт. `COUNT(*)` не округлит. `cyclomatic_complexity > 10` не пропустит.
> Граф свойств кода — единственный честный рецензент при вайбкодинге.
