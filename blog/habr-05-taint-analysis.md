## Хук

> Паттерн `sprintf + SPI_execute` встречается в PostgreSQL 1 297 раз. Из них реальных SQL-инъекций — 13. Остальные 1 284 — ложные срабатывания.

Это не гипотетическая ситуация. Это результат первой версии нашего сканера безопасности — паттерн-детектора, который искал потенциально опасные вызовы по текстовому совпадению. Точность — 70%. Каждый третий алерт оказывался ложным.

Для внутреннего инструмента это ещё терпимо: разработчик проверит руками. Но для продукта, который должен интегрироваться в CI/CD и блокировать мёрж — каждый ложный алерт стоит доверия. После 10 пустых срабатываний команда начинает игнорировать все предупреждения. Инструмент, которому не верят, хуже, чем отсутствие инструмента.

Мы прошли путь от текстового поиска до анализа потоков данных через 5 фаз — и на каждой фазе срезали часть ложных срабатываний. Вот как это работало.

## 1. Фаза 1: сопоставление шаблонов (точность ~70%)

Первая версия сканера (`CodeStringTracer`) работала просто:

1. Найти все вызовы опасных функций — `SPI_execute`, `SPI_exec`, `system`, `popen`
2. Посмотреть ±20 строк вокруг вызова: есть ли там конструирование строки — `sprintf`, `appendStringInfo`, `strcat`?
3. Проверить, используется ли санитизация — `quote_literal`, `quote_identifier`
4. Вычислить оценку риска

Вот формула оценки:

```
итоговый_риск = базовый_риск × (1 − эффективность_санитайзера × 0.7)
```

Где `базовый_риск` зависит от паттерна:

| Паттерн | Риск |
|---------|------|
| `sprintf` с `%s` | 0.9 |
| `strcat` | 0.9 |
| `strcpy` | 0.8 |
| конкатенация через `+` | 0.7 |

На PostgreSQL (52 тыс. методов, 1.4 млн вызовов) сканер отработал за 2–3 секунды и нашёл:

- **13 SQL-инъекций** высокого риска (в том числе 10 в `matview.c` — в обработке материализованных представлений)
- **34 потенциальных shell-инъекции** в утилитах и contrib-модулях
- **0 ложных срабатываний** среди SQL-инъекций высокого риска

Цифра «0 ложных срабатываний» выглядит хорошо, но есть нюанс: мы установили порог `risk_score ≥ 0.8`. Стоит опустить порог до 0.5 — и точность падает до 70%.

### Почему сопоставление шаблонов упирается в потолок

Фундаментальная проблема: **близость в тексте ≠ связь по данным**. Функция `sprintf` в строке 630 может форматировать строку, которая **никогда** не попадёт в `SPI_execute` в строке 650. Между ними — условие, которое направляет данные в другую ветку.

И наоборот: данные из `getenv()` в строке 10 могут через цепочку из 5 функций добраться до `SPI_execute` в другом файле — и ни один паттерн в радиусе 20 строк этого не увидит.

Конкретные ограничения:

| Ограничение | Последствие |
|-------------|-------------|
| Радиус поиска ±20 строк | Не видит поток данных через вызовы функций |
| Нет отслеживания значений | Не различает пользовательский ввод и константу |
| Нет анализа управляющего потока | Считает все ветки равновероятными |
| Нет межпроцедурного анализа | Не отслеживает данные через границы функций |

## 2. Фаза 2: анализ потоков данных (точность ~85–90%)

Перелом произошёл, когда мы наполнили таблицу `edges_reaching_def` — 8.4 миллиона рёбер, связывающих определения переменных с их использованиями. Это рёбра графа свойств кода (CPG), которые показывают, **куда** данные реально попадают.

Вместо «поищи `sprintf` рядом с `SPI_execute`» алгоритм стал работать так:

1. Найти **источники** заражённых данных — вызовы `getenv`, `recv`, `fgets`, `PQgetvalue` (41 функция из доменного плагина PostgreSQL)
2. От каждого источника запустить **обход в ширину** по рёбрам `edges_reaching_def` — это и есть реальный поток данных, записанный в графе
3. Проверить, достигает ли заражённый поток **приёмника** — `SPI_execute`, `system`, `popen` (48 функций из доменного плагина)
4. По пути проверить, встретился ли **санитайзер** — `quote_literal`, `pg_escape_string` (7 функций с оценкой эффективности)

```
Источник → [reaching_def] → ... → [reaching_def] → Приёмник
  getenv()                                          SPI_execute()
              ↑ Если на пути нет санитайзера — уязвимость
```

### Рекурсивный SQL-запрос для поиска заражённых путей

Ключевой запрос к DuckDB, который делает всю работу:

```sql
WITH RECURSIVE taint_flow AS (
    -- Базовый случай: источники заражения
    SELECT
        nc.id AS node_id,
        nc.id AS source_id,
        nc.name AS source_func,
        0 AS depth,
        CAST(nc.id AS VARCHAR) AS path
    FROM nodes_call nc
    WHERE nc.name IN ('getenv', 'recv', 'fgets', 'PQgetvalue')

    UNION ALL

    -- Рекурсия: следуем по рёбрам потока данных
    SELECT
        rd.dst AS node_id,
        tf.source_id,
        tf.source_func,
        tf.depth + 1,
        tf.path || '->' || CAST(rd.dst AS VARCHAR)
    FROM taint_flow tf
    JOIN edges_reaching_def rd ON rd.src = tf.node_id
    WHERE tf.depth < 15  -- Ограничение глубины
)
-- Ищем: какие приёмники достижимы из заражённых источников
SELECT DISTINCT
    tf.source_func,
    nc_sink.name AS sink_func,
    nc_sink.filename,
    nc_sink.line_number,
    tf.depth AS path_length
FROM taint_flow tf
JOIN nodes_call nc_sink ON nc_sink.id = tf.node_id
WHERE nc_sink.name IN ('SPI_execute', 'SPI_exec', 'system', 'popen')
ORDER BY tf.depth;
```

Один рекурсивный запрос к DuckDB заменяет весь эвристический анализ на основе шаблонов. И работает не с текстовой близостью, а с **реальными** путями передачи данных.

### Что мы получили

| Метрика | Шаблоны (Фаза 1) | Потоки данных (Фаза 2) |
|---------|:---:|:---:|
| Истинные срабатывания | ~70% | 85–90% |
| Ложные срабатывания | ~20% | 10–15% |
| Пропущенные уязвимости | ~30% | 10–15% |
| Межпроцедурный анализ | нет | да |
| Время на PostgreSQL | ~100 мс | ~500 мс |

Пятикратное замедление — с 100 мс до 500 мс — оправданная цена за 20% точности.

### Межпроцедурный анализ: как данные пересекают границы функций

Таблица `edges_parameter_link` связывает фактический аргумент вызова с формальным параметром вызываемой функции. Это позволяет **проследить** заражение через цепочку вызовов:

```
файл A:  input = getenv("USER")
         process_input(input)          ←— фактический аргумент
                  ↓ edges_parameter_link
файл B:  void process_input(char* data)  ←— формальный параметр
               build_query(data)
                  ↓ edges_parameter_link
файл C:  void build_query(char* val)
               SPI_execute(val)        ←— приёмник, заражён!
```

Паттерн в радиусе 20 строк это не увидит — данные проходят через три файла. Анализ потоков — видит.

## 3. Фаза 3: учёт управляющего потока (точность ~92–93%)

Анализ потоков данных дал 85–90%, но всё ещё считал все пути одинаково вероятными. Рассмотрим пример:

```c
char* input = getenv("USER");        // Источник заражения

if (validate_input(input)) {
    SPI_execute(input);              // Приёмник — но за валидацией!
} else {
    return ERROR;
}
```

Фаза 2 сообщает: «Путь `getenv → SPI_execute`, риск высокий». Но `SPI_execute` выполняется **только если** `validate_input` вернул истину. Если валидация действительно проверяет вход — это не уязвимость, а защита.

Мы добавили анализ **графа управляющих зависимостей** (таблица `edges_cdg` — 3.5 миллиона рёбер). CDG показывает, какие узлы зависят от каких условий — то есть какой код выполняется только при определённых ветвлениях.

### Классификация условий

Не все условия одинаково полезны. Мы классифицируем их на 5 типов:

| Тип | Ключевые слова | Пример | Влияние на риск |
|-----|----------------|--------|-----------------|
| Проверка санитизации | `quote_literal`, `escape`, `sanitize` | `if (is_sanitized(x))` | Сильно снижает |
| Проверка валидации | `validate`, `check`, `verify`, `is_valid` | `if (validate_input(x))` | Снижает |
| Обработка ошибок | `NULL`, `error`, `errno`, `failed` | `if (input == NULL)` | Снижает вероятность |
| Проверка авторизации | `auth`, `permission`, `admin`, `acl` | `if (is_admin())` | Снижает вероятность |
| Флаг конфигурации | `enable`, `disable`, `flag`, `config` | `if (enable_feature)` | Снижает вероятность |

### Формула условной вероятности

Каждое условие на пути уменьшает вероятность выполнения:

```
P(путь выполнится) = 0.5^(количество условий)
```

Одно условие — 50%. Два условия — 25%. Три — 12.5%. Если среди условий есть проверка санитизации или валидации — вероятность дополнительно умножается на 0.7.

Конкретный пример — путь через два условия, одно из которых — валидация:

```
Уязвимость: getenv → SPI_execute

Без учёта управляющего потока:
  Риск: 0.85 (ВЫСОКИЙ)
  Условия: [не анализировались]

С учётом управляющего потока:
  Условия: [
    validate_input(input) — проверка валидации
    is_admin() — проверка авторизации
  ]
  P(выполнение) = 0.5² × 0.7 = 0.175 (17.5%)
  Риск: 0.42 (СРЕДНИЙ)
```

Риск упал с ВЫСОКОГО до СРЕДНЕГО. Это не значит, что уязвимости нет — это значит, что команда безопасности может заняться **сначала** безусловными путями (риск 0.85), а потом — условными (риск 0.42).

### Эффект на практике

Из 13 SQL-инъекций в PostgreSQL, найденных на Фазе 1:

- **8 путей** оказались безусловными — риск подтверждён
- **3 пути** были за одной проверкой — риск снижен до СРЕДНЕГО
- **2 пути** были за двумя проверками — риск снижен до НИЗКОГО

Точность выросла до 92–93%: false positive rate упал с 10–15% до 6–8%.

## 4. Фаза 4: чувствительность к полям структур (точность ~94–96%)

Предыдущие фазы обрабатывали структуры как единое целое: если `user→username` заражён — вся структура `user` считается заражённой. Это порождает ложные срабатывания:

```c
typedef struct {
    char* username;  // Из пользовательского ввода (заражено)
    int user_id;     // Из базы данных (безопасно)
} User;

User* user = get_user_input();

// Безопасно: поле user_id — из БД
sprintf(query, "SELECT * FROM logs WHERE uid=%d", user->user_id);
SPI_execute(query);   // Фаза 3 скажет: ВЫСОКИЙ риск (неправильно!)

// Опасно: поле username — от пользователя
sprintf(query, "SELECT * FROM users WHERE name='%s'", user->username);
SPI_execute(query);   // Фаза 3 скажет: ВЫСОКИЙ риск (правильно!)
```

Без учёта полей — оба вызова `SPI_execute` будут помечены как опасные. С учётом полей — только второй.

Таблица `nodes_field_identifier` (500 тыс. узлов) хранит обращения к полям структур с каноническими именами вроде `user->username` или `data.raw_input`. Мы построили `FieldTaintMap` — карту заражённости на уровне отдельных полей:

```
FieldTaintMap для user:
  user->username  : заражено (источник: getenv)
  user->user_id   : чисто (источник: БД)
  user->email     : заражено (источник: getenv)
```

Теперь при достижении приёмника мы проверяем: **какое именно поле** используется в опасном вызове. Если `user->user_id` — false positive устранён. Если `user->username` — уязвимость подтверждена.

Ещё один выигрыш: различение сырого и санитизированного поля в одной структуре:

```c
data->raw_input = getenv("USER");
data->sanitized = quote_literal(data->raw_input);

SPI_execute(data->sanitized);  // Поле санитизировано → НИЗКИЙ
SPI_execute(data->raw_input);  // Поле сырое → ВЫСОКИЙ
```

Без чувствительности к полям оба вызова получают одинаковый риск. С ней — различаются.

## 5. Фаза 5: генерация гипотез по базе CWE/CAPEC

Все предыдущие фазы работают реактивно: мы задаём источники и приёмники, а сканер ищет пути между ними. Но откуда берётся список источников и приёмников? Кто решает, что `getenv` — это источник, а `SPI_execute` — приёмник?

Мы собрали базу знаний из 214 записей CWE (Common Weakness Enumeration — международная классификация программных слабостей) и связанных с ними атак CAPEC (классификация методов атак). Для каждой записи хранятся: распространённость, эксплуатируемость, затронутые языки и паттерны обнаружения.

Вот верхушка для языка C:

| CWE | Название | Распространённость | Эксплуатируемость |
|-----|----------|:---:|:---:|
| CWE-120 | Переполнение буфера | 0.85 | 0.90 |
| CWE-476 | Разыменование NULL | 0.80 | — |
| CWE-416 | Использование после освобождения | 0.75 | — |
| CWE-190 | Переполнение целого числа | 0.70 | — |
| CWE-78 | Инъекция команд ОС | 0.65 | 0.95 |
| CWE-89 | SQL-инъекция | 0.60 | 0.95 |

### Алгоритм: от классификации слабостей к исполняемым запросам

Идея вдохновлена статьёй [VulAgent](https://arxiv.org/abs/2509.11523): вместо ручного перечисления паттернов — автоматическая генерация **тестируемых гипотез**.

```
Шаг 1: Перечисление
  Взять топ CWE для языка проекта

Шаг 2: Декартово произведение
  Гипотезы = CWE × Методы_атаки × Приёмники × Источники

Шаг 3: Шаблонизация
  «Если [источник] достигает [приёмник] без [санитайзер],
   то [CWE] делает возможной [атаку]»

Шаг 4: Ранжирование
  Приоритет = 0.4 × частота_CWE
            + 0.3 × похожесть_на_известные_атаки
            + 0.3 × экспозиция_в_кодовой_базе

Шаг 5: Синтез запросов
  Для каждой гипотезы — SQL-запрос к DuckDB
```

### Конкретный пример: гипотеза для CVE-2025-8714

PostgreSQL 17.6 исправил три уязвимости. Одна из них — CVE-2025-8714 (CVSS 8.8): имена объектов БД, содержащие метасимволы, без экранирования попадали в вывод `pg_dump`, что позволяло выполнить произвольный код при восстановлении из дампа.

Генератор гипотез формулирует это так:

```
Гипотеза: Если имена объектов базы данных (PQgetvalue, getTables)
  достигают функций формирования вывода (appendPQExpBuffer)
  без экранирования (fmtId, fmtQualifiedId),
  то CWE-94 делает возможным выполнение кода при pg_restore.
```

И автоматически синтезирует запрос:

```sql
SELECT DISTINCT
    c.name AS приёмник,
    c.filename,
    c.line_number,
    src.name AS источник_данных
FROM nodes_call c
JOIN edges_reaching_def rd ON rd.dst = c.id
JOIN nodes_call src ON rd.src = src.id
WHERE c.name IN ('appendPQExpBuffer', 'appendStringInfo')
  AND src.name IN ('PQgetvalue', 'PQfname', 'getTables')
  AND c.code NOT LIKE '%fmtId%'
  AND c.code NOT LIKE '%fmtQualifiedId%'
ORDER BY c.filename, c.line_number;
```

Запрос находит места, где данные из БД (имена таблиц) попадают в буфер вывода **без** экранирования через `fmtId`. Именно эти места были исправлены в патче PostgreSQL 17.6.

### Валидация: три CVE, два найдены

Мы проверили генератор гипотез на трёх CVE из PostgreSQL 17.6:

| CVE | Описание | CVSS | Найден? |
|-----|----------|:---:|:---:|
| CVE-2025-8714 | Инъекция кода через pg_dump | 8.8 | Да |
| CVE-2025-8715 | Инъекция через перенос строки в pg_dump | 8.8 | Да |
| CVE-2025-8713 | Утечка данных через статистику оптимизатора | Средний | Частично |

Детекция CVE-2025-8713 — частичная: генератор нашёл функции `analyze_*` без проверки прав доступа (`pg_class_aclcheck`), но оценка риска оказалась ниже порога из-за специфики задачи — здесь проблема не в потоке данных, а в отсутствии проверки авторизации.

## 6. Верификация: гибридный подход

Мы не заменили шаблоны потоками данных — мы построили **гибрид**. Класс `TaintVerifiedScanner` работает в два прохода:

**Первый проход — быстрый паттерн-детектор.** Находит все потенциально опасные вызовы за 2–3 секунды.

**Второй проход — верификация потоками данных.** Для каждой находки первого прохода проверяет: существует ли реальный путь от заражённого источника до этого приёмника?

Между проходами — фильтр параметризованных запросов. Восемь регулярных выражений отсеивают безопасные вызовы вроде `cursor.execute("SELECT * FROM users WHERE id=$1", [user_id])` ещё до анализа потоков — это экономит время.

Результат верификации:

```
Не верифицировано (нет реального пути данных):
  Было: CRITICAL → стало: MEDIUM
  Было: HIGH → стало: MEDIUM
  Было: MEDIUM → стало: LOW

Верифицировано (путь подтверждён):
  Уровень сохраняется + добавляется трасса заражения
```

Это позволяет команде безопасности **сначала** просматривать верифицированные находки (с подтверждённым путём от источника до приёмника), а потом — непроверенные (которые могут оказаться ложными).

## 7. Эволюция точности: итоговая таблица

> **От синтаксиса к семантике.** Каждая фаза ниже — это ещё один слой семантической информации поверх синтаксического дерева. Инженеры, знакомые с Roslyn, узнают ту же прогрессию: `SyntaxTree` (фаза 1 — видим текст) → `SemanticModel` (фазы 2–4 — понимаем, откуда данные и какого они типа) → решатель ограничений (фаза 5 — Z3 проверяет достижимость путей). Ни grep, ни ast-grep, ни Semgrep не выходят за пределы фазы 1 — они работают на уровне синтаксиса. Точность 94–96% достигается только на уровне семантической модели.

| Фаза | Метод | Точность | Ложные срабатывания | Что срезает |
|:---:|-------|:---:|:---:|-------------|
| 1 | Шаблоны (±20 строк) | ~70% | ~20% | — |
| 2 | Потоки данных (reaching_def) | 85–90% | 10–15% | «Строка рядом» ≠ «данные связаны» |
| 2+ | Межпроцедурный анализ (parameter_link) | 87–90% | 10–12% | Данные через границы функций |
| 3 | Управляющие зависимости (CDG) | 92–93% | 6–8% | Путь за валидацией ≠ уязвимость |
| 4 | Чувствительность к полям | 94–96% | 4–6% | Чистое поле структуры ≠ заражённое |
| 5 | Генерация гипотез (CWE/CAPEC) | — | — | Автоматизирует выбор что искать |
| 6 | Гибридная верификация | 94–96% | 3–5% | Шаблон + подтверждение потоком |

Каждая фаза добавляет один тип информации из графа свойств кода:

- **Фаза 2**: рёбра `edges_reaching_def` (поток данных)
- **Фаза 2+**: рёбра `edges_parameter_link` (связь аргументов через вызовы)
- **Фаза 3**: рёбра `edges_cdg` (управляющие зависимости)
- **Фаза 4**: узлы `nodes_field_identifier` (обращения к полям)

Каждое ребро графа — это информация, которую текстовый поиск **принципиально** не может извлечь из кода.

## 8. Символьное выполнение: следующий рубеж

На границе анализа — интеграция с Z3 (SMT-решатель — инструмент автоматической проверки логических ограничений) для проверки **достижимости путей**. Если на пути от источника до приёмника стоит условие `if (len < 0)`, а `len` — это `size_t` (беззнаковый тип, всегда ≥ 0), то путь **физически невозможен** и уязвимость — ложное срабатывание.

`PathConstraintTracker` собирает условия ветвлений на пути (до 20 ограничений) и отправляет их Z3 на проверку выполнимости. Это дополнительно снижает ложные срабатывания с 4–6% до 3–5%.

Мы сознательно ограничиваем глубину: до 20 ограничений на путь и до 15 переходов по рёбрам. Символьное выполнение всей кодовой базы — экспоненциально дорогая задача. Но точечная проверка конкретных путей, **уже найденных** анализом потоков, работает быстро и окупается.
