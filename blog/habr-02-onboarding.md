## Хук

> 60% рабочего времени разработчика уходит на **понимание кода**, а не на его написание.

Это не интуитивная оценка — это данные исследования Atlassian Developer Experience за 2025 год. Для новых сотрудников цифра ещё выше: первые 3-6 месяцев junior и middle-разработчик тратят до 80% времени, пытаясь разобраться в кодовой базе.

Документация устарела. Архитектурные решения живут в головах 2-3 senior-инженеров. Один из них уволился в прошлом квартале — и вместе с ним ушли ответы на вопросы, которые новичок задаёт каждый день.

Знакомая ситуация? В этой статье разберём, **почему онбординг буксует**, что такое граф кода и как он сокращает время адаптации в 6 раз — с реальными примерами запросов.

## 1. Почему онбординг занимает 3-6 месяцев

### Симптомы

Типичная картина в компании с кодовой базой 500K+ строк:

| Проблема | Что происходит |
|----------|---------------|
| **Documentation decay** | README написан 2 года назад. Архитектурные ADR покрывают 20% решений. Swagger устарел на 3 версии API |
| **Tribal knowledge** | «Спроси Сашу, он знает, как работает биллинг» — а Саша в отпуске / уволился / перегружен |
| **Code archaeology** | Новичок открывает функцию на 200 строк, видит 15 вызовов в другие модули и не понимает, с чего начать |
| **Bus factor = 1** | Один человек знает критичную подсистему. Если он уйдёт — команда встанет |

### Корневая причина

Проблема не в людях и не в процессах. Проблема в **инструментах**. IDE показывает файл. Git показывает историю. Grep ищет текст. Ни один из них не отвечает на вопрос:

> «Что произойдёт с системой, если я изменю эту функцию?»

Для ответа нужно понимать **зависимости** — кто вызывает функцию, какие данные через неё проходят, какие модули затронет изменение. Это знание живёт в **структуре кода**, а не в документации.

## 2. Что такое граф кода

Code Property Graph (CPG) — это **структурированное представление кодовой базы** в виде графа, который объединяет:

- **Синтаксис** (AST) — как написан код
- **Поток управления** (CFG) — в каком порядке выполняются инструкции
- **Зависимости по данным** (PDG/DDG) — как значения переменных передаются между функциями

Когда вся кодовая база представлена как единый граф, можно задавать вопросы на **естественном языке**:

```
«Кто вызывает функцию process_payment?»
«Какие модули затронет изменение в AuthService?»
«Покажи все пути данных от HTTP-запроса до базы данных»
```

Вместо часового путешествия по файлам — ответ за **2-3 миллисекунды**.

## 3. Три запроса, которые меняют онбординг

### Запрос 1: «Кто вызывает эту функцию?»

Новичок видит функцию `validate_order()` и хочет понять её роль в системе.

**Без графа кода**: Ctrl+Shift+F по проекту → 47 совпадений → половина в тестах → половина в комментариях → 10 реальных вызовов в 7 файлах → 40 минут на понимание контекста.

**С графом кода**:
```
Вопрос: «Кто вызывает validate_order и в каком контексте?»

Ответ:
→ OrderService.create_order() [line 45] — при создании нового заказа
→ OrderService.update_order() [line 112] — при изменении существующего
→ BatchProcessor.process_batch() [line 78] — при массовой обработке
→ API endpoint POST /orders [handler.go:34] — точка входа

Граф вызовов: HTTP Request → handler → OrderService → validate_order → [3 валидатора]
```

**Результат**: 40 минут → 10 секунд. Новичок сразу видит полную картину.

### Запрос 2: «Что сломается, если я изменю эту функцию?»

Новичку поручили добавить поле в структуру `UserProfile`. Вопрос: где ещё она используется?

**Без графа кода**: Поиск по имени типа → ручной обход вызовов → пропущена сериализация в JSON → баг в production через неделю.

**С графом кода**:
```
Вопрос: «Impact analysis для структуры UserProfile»

Ответ:
Прямые зависимости (12):
→ UserService: create, update, delete, get_by_id
→ AuthService: login, register (использует UserProfile.email)
→ NotificationService: send_welcome (использует UserProfile.name)
→ API: 3 эндпоинта сериализуют UserProfile в JSON
→ DB: миграция таблицы users

Транзитивные зависимости (8):
→ OrderService (через UserService.get_by_id)
→ PaymentService (через AuthService.get_current_user)
→ ReportGenerator (через агрегацию UserProfile)

Рекомендация: обновить JSON-сериализацию в api/serializers.go
и миграцию в db/migrations/
```

**Результат**: Новичок видит **полный blast radius** изменения до того, как написал первую строку кода.

### Запрос 3: «Как устроена подсистема биллинга?»

Вместо «спроси Сашу» — вопрос к графу.

**С графом кода**:
```
Вопрос: «Архитектурная карта модуля billing»

Ответ:
Модуль billing/ (14 файлов, 2 340 строк):

Точки входа:
→ POST /api/billing/charge — BillingHandler.charge()
→ CRON job — RecurringBillingJob.run() (каждые 24 часа)

Ключевые компоненты:
→ BillingService — оркестратор (fan-out: 5 зависимостей)
→ PaymentGateway — интеграция со Stripe/YooKassa
→ InvoiceGenerator — PDF-генерация
→ TaxCalculator — расчёт НДС (зависит от UserProfile.country)

Внешние зависимости:
→ UserService (получение профиля)
→ OrderService (получение суммы заказа)
→ NotificationService (отправка чека)

Метрики:
→ Cyclomatic complexity: средняя 8, максимум 23 (BillingService.process)
→ Fan-in/Fan-out: BillingService — hotspot (fan-out = 5)
→ Последнее изменение: 12 дней назад (автор: @alex)
```

**Результат**: Новичок получает структурированное понимание подсистемы за 30 секунд. Без Саши.

## 5. Что нужно для старта

### Индексация

Граф кода строится автоматически из исходного кода. Не нужно писать документацию, расставлять аннотации или менять процессы.

- **1 миллион строк кода** → индексация за ~30 минут
- **Инкрементальное обновление** при каждом коммите → секунды
- **11 языков**: C, C++, Go, Python, JavaScript, TypeScript, Java, Kotlin, C#, PHP, 1С

### Интеграция

- CI/CD: GitHub Actions, GitLab CI (готовые интеграции)
- IDE: REST API + MCP-сервер для подключения к любому IDE
- On-premise: Docker / Kubernetes, данные не покидают контур

### Процесс онбординга с графом кода

```
День 1:  Новичок получает доступ к CodeGraph
         → Задаёт вопросы: «Какие модули есть?», «Как устроен API?»
День 2-3: Изучает свою подсистему через граф
         → Impact analysis перед первым PR
День 4-5: Первый PR с пониманием контекста
         → Code review проходит быстрее (reviewer видит тот же граф)
Неделя 2: Самостоятельная работа
         → Граф отвечает на вопросы, которые раньше шли к senior
```

## 6. А что с документацией?

Граф кода **не заменяет** документацию. Он заменяет ту часть знаний, которая **никогда не попадает** в документацию:

- Неявные зависимости между модулями
- Реальный поток данных (не то, что нарисовано на диаграмме год назад)
- Актуальные метрики кода (complexity, fan-in/fan-out, hotspots)
- История изменений с привязкой к структуре (кто и когда менял этот модуль)

Документация отвечает на «зачем». Граф кода отвечает на «как» и «что».

## Заключение

Онбординг разработчика — это не проблема HR или менторинга. Это проблема **доступа к знаниям о коде**. Когда знания заперты в головах людей и разбросаны по тысячам файлов, никакой процесс не поможет.

Граф кода делает структуру кодовой базы **queryable** — доступной для запросов. Новичок задаёт вопрос — и получает ответ за миллисекунды. Не от перегруженного senior-инженера, а от инструмента, который видит всю кодовую базу целиком.

С 3-6 месяцев до 2-3 недель. Это не маркетинг — это математика: 600x ускорение поиска × 15x ускорение review × снятие зависимости от tribal knowledge.
