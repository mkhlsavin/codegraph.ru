### Корневая причина

У нас есть CLAUDE.md на 600+ строк, README, архитектурные заметки. Но даже это покрывает процентов двадцать вопросов, которые задаёт новый разработчик.

Потому что большинство вопросов — не про «зачем», а про «как»:

- Кто вызывает `execute_agent_safely`? (Ответ: никто — она мёртвая, мы её удалили при догфуддинге.)
- Что произойдёт, если я изменю `CPGQueryService`? (Ответ: затронет 11 модулей-примесей, из которых он собран, и все 21 сценарий.)
- Как данные текут от API-запроса до DuckDB? (Ответ: через 4 слоя — маршрутизатор, сервис, оркестратор, хранилище.)

Эти ответы живут не в документации, а в структуре кода. Инструмент, который видит эту структуру — граф свойств кода — отвечает на них за миллисекунды.

## Что такое граф свойств кода

Граф свойств кода (Code Property Graph, CPG) — это структурированное представление кодовой базы, объединяющее:

- Синтаксическое дерево — как написан код
- Граф потока управления — в каком порядке выполняются инструкции
- Граф зависимостей по данным — как значения переменных передаются между функциями
- Граф вызовов — кто кого вызывает

Когда вся кодовая база представлена как единый граф, можно задавать вопросы на естественном языке:

```
«Кто вызывает функцию aggregate_partial_results?»
«Какие модули затронет изменение в CPGQueryService?»
«Покажи все пути данных от HTTP-запроса до базы данных»
```

Вместо часового путешествия по файлам — ответ за миллисекунды. Не из документации, которая устарела вчера, а из самого кода, который актуален прямо сейчас.

## Четыре запроса, которые меняют онбординг

### Запрос 1: «Кто вызывает эту функцию?»

Новый разработчик видит `aggregate_partial_results()` в `src/workflow/error_handling.py` и хочет понять, нужна ли она.

**Без графа**: `Ctrl+Shift+F` по проекту → 12 совпадений → половина в тестах → половина — импорты без вызовов → 20 минут на понимание контекста.

**С графом**: Запрос через МСР-сервер — Model Context Protocol, протокол для интеграции с IDE — или API:
```
codegraph_find_callers("aggregate_partial_results")

→ Вызывается из:
  → security_workflow() [security/main_workflow.py:87]
  → performance_workflow() [performance.py:112]
  → architecture_workflow() [architecture.py:93]
  → 3 композитных сценария через invoker

Граф вызовов: Композитный оркестратор → Параллельный вызов 9 подсценариев
             → aggregate_partial_results() → AggregatedResults
```

20 минут → 3 секунды. Новичок видит не список файлов, а контекст: функция агрегирует результаты параллельных подсценариев в композитных потоках работ.

### Запрос 2: «Что затронет моё изменение?»

Новичку поручили добавить поле в `AgentResult` — базовую структуру данных для результатов агентов.

**Без графа**: Поиск по имени → ручной обход вызовов → пропущена сериализация в JSON → неожиданная ошибка в API через неделю.

**С графом**:
```
codegraph_impact("AgentResult")

→ Прямые зависимости (7):
  → execute_agent_safely() — создаёт AgentResult
  → aggregate_partial_results() — собирает в список
  → WorkflowErrorHandler — хранит .result
  → 3 сценария потоков работ через error_handling
  → to_dict() — сериализация в JSON (обновить!)

→ Транзитивные зависимости (12):
  → security_workflow → API-обработчик → JSON-ответ клиенту
  → audit_composite → _collect_metrics → отчёт аудита
```

Новичок видит полный радиус поражения изменения до того, как написал первую строку. И видит, что нужно обновить `to_dict()` — иначе новое поле не попадёт в API-ответ.

## Как это работает

### Индексация

Граф свойств кода строится автоматически из исходного кода. Никаких аннотаций, документации или настройки не требуется.

```bash
# Построить граф из исходного кода
gocpg parse --input=/path/to/your/project \
            --output=data/projects/myproject.duckdb \
            --lang=python --include-tests

# Задать вопрос
python -m src.cli query "Кто вызывает функцию process_payment?"
```

- 11 языков: C, C++, Go, Python, JavaScript, TypeScript, Java, Kotlin, C#, PHP, 1С
- 33 аналитических прохода (типы, поток управления, потоки данных, вызовы, метрики)
- Инкрементальное обновление при каждом коммите — секунды вместо полной пересборки

### Четыре способа взаимодействия

| Способ | Для кого | Пример |
|--------|---------|--------|
| CLI | Разработчик в терминале | `python -m src.cli query "Кто вызывает X?"` |
| МСР-сервер | Интеграция с IDE (Claude Code, Zed, Cursor) | `codegraph_find_callers("X")` |
| REST API | Интеграция в CI/CD | `POST /api/v1/query` |
| TUI | Интерактивный терминал | `/cpg query "SELECT ..."` |

МСР-сервер даёт языковой модели внутри IDE прямой доступ к графу свойств кода. Вместо того чтобы модель угадывала структуру проекта по видимым файлам, она знает — потому что спрашивает граф.

44 МСР-инструмента: поиск вызывающих/вызываемых, анализ воздействия, горячие точки, объяснение модулей, поиск по шаблонам, анализ потоков данных, диаграммы зависимостей, автоматическое исправление уязвимостей.

## Что граф заменяет, а что — нет

Граф свойств кода не заменяет документацию. Он заменяет ту часть знаний, которая никогда не попадает в документацию:

| Вопрос | Источник ответа |
|--------|----------------|
| «Зачем мы используем DuckDB, а не PostgreSQL для CPG?» | Документация, ADR |
| «Кто вызывает `_collect_metrics` и какие данные передаёт?» | **Граф свойств кода** |
| «Какова бизнес-логика расчёта скидок?» | Документация, вики |
| «Что затронет добавление поля в `AgentResult`?» | **Граф свойств кода** |
| «Почему мы выбрали LangGraph для оркестрации?» | Документация, ADR |
| «Какой метод — горячая точка со сложностью 133 и без тестов?» | **Граф свойств кода** |

Документация отвечает на «зачем». Граф — на «как», «что», «кто» и «сколько». И, в отличие от документации, граф всегда актуален — он строится из кода, а не из намерений.

Ответы на «кто вызывает?», «что затронет?», «сколько связей?» — вычислимы: обход графа, SQL-агрегация, BFS по рёбрам вызовов. Для них не нужна языковая модель — нужны предвычисленные данные из 33 аналитических проходов.

LLM подключается на границе: когда нужно объяснить найденное, сравнить альтернативы или сформулировать рекомендацию.

В терминах Roslyn: `ISymbol.GetMembers()` скажет, что метод существует и откуда вызывается — это структурный факт. «Зачем этот метод спроектирован именно так» — вопрос для человека или LLM.
