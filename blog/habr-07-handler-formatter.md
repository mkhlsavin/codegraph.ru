## Хук

> «Где определена функция `heap_insert`?» — 800 мс, $0.003, ответ LLM.
> «Где определена функция `heap_insert`?» — 47 мс, $0, ответ обработчика.

Один и тот же вопрос. Один и тот же результат. Разница — в архитектуре.

В первой версии CodeGraph каждый запрос пользователя отправлялся в LLM. Задать вопрос — подождать 800 мс — получить ответ. Для сложных аналитических запросов это оправданно: LLM синтезирует текст из нескольких источников, строит выводы, объясняет причинно-следственные связи.

Но 60–90% запросов к CodeGraph — **структурные**: «покажи граф вызовов», «найди уязвимости», «какие методы имеют сложность > 20», «сгенерируй документацию для модуля X». Ответ на каждый из них — это SQL-запрос к DuckDB, шаблон Markdown и подстановка данных. LLM здесь не нужна.

Мы построили пятиуровневую архитектуру, которая перехватывает структурные запросы **до** вызова LLM — и отвечает за < 100 мс. LLM остаётся для сложных случаев: свободного анализа, объяснений «почему», сравнения архитектурных решений. Вот как это устроено.

## 1. Наивный подход и его стоимость

Наивная архитектура AI-инструмента для работы с кодом:

```
Запрос пользователя
    → Prompt + контекст → LLM → Ответ
```

Каждый запрос — вызов LLM. Для корпоративного инструмента с 10 разработчиками, делающими по 50 запросов в день, это 500 вызовов в день. При средней стоимости $0.003 за запрос (input + output tokens) — $1.50 в день, $45 в месяц. Для 100 разработчиков — $450 в месяц только на LLM.

Кроме денег — время. LLM отвечает за 500–2 000 мс. Для запроса «покажи граф вызовов функции X» разработчик ждёт две секунды, хотя ответ — это SQL-запрос к DuckDB (5 мс) и шаблон Markdown (1 мс).

И ещё — **нестабильность**. LLM может сформулировать один и тот же факт по-разному в каждом вызове. Для структурных отчётов (аудит безопасности, метрики качества, граф вызовов) нужна **воспроизводимость**: один вход — один выход.

## 2. Пять уровней перехвата

Архитектура Handler-Formatter — это пять уровней, через которые проходит каждый запрос. Запрос «проваливается» вниз, пока не будет перехвачен — или не достигнет LLM на последнем уровне.

```
┌───────────────────────────────────────────┐
│  Уровень 1: Определение намерения         │
│  Ключевые слова → тип запроса + уверенность│
└──────────────────┬────────────────────────┘
                   ↓
┌───────────────────────────────────────────┐
│  Уровень 2: Реестр обработчиков           │
│  Приоритетный выбор обработчика           │
└──────────────────┬────────────────────────┘
                   ↓
┌───────────────────────────────────────────┐
│  Уровень 3: Обработчик (SQL-запросы)      │
│  CPG-запросы + данные доменного плагина    │
└──────────────────┬────────────────────────┘
                   ↓
┌───────────────────────────────────────────┐
│  Уровень 4: Форматтер (Markdown-шаблон)   │
│  Таблицы, списки, бейджи, локализация     │
└──────────────────┬────────────────────────┘
                   ↓
┌───────────────────────────────────────────┐
│  Уровень 5: LLM (только если нужен)       │
│  Свободный текст, объяснения, анализ      │
└───────────────────────────────────────────┘
```

Уровни 1–4 — **структурный анализ**: ключевые слова, SQL-запросы к графу, шаблоны Markdown. Уровень 5 — **LLM**: свободный текст, объяснения, рассуждения. Это реализация принципа **AST-first, LLM-second**: всё, что можно вычислить из структуры кода, вычисляется без модели. LLM подключается только для задач, которые принципиально не сводятся к обходу графа — объяснение «почему», сравнение альтернатив, генерация рекомендаций.

Если запрос перехвачен на уровне 4 — LLM не вызывается.

## 3. Уровень 1: определение намерения без LLM

Классический подход: отправить запрос пользователя в LLM с промптом «определи намерение». Это стоит один LLM-вызов **на каждый** запрос, ещё до начала работы.

Наш подход: морфологическое сопоставление ключевых слов. Запрос «Найди SQL-инъекции» матчится на ключевое слово «SQL-инъекции» → тип `vulnerability_scan`, уверенность 0.95.

```python
class SecurityIntentDetector:
    INTENT_PATTERNS = {
        "vulnerability_scan": {
            "keywords": [
                "vulnerability", "SQL injection", "buffer overflow",
                "command injection", "XSS", "taint",
                # Русские варианты
                "уязвимость", "SQL-инъекция", "переполнение буфера",
                "инъекция команд", "анализ заражения",
            ],
            "priority": 3,
        },
        "hardcoded_credentials": {
            "keywords": [
                "hardcoded", "credentials", "password", "secret",
                "захардкоженные", "пароли", "секреты", "ключи",
            ],
            "priority": 5,
        },
    }
```

Ключевые особенности:

**Двуязычность.** Каждый паттерн содержит и английские, и русские ключевые слова. Русские слова матчатся с учётом морфологии: «уязвимостей», «уязвимости», «уязвимость» — один паттерн.

**Приоритеты.** Более специфичные паттерны проверяются первыми (меньший приоритет = раньше). «Захардкоженные пароли» (приоритет 5) проверяется раньше, чем общий «уязвимости» (приоритет 10).

**Извлечение метаданных.** Из запроса «Найди SQL-инъекции с высоким уровнем риска» детектор извлекает: тип = `vulnerability_scan`, тип уязвимости = `sql_injection`, фильтр по серьёзности = `high`.

Стоимость: **0 LLM-вызовов**. Время: **< 1 мс**.

## 4. Уровень 2: реестр обработчиков

Реестр (`HandlerRegistry`) — это список обработчиков, отсортированных по приоритету. Каждый обработчик реализует метод `can_handle()`, который проверяет: «это мой тип запроса?»

```python
registry = HandlerRegistry("security")

@registry.register(priority=3)
class VulnerabilityScanHandler(BaseHandler):
    def can_handle(self, query_info):
        return query_info["type"] in ("vulnerability_scan", "hardcoded_credentials")

@registry.register(priority=10)
class TaintAnalysisHandler(BaseHandler):
    def can_handle(self, query_info):
        return query_info["type"] == "taint_analysis"

@registry.register(priority=20)
class SecurityOverviewHandler(BaseHandler):
    def can_handle(self, query_info):
        return query_info["type"] == "security_overview"
```

Реестр перебирает обработчики по приоритету и возвращает первый, где `can_handle()` вернул `True`. Если ни один не подошёл — запрос передаётся дальше, к LLM.

У каждого из 13 сценариев CodeGraph — свой реестр. В сумме — **97 обработчиков** по всем сценариям.

Стоимость: **0 LLM-вызовов**. Время: **< 1 мс**.

## 5. Уровень 3: обработчик — SQL-запросы вместо генерации

Обработчик — это место, где происходит работа. Но не генерация текста, а **запросы к базе данных**. Вот как работает обработчик документации:

```python
class FunctionDocHandler(BaseHandler):
    def handle(self, query_info):
        target = query_info.get("target")  # "heap_insert"

        # Шаг 1: Найти метод в CPG по имени (SQL-запрос)
        results = self.cpg.search_methods_by_name_pattern(target)

        # Шаг 2: Пакетно получить метаданные (один запрос)
        rich_data = self._get_rich_parameters([target])
        params = rich_data["parameters"].get(target, [])
        return_type = rich_data["return_types"].get(target, "")

        # Шаг 3: Связанные функции (граф вызовов)
        related = self._get_related_functions(target, limit=5)

        # Шаг 4: Описание из комментариев CPG (не генерация!)
        descriptions = self.cpg.get_functions_descriptions([target])

        # Шаг 5: Метрики качества (предвычисленные колонки)
        metrics = self.cpg.get_method_quality_metrics_batch([target])

        return HandlerResult(
            data={"functions": [{ ... }]},
            should_return=True,  # ← Вернуть сразу, без LLM
        )
```

Пять шагов — пять SQL-запросов к DuckDB. Ни одного вызова LLM.

Ключевой флаг — `should_return=True`. Он говорит оркестратору: «ответ готов, LLM не нужна». Если обработчик решает, что запрос слишком сложный, он устанавливает `should_return=False` и передаёт собранные данные как контекст для LLM — тогда LLM не начинает с нуля, а дополняет структурированные данные.

### Пакетные операции

Наивный подход: для каждого метода — отдельный запрос к DuckDB (N+1 problem). Наш подход:

```python
# Один запрос на 100 методов (не 100 запросов)
batch_descriptions = self.cpg.get_functions_descriptions(all_func_names)
batch_metrics = self.cpg.get_method_quality_metrics_batch(all_func_names)
```

Стоимость: **0 LLM-вызовов**. Время: **5–50 мс** (зависит от количества результатов).

## 6. Уровень 4: форматтер — шаблоны вместо генерации

Форматтер превращает структурированные данные обработчика в Markdown. Это не LLM-генерация — это подстановка в шаблон:

```python
class DocumentationReportFormatter(BaseFormatter):
    @classmethod
    def format_function_documentation(cls, data, language="en"):
        loc = cls.get_localization(language)
        functions = data.get("functions", [])

        answer = f"# {loc.get('documentation.title')}\n\n"
        answer += f"**{loc.get('common.total')}:** {len(functions)}\n\n"

        for idx, func in enumerate(functions, 1):
            name = func["method_name"]
            answer += f"## {idx}. `{name}`\n\n"

            # Бейдж видимости
            if func.get("is_public_api"):
                answer += "📗 Public API\n\n"

            # Сигнатура
            answer += f"```\n{func['signature']}\n```\n\n"

            # Параметры
            for param in func.get("parameters", []):
                answer += f"- `{param['name']}` ({param['type']})\n"

            # Метрики
            cc = func.get("quality_metrics", {}).get("cyclomatic_complexity")
            if cc:
                answer += f"\n**Сложность:** {cc}\n"

        return answer
```

**Локализация.** Все строки — через `get_text()` с ключом и языком. Русский и английский загружаются из YAML (`src/config/localization/{en,ru}.yaml`). Добавить третий язык — создать YAML-файл.

**Воспроизводимость.** Один вход — один выход. Всегда. Никаких вариаций формулировок между запусками.

Стоимость: **0 LLM-вызовов**. Время: **< 5 мс**.

## 7. Доменные плагины: 11 языков, ноль строк Python

Откуда обработчик берёт список опасных функций для PostgreSQL, если он написан для всех языков одинаково?

Из **доменного плагина**. Доменный плагин — это набор из 10 YAML-файлов, описывающих специфику конкретного языка или фреймворка:

```
src/domains/postgresql_v2/config/
├── annotations.yaml    # Источники заражения, приёмники
├── subsystems.yaml     # Подсистемы (executor, planner, storage...)
├── patterns.yaml       # Паттерны безопасности, привязка к CWE
├── security.yaml       # Точки входа атак, поверхность атаки
├── performance.yaml    # Функции управления памятью
├── debugging.yaml      # Функции отладки
├── transactions.yaml   # Управление транзакциями
├── compliance.yaml     # Правила соответствия
├── intent.yaml         # Ключевые слова для определения намерения
└── prompts.yaml        # Промпты для LLM (если он вызывается)
```

Пример — `annotations.yaml` для PostgreSQL:

```yaml
annotations:
  taint_sources:
    - function: pq_getbyte
      source_type: network_input
    - function: pq_getmessage
      source_type: network_input
    - function: SPI_execute
      source_type: sql
    - function: getenv
      source_type: environment
    # ... 50+ источников ...

  taint_sinks:
    - function: SPI_execute
      sink_type: sql_execution
    - function: system
      sink_type: command_execution
    # ... 48 приёмников ...
```

Обработчик обращается к плагину через абстрактный интерфейс:

```python
from src.domains import get_active_domain

domain = get_active_domain()
sources = domain.get_taint_sources()      # 50+ функций из YAML
sinks = domain.get_taint_sinks()          # 48 функций из YAML
memory = domain.get_memory_functions()    # palloc, pfree, repalloc...
subsystems = domain.get_subsystem_names() # executor, planner, storage...
```

**Ключевое правило:** код обработчика **никогда** не содержит имён функций, модулей или паттернов конкретного домена. Всё — из YAML. Это значит, что один и тот же обработчик работает для PostgreSQL, Python/Django, JavaScript, Go, Kotlin и 1С:Предприятие.

| Плагин | Языки/фреймворки | Особенности |

## 9. Когда LLM всё-таки нужна

Не все запросы структурные. Граница проходит между **обнаружением** (вычислимо) и **объяснением** (требует рассуждения). Обнаружение — «47 методов со сложностью > 20», «3 пути от getenv до SPI_execute» — это факты из графа, которые структурный анализ извлекает за миллисекунды. Объяснение — «почему архитектор выбрал именно такое разделение модулей» — это рассуждение, для которого нужен LLM.

Вот примеры, которые проваливаются на уровень 5:

| Запрос | Почему нужна LLM |
|--------|------------------|
| «Объясни, зачем в PostgreSQL два уровня блокировок» | Требует объяснения концепции |
| «Сравни подходы к обработке ошибок в executor и planner» | Требует сравнительного анализа |
| «Что будет, если убрать функцию X из кодовой базы?» | Требует рассуждения о последствиях |
| «Предложи рефакторинг модуля Y» | Требует генерации кода |

Для таких запросов обработчик устанавливает `should_return=False` и передаёт собранные данные как контекст:

```python
return HandlerResult(
    data=collected_data,
    should_return=False,       # ← Передать дальше, к LLM
    llm_context={
        "cpg_evidence": results,
        "related_functions": callers,
        "metrics": metrics,
    },
)
```

LLM получает не голый запрос, а запрос + структурированные данные из CPG. Это уменьшает длину промпта (не нужно описывать контекст словами) и повышает качество ответа.

## 10. Unified Harness: одно ядро для всех интерфейсов

Handler-Formatter архитектура — это внутренняя механика. Но CodeGraph доступен через четыре интерфейса: CLI, TUI, REST API и протоколы для IDE (MCP, ACP). Каждый интерфейс — это тонкий клиент над общим ядром.

Мы вдохновились архитектурой [OpenAI Codex](https://openai.com/index/unlocking-the-codex-harness/): один Harness (ядро), который оборачивает все сервисы — CPG, граф вызовов, анализ уязвимостей, векторный поиск — и предоставляет единый внутренний API.

```
┌─────────────────────────────────────────────┐
│              CodeGraphHarness                │
│  CPGQuery │ CallGraph │ Taint │ Retriever   │
│  Session  │ Approval  │ Config              │
└──────────────────┬──────────────────────────┘
                   │
       ┌───────────┼───────────┐
       ↓           ↓           ↓
    ┌─────┐   ┌─────────┐  ┌──────────────┐
    │ CLI │   │   TUI   │  │ MCP │ ACP │ API│
    └─────┘   └─────────┘  └──────────────┘
```

Добавить новый интерфейс (например, Slack-бота) — это написать адаптер, который вызывает `harness.execute(query)`. Вся логика обработчиков, форматтеров, доменных плагинов и LLM-fallback — внутри Harness.

| Двуязычность (EN/RU) | дублирование промптов | YAML-локализация |

Снижение стоимости — 60–90% в зависимости от профиля запросов. Для команды, которая в основном ищет уязвимости и строит графы вызовов, — ближе к 90%. Для команды, которая задаёт свободные аналитические вопросы, — ближе к 60%.
